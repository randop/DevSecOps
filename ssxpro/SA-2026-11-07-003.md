**AI Model:** Anthropic Claude Sonnet 5.5

## Executive Summary

This report presents an independent static security review of ssxpro (v0.1.0), a Rust workspace implementing a QUIC (quiche/BoringSSL) remote shell for Linux with Ed25519 public-key authentication, a privilege-separated design (TLS/auth monitor, session broker, network workers), and an io_uring-centric I/O path. The review covers the server (`ssxd`), client (`ssx`), protocol, crypto, IPC, sandbox and session code, plus `SPEC.md`, `docs/`, configuration examples, `deny.toml`, and the test bootstrap script. The software is a pre-release (4 commits, 0.1.0) and its own SPEC states that independent security review is required before public exposure.

**Overall Assessment**: The code shows strong engineering discipline in several areas: strict bounded protocol decoding, `openat2`-based file access with post-open `fstat` checks, HMAC-authenticated single-use session tokens, fd-passing validation, fuzz targets, exact dependency pins, and fail-closed configuration. However, the implementation does **not yet deliver the privilege-separation threat model that `SPEC.md` describes**. The most important gap is that the network-facing QUIC/TLS worker threads run as root inside the main `ssxd` process with no seccomp, Landlock, or credential drop on the packet-handling thread, while the SPEC states workers are unprivileged and contained. Several monitor-side controls (unrestricted host-key signing, no server-nonce freshness tracking, a permissive monitor syscall policy) would also fail to hold against a compromised worker, which the SPEC explicitly places in scope.

**Risk Level**: Medium–High for any internet-exposed deployment (High if the current architecture is deployed as-is on a public port 22); acceptable for development use, consistent with the project's own "do not expose publicly before review" statement.

**Limitations**: This was a static review. The project was not built or executed (no Rust toolchain was available in the review environment, so `cargo audit`, `cargo deny`, Clippy and the fuzz targets were not run). Runtime-dependent claims are labelled as such. Not every file received equal depth (see Methodology).

## Methodology

- Cloned the repository at commit `0e344ef`; inventoried 6 workspace crates and ~11,300 lines of Rust, plus 5 fuzz targets, scripts and docs
- Full manual review of: `ssxpro-server` (`main.rs`, `broker.rs`, `ipc.rs`, `session.rs`, `tls.rs`; the connection-handling, auth, rate-limit, Retry-token and PTY-pump portions of `transport.rs`), `ssxpro-proto` (monitor/broker/session-token codecs, control-frame decoder, state machines), `ssxpro-crypto` (key/file helpers, auth signing input, authorized_keys/known_hosts parsers), the sandbox/seccomp/Landlock code in `ssxpro-io`, and the client host-key pinning path
- Lighter review only: `ssxpro-config` (YAML validation), the remainder of `ssxpro-io` (kernel probes, UDP/io_uring plumbing), the remainder of `ssxpro-server/src/transport.rs`, `ssxpro-client/src/terminal.rs`, fuzz targets and the e2e test scripts
- Trace of attacker-controlled data from the UDP socket through QUIC, the control stream decoder, the worker→monitor auth IPC, the monitor→worker token, and the worker→broker `OpenSession` request to `fork/exec` of the login shell
- Comparison of implementation against the claims in `SPEC.md` (threat model, milestone requirements) and `docs/`
- Candidate issues were verified against the code before being reported. One candidate was **rejected**: a local-user FIFO denial of service on `~/.ssx/authorized_keys` is *not* possible because `openat2_entry` forces `O_NONBLOCK` and the file is checked with `fstat` after opening
- Standards considered: CWE Top 25 classes relevant to Rust/Linux daemons, the project's own threat model, and common remote-login-daemon practice (OpenSSH privilege separation)

## Findings

### High Priority Issues

#### 1. Network-Facing Workers Run as Root and Are Not Sandboxed (New)

**Severity**: High **Status**: Confirmed by source review (deployment unit files are not in the repository)

**Description**: `transport::serve()` runs the QUIC/TLS workers as threads of the main `ssxd` process (`std::thread::scope`). The TLS monitor and session broker are forked from this same process before the workers start, and the monitor reads a root-owned `0600` host key and the broker calls `setresuid`, so the parent is expected to run as root. No credential drop (`setresuid`/`setgid`, `nobody`, capability drop) occurs for the worker threads anywhere in the server crate. `serve_worker()` only calls `harden_worker_process()`, which sets `PR_SET_NO_NEW_PRIVS` and `PR_SET_DUMPABLE=0`. The seccomp allowlist and Landlock deny-all in `sandbox_worker()` are installed only on the small `ssxd-pty-pump` thread (seccomp is per-thread here, `TSYNC` is not used for workers), not on the thread that parses untrusted UDP, QUIC and TLS data.

**Risk**: `SPEC.md` states "Workers are unprivileged and receive only PTY master descriptors" and that a compromised worker "must not be able to read the host key ... or spawn arbitrary host processes." In the current code, a memory-safety or logic bug in quiche or BoringSSL (large C/Rust parsing surface reachable pre-authentication) yields code execution as **root with unrestricted syscalls**, which defeats the monitor/broker separation entirely. Because the worker also holds the monitor IPC sockets, the PTY master descriptors for live sessions, and the broker channel, the architecture provides no containment at that boundary.

**Recommendation**:

- Run workers as separate unprivileged processes (distinct uid, e.g. `ssxd-net`) forked before the network sockets are used, passing only the pre-bound UDP socket, monitor IPC and broker IPC descriptors
- Apply seccomp (`SECCOMP_RET_KILL_PROCESS` for violations) and a Landlock deny-all policy to **every** worker thread, using `TSYNC` or applying before thread creation
- Add an integration test that asserts the worker's uid, `NoNewPrivs`, seccomp mode and capability set from `/proc/<pid>/status`
- Until fixed, update `SPEC.md` so it no longer claims unprivileged workers

### Medium Priority Issues

#### 2. Monitor Does Not Track Server-Nonce Freshness; Captured Auth Requests Are Replayable by a Compromised Worker (New)

**Severity**: Medium (High once Finding 1 is fixed) **Status**: Confirmed

**Description**: The server nonce is generated by the **worker** (`transport.rs`, on `Hello`) and passed to the monitor inside the `Authenticate` IPC request. The monitor (`tls::verify_login_request`) verifies the Ed25519 signature over `"ssxpro-auth-v1" || server_nonce || client_nonce || spki_hash || user || pubkey` but has no record of which nonces it issued, no expiry, and no single-use cache. Any previously observed valid `(user, pubkey, server_nonce, client_nonce, signature)` tuple verifies again, and each success mints a fresh broker session token.

**Risk**: A compromised worker (explicitly in scope per `SPEC.md`) that has seen one legitimate login can request unlimited new shells as that user, at any later time, without the user's involvement. This violates the stated property that a compromised worker "must not be able to ... choose the authenticated principal." It is currently overshadowed by Finding 1 but becomes the primary weakness once workers are confined.

**Recommendation**: Have the monitor generate and own the server nonce (return it to the worker for relay), store it with a short expiry, and consume it on first `Authenticate`. Reject unknown, expired or reused nonces.

#### 3. Unrestricted Host-Key Signing Oracle (New)

**Severity**: Medium **Status**: Confirmed

**Description**: The monitor's `TlsEd25519Sign` handler signs any byte string up to 8192 bytes supplied by the worker (`pair.sign(input)` in `tls::serve_signing_requests`). It does not check that the input has the TLS 1.3 server `CertificateVerify` structure (64 spaces, the context string `TLS 1.3, server CertificateVerify`, a NUL, and a 32/48-byte transcript hash).

**Risk**: A compromised worker can obtain host-key signatures over arbitrary data, enabling forged `CertificateVerify` values for handshakes it does not terminate. Combined with the documented lack of TLS channel binding (Finding 14), this enables man-in-the-middle relaying of other users' authentication on the network path.

**Recommendation**: Enforce the exact TLS 1.3 server `CertificateVerify` prefix and length in the monitor before signing; reject everything else. Optionally rate-limit signing requests.

#### 4. Monitor Sandbox Is Much Weaker Than Described (New)

**Severity**: Medium **Status**: Confirmed

**Description**: The root monitor holds the host key seed and parses user-controlled `authorized_keys` files. `sandbox_tls_monitor()` applies only a seccomp allowlist and no Landlock policy. The allowlist includes `open`, `openat`, `openat2` and `write` with no argument filtering (so root can open or create arbitrary files for writing), `mmap`/`mprotect` with no `PROT_EXEC` restriction, and `getgroups`. The process keeps full root credentials and capabilities. The code comment describes the policy as "signing-only," which overstates it.

**Risk**: A parsing or logic bug reachable through a local user's key file or the IPC channel could be turned into arbitrary root file writes, defeating the stated defense in depth. The Rust implementation lowers, but does not remove, this risk (`unsafe` blocks and BoringSSL/NSS are in the same process).

**Recommendation**: Add a Landlock ruleset that grants read-only access to `/etc/passwd`, `/etc/group`, `/etc/shells`, `/etc/nsswitch.conf` and the configured home-directory roots, and nothing else. Filter `openat*` flags to read-only, forbid `PROT_EXEC` mappings after startup, and drop all capabilities except those strictly needed to read user files.

#### 5. Authentication Failure Limiter Can Be Exhausted to Lock Out All New Clients (New)

**Severity**: Medium **Status**: Confirmed by source review (not exercised at runtime)

**Description**: `AuthFailureLimiter` tracks failures per source IP in a table capped at `MAX_SOURCES = 4096` with a 60-second window. `allow()` returns `false` for any **new** source once the table is full. Entries are added by `record_failure()` on each failed login. An attacker who can originate from many addresses (a single IPv6 /64 provides effectively unlimited addresses, and QUIC Retry address validation does not prevent this because the attacker owns them) can insert 4096 entries with one failed login each, after which all new legitimate sources are refused for the remainder of the window, repeatedly. Limits are also keyed on the full IPv6 address rather than a prefix, so per-source throttling is trivially evaded.

**Recommendation**: Key IPv6 sources by /64 (and optionally /56), evict least-recently-seen entries instead of refusing new sources, and keep a separate small global budget so legitimate users are not locked out. Apply the same prefix logic to `InitialRateLimiter`.

#### 6. Login Session Lacks Account Policy, Auditing and Resource Controls (New)

**Severity**: Medium **Status**: Confirmed in source; items marked (runtime) not verified

**Description**: `session::spawn_login_session` drops privileges correctly (`setgroups`, `setresgid`, `setresuid` in the right order) and clears the environment, but source review found no equivalent of the account controls that remote-login daemons normally provide: no PAM or shadow checks (locked or expired accounts, `/etc/nologin`, access rules), no audit login-uid or session id (system audit records will not attribute user actions), no `utmp`/`wtmp`/`lastlog`, no rlimits or cgroup placement, and no explicit `umask`. The PTY slave is obtained with `TIOCGPTPEER` but never `fchown`ed to the user, so it likely remains `root:tty` (runtime). `SPEC.md` lists `clone3`, `CLONE_INTO_CGROUP`, `cgroup.kill` and `PR_SET_CHILD_SUBREAPER` as required for M6; the implementation uses `std::process::Command` and process-group signals instead, so descendants that call `setsid`/`setpgid` survive session teardown.

**Risk**: Disabled or expired accounts holding a valid key can still log in, user actions are poorly attributable, and a user can exhaust host resources or leave processes behind. This matters for compliance-driven or multi-user deployments.

**Recommendation**: Integrate PAM `acct_mgmt`/`session` (or implement equivalent checks), set the audit login uid, apply rlimits and a per-session cgroup, set `umask`, `fchown` the PTY slave to the user and `tty` group, and implement the cgroup-based teardown promised in the SPEC.

#### 7. Supply-Chain and Assurance Process Gaps (New)

**Severity**: Medium **Status**: Confirmed

**Description**: Security-critical dependencies are pinned exactly (`quiche = "=0.30.0"`, `boring`/`boring-sys = "=4.22.0"`, `io-uring = "=0.7.15"`, `yaml_serde = "=0.10.7"`) and `Cargo.lock` (96 packages) is committed, which is good. However, no CI workflow is present in the repository (no `.github/`), although `docs/dependencies.md` and `SPEC.md` rely on `cargo audit`, `cargo deny` and a kernel CI matrix; `.cargo/audit.toml` and `deny.toml` exist but nothing runs them. Exact pins also mean security fixes in quiche or BoringSSL (the highest-risk code in the product) are not picked up automatically. The server also contains ~210 `unsafe` occurrences and a custom seccomp BPF filter, neither of which has been independently reviewed.

**Recommendation**: Add CI that runs `cargo audit`, `cargo deny check`, Clippy, tests and the fuzz targets on a schedule; subscribe to quiche/BoringSSL advisories and update pins promptly; treat the update procedure in `docs/dependencies.md` as a tracked security SLA; commission the independent review the SPEC calls for before public exposure.

### Low Priority Issues

#### 8. Single Auth Helper Thread on a Network-Reachable Path (New)

**Severity**: Low **Status**: Confirmed

All login authorization runs through one monitor helper thread fed by a queue of 8, including NSS lookups and reads of user key files (which may live on slow network storage). Work that exceeds the 3-second wait leaves the helper blocked while callers get a denial, and a full queue turns into denials for everyone. Per-source rate limits mitigate but do not remove this (see Finding 5). Use a small worker pool with per-job deadlines and consider caching results briefly.

#### 9. File-Descriptor Leak in SCM_RIGHTS Receive Path (New)

**Severity**: Low **Status**: Confirmed

In `ipc::SessionChannel::recv`, only the first `MAX_SCM_FDS` (8) received descriptors are wrapped in `OwnedFd`, but the control buffer can hold up to 28. If a peer attaches 9 to 28 descriptors, the extras are installed in the receiver and never closed, even though the call then returns an error. The broker is the exposed receiver (from a compromised worker) and the channel is closed afterwards, so the leak is bounded, but it should be closed deterministically: size the control buffer to exactly `MAX_SCM_FDS` descriptors and wrap every received fd before validating counts.

#### 10. Wall-Clock Time Used for Token Lifetime, Replay Cache and Retry Tokens (New)

**Severity**: Low **Status**: Confirmed

Session tokens, the broker's used-token cache and QUIC Retry tokens use `SystemTime`. A forward clock step followed by a backward step can evict replay-cache entries while a token is still considered unexpired, permitting a one-time replay of a token already held by a compromised worker. Use `CLOCK_MONOTONIC`/`CLOCK_BOOTTIME` for lifetimes and cache pruning.

#### 11. Client Host-Key Pin Check Can Be Skipped if No Peer Certificate Is Returned (New)

**Severity**: Low **Status**: Confirmed (defensive issue; not shown to be exploitable)

In `ssxpro-client/src/transport.rs`, `pin_checked = true` is set outside the `if let Some(cert_der) = conn.peer_cert()` block, so if no certificate is available the client proceeds to `Hello` and authentication without any host-key verification. A TLS 1.3 server normally must present a certificate, so this is a fail-open code path rather than a known bypass. Make a missing certificate a hard error.

#### 12. Implementation and Specification Drift (New)

**Severity**: Low **Status**: Confirmed

- `Hello` feature bits: the SPEC says unknown bits are rejected; the server matches `Hello { version: 1, .. }` and ignores `features`
- Landlock failure on unsupported kernels is downgraded to a warning, while the SPEC says required features fail closed
- `SPEC.md` itself records an unresolved baseline conflict (6.12 baseline vs. `IORING_ENTER_EXT_ARG_REG` requiring 6.13) and lists per-source limits as an M8 item although a partial limiter exists
- `ssxd` accepts the explicit `--yes-I-know-permission-risks-go-ahead-please` flag, which disables ownership and mode checks on the configuration, host key and all `authorized_keys` sources at once; there is no guard that restricts it to non-root or loopback use

Reconcile the SPEC with the code, or fix the code, before any release.

#### 13. Input Hygiene: TERM, Usernames, Logging (New)

**Severity**: Low **Status**: Confirmed

- `TERM` accepts any printable ASCII up to 64 bytes (including `/`, `.`, `$`, quotes) and is exported unchanged into the login shell environment. Because the shell runs as the authenticated user this does not cross a privilege boundary, but an allowlist such as `[A-Za-z0-9._+-]` is a cheap hardening step
- The wire decoder rejects ASCII control characters in usernames but permits Unicode control and bidirectional-override characters. The monitor escapes the username in its own logs, but verbose (`-v`) worker logging prints it unescaped
- The monitor-side request decoder only rejects NUL and ASCII whitespace; it does not repeat the control-character check, so it relies on the worker having validated input, which the threat model does not allow it to assume

#### 14. No TLS Channel Binding (Documented Limitation)

**Severity**: Low **Status**: Documented in `SPEC.md` (M0 spike)

Authentication binds the server SPKI hash and both nonces, but not the TLS session, because quiche does not expose exporters. Exploiting this requires the host key or a signing oracle (see Finding 3), which is why it is rated Low. Keep the planned exporter-based binding as a tracked requirement.

#### 15. Server-Wide authorized_keys Is a Skeleton Key (By Design)

**Severity**: Low **Status**: Documented

A key in `auth.server_authorized_keys` authenticates as **any** non-root local account (subject to `allow_root` and shell policy). This is clearly documented and the file must be root-owned `0600`, but operators should be warned prominently and the option should be disabled by default (the example config enables the path).

### Informational

#### 16. Hardening Settings With Limited or Unintended Effect

`PR_SET_NO_NEW_PRIVS` is set on the user's login shell, which blocks `sudo`, `su` and file-capability binaries (a functional decision to document). `PR_SET_DUMPABLE=0` set in `pre_exec` is reset by `execve`, so it provides no protection for the exec'd shell.

#### 17. `panic = "abort"` Makes Worker `catch_unwind` Ineffective

`Cargo.toml` sets `panic = "abort"` for release builds, so the `catch_unwind` around each worker does not isolate a panic; any panic (including in the roughly 180 non-test `unwrap`/`expect` call sites, which were not individually triaged) terminates the whole daemon and every session. Prefer returning errors on all input-dependent paths.

#### 18. Kernel Attack Surface

The design depends on io_uring (Linux 6.12+). The worker and monitor policies allow `io_uring_enter`/`io_uring_register`, and ring restrictions are enabled by default, which is good, but io_uring remains a large kernel attack surface and is disabled by policy on some distributions (`kernel.io_uring_disabled`). Document this trade-off and keep the kernel patched.

#### 19. Minor Items

`read_host_key_seed()` returns the seed by value (`Ok(*seed)`), leaving an unzeroed copy in the caller's stack; the host key is a raw unencrypted seed file (acceptable for a daemon, but worth stating); `kill_group()` signals `-pgid` after the leader has been reaped, a theoretical PID-reuse window mitigated because the pgid is held while any member lives.

## Positive Findings

- Protocol decoders are bounded, reject trailing bytes, non-canonical varints, unknown types and bad UTF-8, and use fixed-size buffers; `ssxpro-proto` is `#![forbid(unsafe_code)]`
- Session tokens are HMAC-SHA256 authenticated, short-lived (30 s), single-use at the broker, and compared in constant time; workers cannot forge identities
- File access uses `openat2` with `RESOLVE_NO_SYMLINKS` (and `BENEATH`/`NO_MAGICLINKS` for user files), `O_NONBLOCK`, and post-open `fstat` ownership/mode checks, avoiding symlink and TOCTOU attacks
- Root login is disabled by default; shell must be listed in `/etc/shells`; privilege drop order and `PR_SET_PDEATHSIG` race handling are correct
- SCM_RIGHTS handling rejects unexpected descriptors from workers and validates cmsg bounds; the monitor escapes usernames in logs
- QUIC Retry with HMAC tokens, per-IP initial-packet limits, one auth attempt per connection, and deadlines for Hello/auth/open
- Exact dependency pins, committed lockfile, `deny.toml` (allowed licenses, unknown registries denied), workspace lints (`clippy::all = deny`, `unsafe_op_in_unsafe_fn = deny`), fuzz targets for the main parsers, and zeroization of key material in most paths

## Code Quality Security Assessment

#### Input Validation

**Rating**: Good

Wire and IPC decoders are strict and consistent. The weaknesses are redundancy gaps between layers (Finding 13) and the TERM allowlist.

#### Memory Safety

**Rating**: Good (Rust), with residual native risk

No memory-safety defect was identified in the reviewed Rust code. Risk concentrates in BoringSSL/quiche, ~210 `unsafe` blocks (FFI, `fork`, `ioctl`, `sendmsg`/`recvmsg`) and the custom seccomp program; Finding 9 is a resource leak rather than memory corruption.

#### Cryptographic Implementation

**Rating**: Adequate

Ed25519 via BoringSSL, CSPRNG nonces, and constant-time comparisons are used correctly. The open items are the nonce-ownership and signing-oracle issues (Findings 2 and 3) and missing channel binding (Finding 14).

#### Privilege Separation and Sandboxing

**Rating**: Needs Improvement

The design is sound on paper; the implementation leaves the most exposed component unconfined and the monitor permissive (Findings 1 and 4).

## Dependency Analysis

Pinned: quiche 0.30.0, boring/boring-sys 4.22.0 (BoringSSL commit `44b3df6f` per the docs), io-uring 0.7.15, yaml_serde 0.10.7, clap 4.6.7, libc 0.2.191, zeroize 1.9.1; 96 packages in `Cargo.lock`. **Advisory databases were not queried in this review** (no toolchain available), so absence of known CVEs is not asserted. ## Compliance Assessment

### Threat-Model Conformance (SPEC.md)

- Host key not readable by workers: **Partially met** (separate monitor process, but root workers and a signing oracle weaken this)
- Worker cannot choose the authenticated principal: **Not met** against a compromised worker (Finding 2)
- Worker cannot spawn arbitrary processes or access the filesystem: **Not met** (Finding 1)
- Bounded parser input and fail-closed limits: **Met**, with the limiter caveat in Finding 5

### CWE Mapping

CWE-250 (execution with unnecessary privileges) for Finding 1; CWE-294 (capture-replay) for Finding 2; CWE-347/CWE-345 for Finding 3; CWE-653 (insufficient compartmentalization) for Finding 4; CWE-770 (allocation without limits) for Findings 5 and 8; CWE-775 (missing release of file descriptor) for Finding 9; CWE-1357 (reliance on insufficiently trustworthy component) for Finding 7.

## Recommendations

### Immediate Actions (High Priority)

1. Move the QUIC/TLS workers into unprivileged, sandboxed processes with seccomp and Landlock applied to every thread, and add a test that enforces it (Finding 1)
2. Have the monitor own and single-use-track server nonces (Finding 2)
3. Restrict monitor signing to valid TLS 1.3 `CertificateVerify` inputs (Finding 3)
4. Do not expose `ssxd` on the public internet until items 1-3 are complete and an independent review is done

### Medium-term Improvements

1. Add Landlock and flag-filtered `openat*` to the monitor sandbox (Finding 4)
2. Rework the limiter to prefix-based keys with eviction and a global budget (Findings 5, 8)
3. Add PAM or equivalent account checks, audit login uid, rlimits, cgroup teardown and PTY ownership (Finding 6)
4. Add CI for audit, deny, Clippy, tests and fuzzing; track quiche/BoringSSL advisories (Finding 7)
5. Fix the fd leak, monotonic clock use, client missing-certificate path, TERM allowlist and log escaping (Findings 9-13)
6. Reconcile `SPEC.md` with the implementation (Finding 12)

### Operational Security

1. Run with the permission-override flag only in throwaway development environments
2. Keep `server_authorized_keys` empty unless a skeleton-key model is intended
3. Keep the host key root-owned `0600` on a protected path; monitor for repeated authentication failures
4. Keep the kernel and glibc/musl packages patched, and decide deliberately whether to allow io_uring on the host

## Conclusion

ssxpro 0.1.0 has a thoughtful design and many well-executed low-level details, and the author's own SPEC is candid about unfinished milestones. The gap that matters most is between the documented privilege-separation model and the shipped code: today the code handling untrusted network input holds root with no confinement, and the monitor would not stop a compromised worker from replaying logins or using the host key as a signing oracle. These are fixable architecture-level items rather than isolated bugs. No remotely exploitable memory-safety defect was found in the reviewed Rust code, but the unreviewed native dependencies and the unconfined worker make the practical risk of public exposure high.

**Risk Level**: Medium–High **Recommended Actions**: Address Findings 1-3 before any public deployment; schedule Findings 4-7 for the next milestone; run dependency and fuzz tooling in CI.
