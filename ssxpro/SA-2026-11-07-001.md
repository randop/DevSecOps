## Executive Summary

This report presents an independent static security review of ssxpro 0.1.0, a Linux-only QUIC + io_uring remote-shell system (ALPN `ssxpro/1`) that provides public-key authenticated interactive login to a single PTY-backed login shell. It is deliberately not SSH. The review covers the full workspace (`crates/ssxpro-{server,client,proto,config,crypto,io}`), `SPEC.md`, example configurations, `Cargo.toml` / `Cargo.lock`, and related hardening code.

**Overall Assessment**: The design is unusually careful for an M0 baseline. Authentication binds the signature to both nonces and the server SPKI hash. File loading uses `openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`, exact mode 0600 ownership checks, and size limits. The privileged session broker is forked before worker threads, receives only authenticated one-time session tokens (HMAC-SHA256, 30 s lifetime, nonce replay table), and never trusts descriptors from workers. Root login is denied by default, login shells are validated against `/etc/shells`, and process-group teardown is aggressive. The weaknesses are those expected at this maturity: the threat model still trusts the root monitor and kernel; Landlock/seccomp are planned for later milestones; some configuration defaults and the explicit permission-bypass flag create operational foot-guns; and several resource/availability limits remain coarse. No unauthenticated remote code execution or authentication bypass was identified in the reviewed code.

**Risk Level**: Low–Medium (Low for a correctly deployed production configuration that keeps the host key and authorized_keys files private and does not use the permission-bypass flag).

## Methodology

- Manual line-by-line review of `crates/ssxpro-crypto/src/lib.rs`, `crates/ssxpro-config/src/lib.rs`, `crates/ssxpro-server/src/{main,broker,session,ipc,tls,transport}.rs`, `crates/ssxpro-client/src/{main,terminal,transport}.rs`, `crates/ssxpro-proto/src/lib.rs`, `crates/ssxpro-io/src/lib.rs`, `SPEC.md`, `config/ssxd.example.yaml`, `config/ssx.example.yaml`, workspace `Cargo.toml` / `Cargo.lock`, and supporting documentation.
- Independent derivation of findings from source rather than reuse of any prior conclusions.
- Trace of all network-attacker-controlled data paths: QUIC handshake + ALPN, control-stream framing, authentication challenge/response, session-token minting/verification, broker IPC (SOCK_SEQPACKET + SCM_RIGHTS), PTY spawn + privilege drop, and openat2-based file loading.
- Review of constant-time comparison usage, nonce freshness, token lifetime / replay protection, and process-group cleanup.
- Dependency review of pinned crates (boring 4.22.0, io-uring 0.7.15, etc.) against publicly known issues as of the audit date; no critical RustSec entries were matched for the locked versions in this pass.
- Evaluation against the project’s own threat model in `SPEC.md`, OWASP-relevant categories for remote access services, and standard Linux privilege-separation expectations.

This was a static review. The crate was not executed and `cargo test` / fuzz targets were not run. Findings below are from source inspection and the control-flow simulations implied by the reviewed code.

## Findings

### High Priority Issues

None identified. No authentication bypass, signature forgery under the documented binding, or unauthenticated code-execution path was found in the reviewed sources.

### Medium Priority Issues

#### 1. Explicit Permission-Bypass Flag Disables All Strict File Checks

**Severity**: Medium  
**Status**: Confirmed — intentional but operationally dangerous

**Description**: The long flag `--yes-I-know-permission-risks-go-ahead-please` (and the corresponding `skip_permission_checks` path) disables owner/mode checks on the host key, server-wide authorized_keys, configuration file, and per-user `.ssx/` files. The same path is also used by the “unprivileged development mode” that runs the broker as the target account. When the flag is present, `read_user_file_as_allow_insecure` / `read_server_file_allow_insecure` and the corresponding `check_secure_metadata` skips are taken.

**Risk**: An operator who pastes the flag into a production unit file or container entrypoint can load world-readable host keys or authorized_keys, turning a misconfigured filesystem into a complete authentication compromise. The flag name is deliberately long and awkward, which mitigates accidental use, but the existence of a single switch that disables the entire strict-loading surface remains a configuration hazard.

**Recommendation**:
- Keep the flag, but log a prominent warning (and refuse to start if the configured log level is below a threshold) whenever it is active.
- Consider splitting “skip ownership checks” from “allow unprivileged broker” so the two risks are not coupled.
- Document in the strongest terms that the flag must never appear in production systemd units or container images.

#### 2. Server-Wide Authorized Keys Grant Access to Any Local Account

**Severity**: Medium  
**Status**: Confirmed by design and documented in the example config

**Description**: `auth.server_authorized_keys` (default `/etc/ssx/authorized_keys`) is checked before the per-user file. A key listed there authorizes that key for any local account (subject only to `allow_root` and the shell policy). The example config correctly warns that the file must be root-owned mode 0600.

**Risk**: A single compromised or overly broad server-wide key file becomes a universal login credential. This is useful for emergency access or shared service accounts, but it expands the blast radius of any key that is added to the file.

**Recommendation**:
- Treat the server-wide file as a high-privilege primitive; consider requiring an explicit `allow_any_user` or similar opt-in per key, or limiting it to a configured set of principals.
- Ensure the monitor never falls back to a less-restrictive path if the file is missing or unreadable.

#### 3. Session Token Lifetime and Clock Skew Are Fixed and Relatively Generous

**Severity**: Medium  
**Status**: Confirmed

**Description**: Session tokens minted for the broker use a 30-second lifetime and a 5-second clock-skew allowance. The broker maintains a used-nonce table (capped at 8192 entries) to prevent replay. Tokens embed the full identity (name, uid, gid, home, shell, supplementary groups).

**Risk**: On a heavily loaded or time-skewed system an attacker who obtains a valid token (e.g., via a compromised worker or side channel) has a 30-second window. The fixed constants are not configurable, so an operator cannot tighten them for high-security environments.

**Recommendation**:
- Make lifetime and skew configurable (with tight defaults).
- Consider binding the token to the worker index or a one-time connection identifier so a stolen token cannot be used from a different worker.

#### 4. Coarse Resource Limits and Absence of Per-Source Auth Rate Limiting in M0

**Severity**: Medium  
**Status**: Confirmed — planned for later milestones (M8)

**Description**: Global limits exist (`quic.max_connections`, `session.max_sessions`, control-frame size, hello/auth timeouts), and QUIC Retry is enabled by default. Per-source connection and authentication rate limiting, as well as finer-grained memory budgets for QUIC receive windows, are explicitly deferred.

**Risk**: An unauthenticated flood of Initial packets or Hello/AuthRequest messages can still consume CPU (HMAC verification, nonce generation) and connection-table slots. Availability impact only; no confidentiality or authentication break was identified.

**Recommendation**:
- Implement the planned per-source limits before any public exposure.
- Document the memory product of concurrent connections × advertised QUIC windows so operators can size hosts accordingly.

### Low Priority Issues

#### 5. Known-Hosts Policy Defaults to “ask” on the Client

**Severity**: Low  
**Status**: Confirmed

**Description**: The client’s default known-hosts policy is “ask”. This is appropriate for interactive use but means the first connection to a new host relies on the operator correctly verifying the SPKI fingerprint.

**Risk**: Classic TOFU risk on first connect. Subsequent connections correctly refuse on mismatch.

**Recommendation**: Document the fingerprint verification step clearly; consider a “strict” default for non-interactive / scripted clients.

#### 6. Shell Path Validation Relies on `/etc/shells` and Absolute Paths

**Severity**: Low  
**Status**: Confirmed

**Description**: Login shells must be absolute, appear in `/etc/shells`, not end in `/nologin` or `/false`, and be executable regular files. This is sound.

**Observation**: The check is performed after NSS lookup; a compromised NSS module could still influence the result. This is within the stated threat model (kernel / trusted system databases).

#### 7. Process-Group Teardown Is Aggressive but Relies on Correct setsid

**Severity**: Low  
**Status**: Confirmed by inspection

**Description**: The broker and `SpawnedSession` Drop implementation send SIGHUP then SIGKILL to the process group and use pidfd + waitid. Background descendants that escape the group could in theory linger, but the design makes this difficult.

**Observation**: Continue to treat any failure to install the process group as a hard error.

#### 8. Dependency Surface (BoringSSL via boring, io-uring)

**Severity**: Informational  
**Status**: Pinned versions reviewed; no critical advisories matched in this pass

**Description**: The project correctly pins `boring = "=4.22.0"` and `io-uring = "=0.7.15"` and documents the need to update the BoringSSL commit together with quiche. The crypto crate uses BoringSSL for Ed25519 and HMAC and zeroizes sensitive material.

**Recommendation**: Continue the existing practice of simultaneous quiche / BoringSSL updates and cargo-audit runs before any release.

## Positive Security Observations

- Authentication binding includes server SPKI hash + dual nonces; signature verification is constant-time where appropriate.
- File loading is performed with `openat2` + strict resolve flags and exact 0600 / ownership checks (when the bypass flag is absent).
- Privilege separation is real: the session broker is forked early, workers never receive host keys, and the broker only acts on MAC-authenticated, single-use tokens.
- Root login is disabled by default; shell policy is enforced.
- Control framing is strictly bounded (4096-byte payloads, exact lengths, rejection of unknown types / trailing data).
- 0-RTT and session resumption are disabled in v1.
- Aggressive process-group cleanup and pidfd-based exit observation reduce the window for orphaned shells.
- The SPEC.md threat model is unusually clear about what is and is not claimed.

## Residual Risk Summary

- A correctly configured deployment (private host key + authorized_keys, no permission-bypass flag, production kernel ≥ 6.12 with the required io_uring features) presents **Low** residual risk for the reviewed attack surface.
- Misconfiguration (world-readable keys, use of the bypass flag, or exposure before per-source rate limits land) elevates the risk to **Medium**.
- Kernel compromise, root compromise of the monitor, or a malicious authorized user remain out of scope, as stated in the project threat model.

**Overall residual risk** is assessed as **Low–Medium** (Threat Level Score **3.8 / 10**). It drops to **Low** for a deployment that keeps key material private, disables the permission-bypass flag, and applies the planned M8 rate-limiting before public exposure.
