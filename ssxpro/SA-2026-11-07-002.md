## Executive Summary

This report presents a security review of `ssxpro` 0.1.0, a Linux-only remote-shell service using QUIC, BoringSSL, Ed25519 public-key authentication, `io_uring`, and PTY-backed login sessions. The project is designed around a privileged TLS monitor, a session broker, and constrained network workers.

Overall Assessment: The implementation contains several deliberate security controls, including bounded protocol frames, authenticated session tokens, strict file-permission checks, QUIC Retry, login-account privilege dropping, and a separate TLS monitor and session broker. However, the current network-worker isolation does not meet the project's own stated threat model.

The most serious issue is that network workers are threads within the main server process. The worker hardening routine applies `no_new_privs` and disables dumpability, but does not drop credentials or install the full filesystem and syscall sandbox. The stricter Landlock/seccomp policy is applied to the PTY-pump thread instead. The main server process is required to access a root-owned, mode-`0600` host private key under the normal permission-checking path. Consequently, a compromise of the network-facing process can reach a privilege domain that the specification says must remain inaccessible to a compromised worker.&#x20;

## Methodology

- Reviewed the workspace manifest, `Cargo.lock`, `deny.toml`, `CHANGELOG.md`, `SPEC.md`, and the repository's published top-level structure.
- Traced the server startup path, configuration and host-key permission checks, QUIC worker creation, worker hardening, TLS monitor, session broker, authentication checks, and PTY/login-shell lifecycle.
- Reviewed protocol framing and state-machine requirements, authentication signature construction, client host-key pinning, and the principal server configuration defaults.

## Findings

### High Priority Issues

#### 1. Network Workers Share the Main Server's Privilege Domain

Severity: High

Status: Confirmed by source inspection — the worker architecture does not enforce the isolation required by the project's threat model.

Description:

The project specification states that a compromised worker must not be able to read the host private key, choose an authenticated principal, spawn arbitrary host processes, or access the filesystem and network outside its assigned resources. It further describes workers as unprivileged and assigns host-key ownership to the monitor.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

raw\.githubusercontent.com



The current implementation does not establish that boundary for the network workers:

1. The normal server startup path checks that the configuration and host key are regular files owned by UID `0`, with mode `0600`. The permission-bypass option is separate and is not the normal strict-permission path.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

   raw\.githubusercontent.com+1

2. `transport::serve()` starts the TLS monitor and session broker, then creates the QUIC workers using `std::thread::scope()` and `scope.spawn()`. These are threads in the server process, not independently credential-restricted worker processes.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

   raw\.githubusercontent.com+1

3. Each network worker invokes `harden_worker_process()`. That function calls `sandbox_common()`, which sets `PR_SET_NO_NEW_PRIVS` and `PR_SET_DUMPABLE` only. It does not drop UID/GID, remove capabilities, install a network-worker seccomp allowlist, or impose a Landlock filesystem policy.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

   raw\.githubusercontent.com

4. The stricter `sandbox_worker()` function installs a deny-all Landlock ruleset and a seccomp syscall allowlist, but the transport code invokes it on the dedicated `ssxd-pty-pump` thread after that thread opens and registers its PTY descriptor. It is not the hardening function used by the QUIC network workers.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

   raw\.githubusercontent.com+1

5. The session broker's login-shell path does explicitly drop supplementary groups, GID, and UID to the target account. This is a useful control for the spawned shell, but it does not reduce the privileges of the network-worker threads in the parent server process.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

   raw\.githubusercontent.com



`PR_SET_NO_NEW_PRIVS` prevents gaining new privileges through mechanisms such as set-user-ID execution; it does not remove privileges the process already has. Disabling dumpability is also not a substitute for restricting filesystem access or reducing process credentials.

Because the main process must read the root-owned host key under the standard permission-checking path and the network workers share that process, the intended “compromised worker cannot read the host key” property is not enforced by the current boundary. A memory-safety or control-flow compromise in the network-facing process could therefore have access to the same process credentials and filesystem permissions that permit access to that key.

Risk:

A compromise in a network-facing code path could have a substantially larger impact than intended by the threat model. Depending on the daemon's runtime credentials and capabilities, an attacker could access root-protected files, interfere with privileged server operations, or undermine the separation between the QUIC workers and the TLS monitor/session broker.

This is a containment weakness, not evidence of a specific remotely exploitable memory-corruption flaw in `quiche`, BoringSSL, or the application.

Recommendation:

- Run network workers as separate OS processes rather than threads in the privileged parent process.
- Drop worker UID/GID and all unnecessary Linux capabilities before processing untrusted network packets.
- Apply an explicit seccomp allowlist and Landlock policy to the network-worker processes, allowing only the required pre-opened socket, IPC, and `io_uring` operations.
- Keep the host private key readable only by the TLS monitor. Do not leave a process that handles untrusted QUIC packets with filesystem permissions that can reopen the private-key file.
- Keep the privileged session broker isolated from network workers, and expose only the minimum authenticated IPC operations required to create and manage sessions.
- Add integration tests that verify worker EUID/EGID, capability sets, filesystem access to the host-key path, and syscall restrictions. Include a regression test demonstrating that a compromised or test-only network worker cannot read the host key or create an arbitrary process.
- Update `SPEC.md` to describe the actual process boundaries and make release readiness conditional on verifying those boundaries at runtime.

Source evidence for Finding 1: The startup path checks for a UID-0, mode-`0600` host key; the network workers are spawned as threads; and the worker-hardening implementation distinguishes the limited network-worker hardening from the full PTY-pump sandbox.&#x20;

### Low Priority Issues

#### 2. Server-Wide Authorized Keys Are Not Bound to a Specific Login Account

Severity: Low

Status: Confirmed behavior — conditional access-control risk if operators expect keys in the global file to be restricted to individual usernames.

Description:

The server configuration defines a global `server_authorized_keys` file, defaulting to `/etc/ssx/authorized_keys`. The configuration describes this file as being checked before the per-user `~/.ssx/authorized_keys` file.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

raw\.githubusercontent.com+1



In `verify_login_request()`, the requested username is first resolved to a local login identity. The server then checks whether the presented public key appears anywhere in the global key list. If it matches, the per-user key file is not checked. The global key entry is not associated with the requested username.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

raw\.githubusercontent.com



As a result, a public key placed in the server-wide file can authenticate as any eligible local account, rather than only one particular account. Root access remains separately disabled by default, but other accounts with permitted login shells may be selected.

This may be intentional for centrally managed, host-wide access. It becomes an access-control mistake if an administrator places a user's key in the global file while expecting the key to authorize only that user's account.

Risk:

A key intended for one account could grant access to other non-root accounts on the same host. The impact depends on how administrators populate the global key file and whether they understand its host-wide scope.

Recommendation:

- Document explicitly that every key in `server_authorized_keys` can authenticate as every eligible local account.
- Consider replacing the global key list with a username-to-key mapping if per-account authorization is required.
- Alternatively, provide an explicit configuration option for host-wide keys, disabled by default.
- Add tests demonstrating the intended behavior when one global key is presented with different usernames.

## Compliance Assessment

The following is a high-level control assessment. OWASP categories are used as a comparison framework; ssxpro is a remote-shell service rather than a web application, so not every web-specific control applies directly.

### Authentication and Access Control

- Positive: Ed25519 public-key authentication, server/client nonces, server SPKI binding, and a separate monitor for authentication decisions.
- Positive: Root login is denied by default; login shells are started with the target user's groups and UID/GID.
- Concern: A key in the global authorized-key file is valid for any eligible local login account, not a particular username.
- Concern: The network workers share the server process privilege domain despite the documented compromised-worker threat model.

### Cryptographic Protection and Sensitive Data

- Positive: TLS 1.3 is used over QUIC, and host identity is pinned using the server SPKI.
- Positive: The authentication signature includes fresh nonces and the username.
- Concern: The host-key protection boundary depends on separating the monitor from network workers, but the worker process boundary is insufficient.
- Design note: The protocol currently uses nonce-plus-SPKI authentication binding instead of TLS exporter material; the specification records this limitation and the condition for changing it.

### Input Validation and Protocol Security

- Positive: Control frames are length-limited and decoded with exact-length validation.
- Positive: The protocol state machine restricts the message sequence and allowed streams.
- Positive: Invalid, unsupported, and out-of-order messages are rejected. The specification disallows 0-RTT.
- Concern: The parser and transport paths should be exercised under fuzzing and adversarial network tests before production exposure.

### Availability and Resource Controls

- Positive: QUIC Retry is enabled by default. Connection and session counts have configurable bounds.&#x20;

  [image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

  raw\.githubusercontent.com

- Positive: Initial traffic is rate-limited per source, with a maximum of 20 admissions per IP in a 10-second window. Authentication failures are capped at five per source over 60 seconds. Both maps have bounded entry counts.&#x20;

- Concern: The specification lists cgroup v2 session placement as a later-stage feature. Per-session CPU, memory, and process-count enforcement should be in place before the service is used to host mutually untrusted accounts.&#x20;

### Security Configuration and Supply Chain

- Positive: Configuration parsing rejects unknown fields and validates important values before startup.
- Positive: The server checks host-key ownership and file mode under its normal strict-permission path.
- Positive: `deny.toml` contains an advisory policy with no ignored entries.
- Concern: The global authorized-key scope and unused `auth.max_attempts` setting could mislead operators if not documented clearly.
- Concern: Dependency checks and release CI were not executed as part of this review.

## Recommendations

### Immediate Actions — High Priority

1. Implement actual network-worker isolation. Move QUIC workers into separate processes, drop their UID/GID and capabilities, and install a worker-specific seccomp and Landlock policy. Ensure the network-facing workers cannot reopen the host private key.
2. Verify the isolation at runtime. Add tests that inspect worker credentials and capabilities and confirm that host-key file access and arbitrary process creation are denied.
3. Review IPC capability boundaries. Confirm that each worker receives only the minimum monitor and session-broker operations required to service authenticated connections.

### Medium-Term Improvements

1. Clarify the scope of `server_authorized_keys` and add username-to-key mapping if account-specific authorization is required.
2. Remove the unused `auth.max_attempts` setting or implement the documented behavior consistently with the protocol's one-attempt-per-connection rule.
3. Add `cargo audit`, `cargo deny check`, formatting, tests, and fuzz-target execution to CI.
4. Add integration tests for QUIC handshake limits, invalid protocol-state transitions, authentication failure throttling, broker IPC, PTY teardown, and process isolation.
5. Add cgroup v2 or equivalent deployment-level per-session resource controls for mutually untrusted accounts.
6. Revalidate the custom nonce-plus-SPKI authentication binding and retain the specification's requirement for a tested TLS-exporter migration before changing the scheme.

### Operational Security

1. Keep the server configuration and host private key owned by root, with mode `0600`, and ensure the host-key directory is not writable by untrusted users.
2. Do not use the permission-check bypass option in production.
3. Disable root login unless there is a documented operational requirement and a separate risk review.
4. Use per-user authorized-key files when account-specific key scope is intended.
5. Keep the Linux kernel patched and use a supported kernel with the required `io_uring`, seccomp, and Landlock features.
6. Monitor authentication failures, worker crashes, broker failures, and unexpected process exits.
7. Do not expose the service to untrusted networks until the network-worker isolation issue has been addressed and verified.

## Conclusion

`ssxpro` 0.1.0 demonstrates deliberate security engineering in its protocol framing, authentication design, session handling, and use of Linux confinement mechanisms. The separate TLS monitor and session broker, fixed protocol limits, strict file checks, and target-account privilege dropping are valuable foundations.

However, the network-worker implementation does not meet the worker-compromise boundary described in `SPEC.md`. Because packet-processing workers are threads in the main server process and do not receive the full sandbox or a credential drop, the design does not adequately contain a compromise of network-facing code. The presence of a separately sandboxed PTY-pump thread does not resolve this problem.

The service should not be considered ready for exposure to untrusted networks until Finding 1 is fixed and its replacement process boundary is verified by integration tests. Finding 2 is a lower-priority authorization-scope concern that should be documented or changed to match the intended account model.

Risk Level: High

Recommended Actions: Address Finding 1 before production deployment. Clarify and test global authorized-key behavior, complete dependency checks in CI, and verify process/resource isolation before accepting untrusted users.
