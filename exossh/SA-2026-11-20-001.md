## Executive Summary

This report presents a security audit of exossh v1.3.0, a minimalist C/libuv SSH honeypot that listens on TCP port 2222, emits periodic pseudo-random lines, records client addresses, and optionally interprets PROXY protocol v1/v2 data. The audit covered all tracked source, build scripts, and documentation, with particular attention to asynchronous object lifetimes, disconnect handling, resource controls, PROXY protocol trust and parsing, logging, build hardening, and dependency management.

The small codebase has some useful defensive properties: fixed-size read storage, bounded PROXY v1 string conversions, length-checked PROXY v2 address reads, and no shell command execution, file parsing, credential handling, or dynamic request routing. However, local validation confirmed a stack-use-after-return in asynchronous output and a duplicate-close process abort. The service also permits unlimited indefinitely idle connections, exposing it to straightforward resource exhaustion. PROXY protocol handling currently allows untrusted clients to alter logged attribution and accepts malformed v1 fields.

**Overall Assessment**: The current daemon should not be exposed to untrusted networks without first correcting the connection lifecycle and resource-exhaustion issues. No critical vulnerability, credible remote-code-execution path, credential disclosure, or SSH authentication bypass was identified. The dominant risks are process-wide denial of service, a bounded potential stack-information disclosure, and loss of honeypot log integrity.

**Risk Level**: High

## Methodology

- Manual review of all eight tracked files, including `src/main.c`, build/debug scripts, and project documentation.
- Data-flow and lifecycle analysis of TCP accept, read, write, timer, cancellation, close, and free paths.
- Review against [libuv stream semantics](https://docs.libuv.org/en/v1.x/stream.html), [libuv handle semantics](https://docs.libuv.org/en/v1.x/handle.html), and the [HAProxy PROXY protocol specification](https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt).
- GCC 16.2 static analyzer, Clang 23 static analyzer, and clang-tidy checks; manual triage removed generic and non-security warnings.
- Local loopback-only harnesses invoking the unchanged production parsers and callbacks under AddressSanitizer and UndefinedBehaviorSanitizer.
- Targeted disconnect, write-backpressure, and parser tests; no testing against external systems.
- Dependency/configuration review and limited OSV queries for libuv 1.52.0 and 1.53.0. Absence of a query result is not treated as proof that no vulnerability exists.

### Key Validation Evidence

- A queued three-byte write caused AddressSanitizer to report `stack-use-after-return` in libuv, pointing to `line` at `src/main.c:261`.
- EOF during a queued write caused `on_write()` to receive `UV_ECANCELED`, followed by libuv's assertion `!uv__is_closing(handle)` and process exit 134.
- An isolated post-FIN write test, with reads disabled to exercise the timer/write path, terminated with `SIGPIPE` (exit 141). A full-daemon disconnect/write race was not reproduced; this limitation affects the severity assigned below.
- Parser tests confirmed acceptance of a non-IP source, out-of-range ports, LF-only termination, trailing fields, raw terminal escape bytes, and UDP-over-IPv4 v2 framing on this TCP service.
- A fragmented v1 header caused `proxy_done` to be set before the header was parsed. Parser smoke testing across input lengths 0–2048 found no out-of-bounds parser access under ASan/UBSan.

## Findings

### High Priority Issues

#### 1. Unbounded Idle Connections Enable Remote Resource Exhaustion
**Severity**: High  
**Status**: Requires Immediate Attention  
**CWE**: CWE-770 — Allocation of Resources Without Limits or Throttling

**Description**: Every accepted connection allocates a `client_t`, a file descriptor, TCP and timer handles, a write request, and a 1 KiB read buffer (`src/main.c:64-73`, `282-324`). There is no global or per-IP active-connection ceiling, handshake deadline, idle timeout, absolute session lifetime, or write-progress deadline. `MAX_BACKLOG` at lines 41 and 341 limits only pending kernel connections, not established clients.

An unauthenticated party can open connections and send no data, retaining each allocation indefinitely. Enough connections can exhaust file descriptors or memory and deny service to all clients. The allocation-failure path compounds this problem: lines 282-286 return without accepting or closing libuv's pending connection. Under libuv 1.53, an unaccepted `accepted_fd` causes accept polling to stop, potentially leaving the listener stalled after memory pressure.

**Risk**: Reliable unauthenticated availability loss, directly undermining the project's stated denial-of-service protection goal.

**Recommendation**:
- Enforce a hard global active-client limit and per-transport-IP limits.
- Add short initial-header, idle, write-progress, and absolute-lifetime deadlines.
- Stop accepting or immediately accept-and-close excess clients using valid libuv lifecycle handling.
- Use a preallocated emergency client handle for allocation/setup failure paths.
- Add OS file-descriptor, memory, and process limits as defense in depth, not as substitutes for application limits.

#### 2. Pending-Write Cancellation Causes Duplicate Close and Process Abort
**Severity**: High  
**Status**: Reproduced; Requires Immediate Attention  
**CWE**: CWE-664 — Improper Control of a Resource Through Its Lifetime

**Description**: `on_read()`, malformed-PROXY handling, `on_write()`, and `on_timer()` independently close both the TCP handle and timer (`src/main.c:212-218`, `233-237`, `245-255`, `269-273`). No closing-state guard coordinates these paths.

Libuv cancels an outstanding write when its stream is closed. The resulting sequence is:

1. A banner write remains queued during backpressure.
2. `on_read()` receives EOF/an error or a malformed PROXY header and calls `uv_close()` on both handles.
3. Libuv invokes `on_write()` with `UV_ECANCELED`.
4. `on_write()` calls `uv_close()` again on handles that are already closing.

The local harness reproduced this exact sequence. Libuv aborted on `Assertion '!uv__is_closing(handle)' failed`, producing process-wide denial of service. A successful completion racing with teardown can also attempt to rearm a closing timer at lines 253-254.

**Risk**: An unauthenticated client able to combine disconnect/error handling with an outstanding write can terminate the entire daemon. Timing/backpressure is required, but the consequence affects every connection.

**Recommendation**:
- Route every shutdown path through one idempotent `close_client()` function guarded by a per-client `closing` flag and `uv_is_closing()`.
- Make `on_write()` return immediately when closing has begun; never rearm timers or submit writes after that point.
- Preserve `client_t` and write storage until all callbacks and both handle-close callbacks have completed.
- Add regression tests for EOF, RST, malformed input, and write cancellation under backpressure.

#### 3. Asynchronous Write Uses an Expired Stack Buffer
**Severity**: Medium–High  
**Status**: Reproduced; Requires Immediate Attention  
**CWE**: CWE-416 — Use After Free / Expired Lifetime

**Description**: `on_timer()` creates `char line[256]` on its stack and passes it to `uv_write()` through a `uv_buf_t` (`src/main.c:258-268`). Libuv explicitly requires the memory referenced by write buffers to remain valid until the write callback executes. `line` ceases to exist when `on_timer()` returns, while partial or blocked output can remain queued.

With a deliberately backlogged loopback socket, AddressSanitizer confirmed a libuv read from the expired `line` frame after `on_timer()` returned. The local `uv_buf_t` descriptor itself is copied by libuv and is not the defect.

**Risk**: Undefined behavior and disclosure to the remote peer of up to 32 bytes per affected banner if subsequent stack activity replaces the intended contents. Banner integrity can also be lost. No memory write to the expired buffer or code-execution path was established, so the issue is not rated Critical.

**Recommendation**:
- Store the banner in `client_t`, for example `char write_buf[MAX_LINE_LENGTH]`, and keep it unchanged until `on_write()` completes.
- Alternatively, use a per-write allocation containing both request and data, freed on every success, error, and cancellation path.
- Retain the one-outstanding-write invariant and test partial writes with `detect_stack_use_after_return=1`.

### Medium Priority Issues

#### 4. Unsuppressed SIGPIPE Can Terminate the Process During Disconnect/Write Races
**Severity**: Medium  
**Status**: Isolated Path Reproduced; Full-Daemon Reachability Timing-Dependent  
**CWE**: CWE-755 — Improper Handling of Exceptional Conditions

**Description**: The program does not ignore or block `SIGPIPE` (`src/main.c:331-351`). On Linux, libuv 1.53 implements ordinary stream output with `write()`/`writev()` rather than `send(..., MSG_NOSIGNAL)`. A write to a sufficiently disconnected TCP peer can therefore terminate the process synchronously before `uv_write()` error handling runs.

An isolated harness using the unchanged `on_timer()` callback exited with signal 13 after a post-FIN write sequence. A preceding RST-only attempt returned `ECONNRESET` instead, and a full-daemon exploit was not reproduced. Active reads normally close a disconnected client promptly, but timer and socket-event ordering leaves a plausible race that should be removed rather than relied upon.

**Risk**: Potential unauthenticated process-wide denial of service during peer disconnects, with exploitability dependent on TCP and event-loop timing.

**Recommendation**:
- Set `SIGPIPE` to `SIG_IGN` using `sigaction()` during initialization, before accepting connections.
- Continue handling `UV_EPIPE`, `UV_ECONNRESET`, and cancellation through the idempotent teardown path recommended in Finding 2.
- Regression-test FIN and RST immediately before, during, and after banner writes.

#### 5. Any Client Can Spoof PROXY Source Attribution
**Severity**: Medium  
**Status**: Reproduced; Requires Code and Deployment Controls  
**CWE**: CWE-345 — Insufficient Verification of Data Authenticity

**Description**: Every connection is eligible for automatic PROXY v1/v2 detection (`src/main.c:75-189`, `225-240`). There is no configuration switch, trusted-proxy allowlist, or dedicated listener. A direct client can submit a valid header and replace the address obtained from `uv_tcp_getpeername()` at lines 299-310.

A loopback test supplying a direct v2 header changed the logged address to `203.0.113.11`. The transport peer is printed once before parsing at line 313, which preserves some forensic evidence, but a second `connected` line and the `disconnected` line use the supplied address. Current use is logging-only; no access-control decision was found.

**Risk**: False attribution, corrupted honeypot telemetry, and misleading incident analysis. Future IP-based throttling built on this field would also be bypassable unless the trust model is fixed first.

**Recommendation**:
- Disable PROXY parsing by default and enable it only on a dedicated listener behind trusted proxies.
- Enforce a transport-peer allowlist before accepting PROXY data; do not auto-detect it on public listeners.
- Store and log transport and proxied addresses separately with explicit labels.
- Never use the proxied address for access control or throttling without this verification.

#### 6. PROXY v1 Validation Permits Malformed Data and Log/Terminal Injection
**Severity**: Medium  
**Status**: Reproduced  
**CWE**: CWE-20 — Improper Input Validation; CWE-117 — Improper Output Neutralization for Logs

**Description**: The v1 parser copies `src` directly to `ip_address` without validating it as an address (`src/main.c:98-117`). It also fails to validate port ranges, require CRLF, consume the complete line, or ensure the source and destination match the declared family. The low transport-protocol nibble in v2 is similarly ignored, allowing UDP framing on this TCP service.

Tests confirmed acceptance of `not-an-ip`, ports `-1` and `70000`, LF-only termination, trailing junk, and a source containing an unescaped terminal escape byte. The bounded `%7s`/`%45s` conversions prevent a direct destination overflow, and v2 address conversion through `inet_ntop()` is safe; these strengths do not address semantic validation or log neutrality. Extremely large decimal port conversions also need range-checked parsing rather than `%d`.

**Risk**: Forged or ambiguous security logs, terminal-control effects when logs are viewed, and acceptance of protocol-invalid attribution. Newline-based log forging was not demonstrated because whitespace terminates the scanned source token.

**Recommendation**:
- Parse v1 with strict token counts and full-line consumption; require CRLF and canonical syntax.
- Validate source and destination with `inet_pton()` according to `TCP4`/`TCP6`.
- Parse ports with checked `strtoul()` conversions and enforce `0..65535`.
- For v2, accept only supported TCP/UNSPEC combinations appropriate to the listener.
- Escape all non-printable log characters and retain the transport peer for `UNKNOWN`/`LOCAL` records.

### Low Priority Issues

#### 7. Fragmented PROXY Headers Bypass Parsing
**Severity**: Low  
**Status**: Reproduced  
**Description**: Parser return value `0` means both “need more data” and “not a PROXY header.” After any such result, `on_read()` sets `proxy_done = 1` (`src/main.c:225-240`). A valid header split across TCP reads is therefore never parsed, and declared v2 payloads larger than the first read have the same problem.

**Risk**: Legitimate proxied clients can lose source attribution, and fragmented headers produce inconsistent security telemetry. The original transport address remains available in the initial log, limiting impact.

**Recommendation**: Use distinct `NEED_MORE`, `VALID`, `INVALID`, and `NOT_PROXY` states; accumulate bounded per-client header bytes across reads; enforce a header deadline and supported maximum; and consume only the parsed header length.

#### 8. Release Build Hardening Is Not Explicit or Reproducible
**Severity**: Low  
**Status**: Requires Improvement  
**Description**: `scripts/compile.sh:7` builds with `-g -O0` and does not explicitly select release hardening, optimization, or fortified libc checks. The audited local build inherited PIE, stack-protector support, NX, and partial RELRO from toolchain defaults, but did not bind relocations immediately. These inherited properties may differ on another supported system.

**Recommendation**: Provide separate debug and release builds. For release, use optimization and explicit supported flags such as `-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2` (or 3 where supported), PIE, and `-Wl,-z,relro,-z,now`. Keep ASan/UBSan and analyzer jobs in CI rather than enabling sanitizers in production.

#### 9. Dependency Provenance and Security Update Policy Are Undocumented
**Severity**: Low  
**Status**: Operational  
**Description**: The only third-party runtime dependency identified is libuv, declared as `>= 1.52.0` in `README.md:11` and resolved dynamically through `pkg-config` in `scripts/compile.sh:7`. There is no dependency lock/SBOM, recorded build-time version, security-update policy, or automated advisory check.

**Risk**: Builds and deployments can silently use different libuv security patch levels. No specific currently exploitable libuv CVE is asserted by this audit.

**Recommendation**: Record libuv version and provenance in release artifacts, generate an SBOM, monitor distribution and upstream advisories, and deploy supported patched packages. Avoid pinning to an old exact version without an update process.

#### 10. Deterministic, Non-SSH Output Makes the Honeypot Easy to Fingerprint
**Severity**: Low  
**Status**: Security-Effectiveness Weakness  
**Description**: `client_t` is zero-initialized, so every client's linear-congruential generator starts from the same state (`src/main.c:46-62`, `288`). Output is sent at a fixed ten-second interval and deliberately avoids an `SSH-` prefix. This is not a cryptographic-key issue because no secrets use the PRNG, but the deterministic sequence, timing, and non-SSH syntax provide a straightforward honeypot signature.

**Risk**: Attackers and scanners can identify and avoid the honeypot, reducing monitoring value rather than directly compromising the host.

**Recommendation**: If realistic interaction is a project goal, emulate a constrained SSH identification/handshake and vary timing and responses safely. Do not use `rand16()` for security secrets; seed any non-security variation from `getrandom()` where unpredictability is desired.

### Informational Issue

#### 11. Short-Banner Comparison Can Inspect Uninitialized Storage
**Severity**: Informational  
**Status**: Static Analyzer Finding; No Exploit Demonstrated  
**Description**: `randline()` can produce a three-byte line but always calls `memcmp(line, "SSH-", 4)` (`src/main.c:51-60`). Clang's analyzer reported that the fourth byte can be uninitialized on the shortest path. The access remains inside the 256-byte array, and no disclosure or memory corruption was demonstrated.

**Recommendation**: Initialize the array or guard the comparison with `len >= 4`. This is robustness cleanup, not a driver of the overall risk rating.

## Code Quality Security Assessment

#### Input Validation
**Rating**: Needs Improvement  
- Fixed-size reads and bounded v1 string destinations reduce classic overflow risk.
- V2 signature, minimum address lengths, version/command, and source-address reads are checked.
- Semantic v1 validation, transport-protocol checks, streaming reassembly, and log neutralization are insufficient.

#### Memory and Lifecycle Safety
**Rating**: Weak  
- Heap clients are zero-initialized and normal close callbacks defer freeing until both handles close.
- The confirmed expired-stack write buffer and duplicate-close abort are material defects.
- No parser out-of-bounds access was found in targeted review and sanitizer smoke testing.

#### Resource Management
**Rating**: Weak  
- One outstanding write per client prevents routine request reuse and naturally limits per-client queued banner count.
- There are no active-client or lifetime limits, and setup/error returns need systematic handling.
- Backlog size and small socket receive buffers do not provide denial-of-service protection.

#### Cryptographic Implementation
**Rating**: Not Applicable  
- The project does not implement an SSH cryptographic handshake, authentication, TLS, certificates, or secret storage.
- The custom PRNG is not suitable for cryptographic use, but no such use was identified.

#### Logging and Monitoring
**Rating**: Needs Improvement  
- Transport addresses are logged before PROXY processing, which is a useful forensic safeguard.
- Duplicate/untyped address records, attacker-controlled v1 text, absent timestamps/ports, and no explicit transport-versus-proxy fields reduce reliability.

## Compliance Assessment

### OWASP Top 10 Coverage
The OWASP Top 10 is web-oriented and is used here only as supplemental categorization; CWE and protocol-specific requirements are more directly applicable.

- **A04: Insecure Design**: Missing resource ceilings and an unauthenticated PROXY trust model.
- **A05: Security Misconfiguration**: Public PROXY auto-detection and non-explicit release hardening.
- **A06: Vulnerable and Outdated Components**: Dependency inventory/update automation is absent; no specific vulnerable component was confirmed.
- **A09: Security Logging and Monitoring Failures**: Spoofable attribution and insufficient log neutralization.
- **Injection / cryptographic failures / SSRF / XXE / XSS**: No corresponding web, template, XML, command-execution, or cryptographic feature was found.

### SSH and Honeypot Security
- The service is a decoy, not a full SSH server; SSH authentication and cryptographic assessments are therefore not applicable.
- Periodic non-SSH lines and deterministic behavior reduce deception quality.
- Intentional untrusted exposure makes process isolation and availability controls especially important.

### PROXY Protocol Security
- The implementation does not follow the specification's requirement to configure PROXY reception explicitly and restrict it to trusted proxies.
- v1 canonical address, port, CRLF, and full-line validation are incomplete.
- TCP fragmentation must be handled deliberately rather than treated as completion of PROXY detection.

## Recommendations

### Immediate Actions (Before Untrusted Exposure)
1. Implement idempotent client teardown and eliminate duplicate `uv_close()` calls.
2. Move asynchronous banner data into storage that remains valid through completion/cancellation.
3. Add active-client/per-IP ceilings and initial, idle, write, and absolute timeouts.
4. Ignore `SIGPIPE` and exercise FIN/RST/write races in regression tests.
5. Run the corrected daemon under ASan/UBSan with forced write backpressure and cancellation tests.

### Medium-Term Improvements (Within 30 Days)
1. Restrict PROXY support to explicitly configured trusted listeners/peers and log transport/proxied addresses separately.
2. Replace v1 `sscanf()` parsing with strict, range-checked, full-line parsing and implement bounded streaming reassembly.
3. Neutralize control characters in logs and add timestamps, event types, and connection identifiers.
4. Add release/debug build profiles, automated analyzers, sanitizer tests, and dependency/SBOM reporting.
5. Handle allocation and every libuv initialization/start return through controlled overload or teardown paths.

### Operational Security
1. Run as a dedicated unprivileged user with a restrictive service sandbox and no unnecessary filesystem access.
2. Apply file-descriptor, memory, CPU, and connection limits at the service manager/container layer as defense in depth.
3. Firewall the PROXY-enabled listener so only approved proxies can reach it.
4. Protect logs from untrusted terminal rendering and monitor descriptor count, memory, queued bytes, and connection rates.
5. Keep the OS, libc, compiler runtime, and libuv security updates current.

## Conclusion

Exossh v1.3.0 has a compact and reviewable implementation, but its current network lifecycle is not resilient enough for its intended hostile environment. The unbounded connection model and reproduced duplicate-close abort create high availability risk. The confirmed expired-stack read, conditional `SIGPIPE` termination path, and spoofable/malformed PROXY handling add memory-safety and telemetry-integrity concerns.

The highest-value remediation is small and localized: centralize teardown, preserve write-buffer lifetime, suppress `SIGPIPE`, and enforce connection/time limits. PROXY trust and strict streaming validation should follow before the logged address is used for reputation, alerting, or throttling. With those changes and automated regression tests, the project's residual risk could be reduced substantially.

**Risk Level**: High  
**Recommended Actions**: Address Findings 1–3 before deployment to untrusted networks; address Findings 4–6 within the next remediation cycle.
