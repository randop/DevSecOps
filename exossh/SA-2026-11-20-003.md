# Security Audit Report: exossh (SSH Honeypot)

**Project:** [exossh](https://github.com/randop/exossh)  
**Version:** `1.3.0` (source version macros in `src/main.c`)  
**Audit Date:** 2026-11-20  
**Auditor:** OpenAI GPT-6  
**Audit Type:** Static source-code security review  
**Artifact Reviewed:** `exossh-1.3.0.zip`  
**Report ID:** `SA-2026-11-20-003`  
**Revision:** Completed source review; supersedes the preliminary report with the same ID  
**Overall Risk:** **HIGH**

## Executive Summary

The supplied `exossh-1.3.0.zip` archive enabled review of the complete application source and the included scripts. The application is a small C/libuv TCP listener that binds to the IPv6 wildcard address on port `2222`, accepts connections, optionally parses a PROXY protocol header, logs connection addresses, and periodically writes generated text to connected clients.

The review identified **one High**, **two Medium**, and **three Low** severity findings:

1. **High — Unbounded connection retention enables remote denial of service.** The server has no active-connection cap, per-source limit, read-rate control, or idle timeout. `MAX_BACKLOG` limits the listen queue, not the number of already accepted clients.
2. **Medium — Asynchronous write uses a stack-local buffer.** `on_timer()` passes a pointer to its local `line` array to `uv_write()`, although libuv requires the pointed-to bytes to remain valid until the write callback.
3. **Medium — PROXY headers are trusted from every peer.** An unauthenticated client can supply a false source address and overwrite the address used in connection and disconnect logs.
4. **Low — PROXY v1 source text is not sanitized before logging.** Control characters, including terminal escape sequences, can be carried through the unvalidated source token and printed to stdout.
5. **Low — Banner generation compares an uninitialized byte for the shortest generated line.** The generated line can be three bytes long, but `memcmp()` is always asked to compare four bytes.
6. **Low — libuv operation results are not consistently checked.** In particular, handle initialization and read/timer start results are ignored, weakening failure handling.

The source does **not** implement an SSH protocol handshake, authentication, shell, command execution, forwarding, or cryptographic negotiation. It reads client data but, after the optional first PROXY header, discards it. This limits the attack surface for command injection and SSH packet parser flaws, but it also means this program should be understood as a TCP decoy/banner sink rather than a protocol-compliant SSH server.

No direct shell execution, process spawning, file access, or persistence operation was found in the supplied source. This is a positive observation, not a guarantee against exploitation of memory-safety or resource-management defects.

**Deployment recommendation:** Do not expose this version directly to untrusted networks until the High and Medium findings are fixed. If it must be deployed before remediation, place it behind strict network controls, cap connections externally, and ensure the PROXY protocol is accepted only from trusted proxy addresses.

## Findings

### High Priority Issues

#### H-01. No Active-Connection Limit or Idle Timeout Enables Remote Resource Exhaustion

**Severity:** High  
**Status:** Confirmed by source review  
**CWE:** CWE-400 — Uncontrolled Resource Consumption  
**Affected locations:** `src/main.c:37–41`, `src/main.c:276–329`, `src/main.c:207–243`

**Description**

The listener accepts connections and allocates a `client_t` object for each accepted peer. Each object contains libuv TCP and timer handles, a write request, a fixed 1,024-byte read buffer, and connection metadata. There is no global maximum for active clients, no per-source connection limit, no connection-rate limit, and no idle-session deadline.

The only connection-related constant is `MAX_BACKLOG 64` (`src/main.c:41`). This is passed to `uv_listen()` as the listen backlog (`src/main.c:341`); it does not cap clients already accepted by the process.

After accepting a connection, the program starts reading and starts a banner timer (`src/main.c:322–324`). The read callback does not close an idle connection or enforce an input budget. After the optional PROXY header has been handled, incoming data is simply ignored (`src/main.c:225–243`). A client that keeps its TCP connection open can therefore retain its client object, handles, timer, file descriptor, and kernel socket resources indefinitely.

**Impact**

An unauthenticated remote actor can open many connections and keep them open, consuming file descriptors, memory, libuv handles/timers, and kernel socket resources. Sustained inbound traffic can also keep the event loop servicing read callbacks without a useful-work or rate limit. Resource exhaustion can prevent legitimate connections from being accepted or serviced.

This is directly inconsistent with the README's stated goal of minimizing resource use and protecting against denial-of-service traffic.

**Recommendation**

- Add a strict global active-client limit and reject or immediately close connections after the limit is reached.
- Add per-source limits and connection-rate controls. Account for IPv4-mapped IPv6 addresses consistently.
- Add a bounded idle timeout and, where appropriate, a maximum session lifetime.
- Enforce an inbound byte/rate budget, or stop reading once the small amount of input needed by the application has been consumed.
- Ensure every close path decrements active-client counters exactly once.
- Apply external safeguards as defense in depth: firewall/rate-limit rules, process file-descriptor limits, memory/cgroup limits, and monitoring.
- Document that the listen backlog is not an active-session limit.

### Medium Priority Issues

#### M-01. Stack-Local Banner Buffer Is Passed to an Asynchronous Write

**Severity:** Medium  
**Status:** Confirmed API-lifetime violation; runtime impact not measured  
**CWE:** CWE-825 — Expired Pointer Dereference  
**Affected locations:** `src/main.c:258–273`

**Description**

`on_timer()` creates `char line[256]` as an automatic local variable, generates the banner into it, and passes its address to `uv_write()`:

```c
char line[256];
int len = randline(line, MAX_LINE_LENGTH, &client->rng_state);

uv_buf_t buf = uv_buf_init(line, (unsigned int)len);
int r = uv_write(req, (uv_stream_t *)&client->handle, &buf, 1, on_write);
```

`on_timer()` returns while libuv may still have an outstanding write request that refers to `line`. The local array's lifetime ends when the callback returns. Libuv explicitly requires the memory pointed to by write buffers to remain valid until the write callback is called.

**Impact**

When a write is queued rather than completed immediately, libuv may access memory after the stack-local buffer has gone out of scope. Depending on timing and stack reuse, this can corrupt the banner bytes, send stale stack data, or cause a process fault. The exact remote exploitability depends on write-queue/backpressure conditions and was not dynamically tested. This should be treated as a real memory-lifetime defect, not merely a formatting issue.

**Recommendation**

- Keep the outgoing bytes in storage whose lifetime extends through `on_write()`, for example a buffer owned by a per-write request structure.
- Alternatively, add a suitably sized output buffer to `client_t`, ensuring that a new write cannot overwrite it before the previous write completes.
- Release per-write storage only from the write completion callback.
- Track outstanding request lifetime explicitly if client cleanup can occur while a write is pending.
- Avoid storing a function pointer in `uv_write_t.data` via conversion to/from `void *`; call `on_timer` directly from `on_write()` or use a properly typed state field.

#### M-02. PROXY Protocol Source Address Is Accepted from Untrusted Peers

**Severity:** Medium  
**Status:** Confirmed by source review  
**CWE:** CWE-345 — Insufficient Verification of Data Authenticity  
**Affected locations:** `src/main.c:75–117`, `src/main.c:120–179`, `src/main.c:207–240`

**Description**

The server attempts to parse PROXY protocol v2 and v1 data from the first positive read on every connection. There is no check that the TCP peer is a trusted load balancer or reverse proxy.

For PROXY v1, the parser accepts a source token using `%45s` and copies it directly into `client->ip_address` (`src/main.c:98–117`). It verifies that the protocol token is `TCP4` or `TCP6`, but does not validate the source token with `inet_pton()` or otherwise verify that it is an address of the declared family.

For PROXY v2, the source address is decoded from the supplied binary header and normalized with `inet_ntop()`, but the sender is still not authenticated. Any network client able to reach the listener can send a syntactically valid PROXY header and claim an arbitrary source address.

The resulting value replaces the address obtained from `uv_tcp_getpeername()` and is later used in connection and disconnect logs (`src/main.c:225–230`, `src/main.c:199–204`).

**Impact**

A direct client can forge the source identity recorded by the honeypot. This undermines incident attribution, source-based blocking, correlation, and any downstream analytics that treat the logged address as the actual network peer. Since the listener binds to the IPv6 wildcard address, this trust issue is material whenever the port is reachable by untrusted clients.

**Recommendation**

- Disable PROXY protocol parsing unless the service is explicitly deployed behind a PROXY-protocol-speaking load balancer.
- When enabled, accept PROXY headers only from a strict allowlist of proxy source addresses, enforced before trusting the header.
- Prefer binding the listener to a private interface reachable only by the trusted proxy and enforce the same condition with a firewall.
- Validate PROXY v1 source/destination addresses using `inet_pton()` and require the address family to match `TCP4` or `TCP6`.
- Validate port ranges, protocol/family fields, header length, and the complete header grammar.
- Preserve the actual socket peer address separately from the claimed forwarded address and label the latter explicitly in logs.

### Low Priority Issues

#### L-01. PROXY v1 Source Field Allows Terminal-Control and Log Injection

**Severity:** Low  
**Status:** Confirmed by source review  
**CWE:** CWE-117 — Improper Output Neutralization for Logs  
**Affected locations:** `src/main.c:98–117`, `src/main.c:199–204`, `src/main.c:225–234`

**Description**

The PROXY v1 source field is parsed as an arbitrary whitespace-delimited string, not a validated IP address. Non-whitespace control characters such as ESC are not rejected by `%s` and can therefore be copied into `client->ip_address`.

That value is printed directly using `%s` in connection and disconnect messages. A crafted source token containing terminal escape sequences can manipulate the display of a terminal or log viewer that interprets ANSI control sequences. It can also make displayed log output misleading.

**Impact**

An attacker who can submit a PROXY v1 header can inject terminal control characters into stdout logs. The practical impact depends on how stdout is collected and viewed; plain-text storage alone does not execute terminal escapes, but interactive viewers may interpret them.

**Recommendation**

- Validate source addresses as IPv4/IPv6 literals and convert them back to a canonical representation before logging.
- Escape all control characters in any untrusted log field, including ESC, CR, LF, DEL, and other C0 controls.
- Use structured logging with a field dedicated to the claimed PROXY address.
- Do not rely on `%s` formatting alone as log sanitization.

#### L-02. Banner Generation Reads an Uninitialized Byte for Three-Byte Lines

**Severity:** Low  
**Status:** Confirmed by source review  
**CWE:** CWE-457 — Use of Uninitialized Variable  
**Affected locations:** `src/main.c:51–61`

**Description**

`randline()` can generate a line length as short as three bytes (`len = 3 + rand16(...) % 30`). For that length, it initializes `line[0]`, `line[1]`, and `line[2]`, then always calls:

```c
if (memcmp(line, "SSH-", 4) == 0) {
```

The fourth byte, `line[3]`, is not initialized for a three-byte line. The comparison therefore examines a byte outside the generated logical line whose value is indeterminate, even though it remains within the allocated 256-byte array.

**Impact**

This is an unnecessary uninitialized-memory read and can be reported by memory-initialization analysis tools. It may make behavior toolchain-dependent, although the earlier CR/LF bytes mean this comparison cannot match the `SSH-` prefix for a three-byte generated line.

**Recommendation**

- Check `len >= 4` before comparing four bytes.
- Alternatively compare only the initialized portion or initialize the complete local buffer before use.
- Add a test that exercises the minimum generated line length and run it under MemorySanitizer or an equivalent tool.

#### L-03. libuv Initialization and I/O Return Values Are Not Consistently Checked

**Severity:** Low  
**Status:** Confirmed by source review  
**CWE:** CWE-703 — Improper Check or Handling of Exceptional Conditions  
**Affected locations:** `src/main.c:292–293`, `src/main.c:322–324`, `src/main.c:334–345`

**Description**

The program does not check the return values of `uv_tcp_init()`, `uv_timer_init()`, `uv_read_start()`, or `uv_timer_start()`. It also does not check the return value of `uv_tcp_bind()` before calling `uv_listen()`.

This leaves failure paths unclear. In particular, if handle initialization fails, the code continues to assign handle data and may proceed to accept or close handles that were not successfully initialized. Failures starting reads or timers can leave a connection in a partially functional state.

**Impact**

Under API or resource failures, the process may fail to service a connection correctly or may attempt cleanup on an improperly initialized handle. The conditions were not reproduced because the application could not be built in the audit environment.

**Recommendation**

- Check every libuv function that returns a status code.
- On partial initialization, close only handles that were successfully initialized and release the client object through a single well-defined cleanup path.
- Handle failures from `uv_read_start()` and `uv_timer_start()` by closing the affected connection and recording the reason.
- Check and report bind/listen errors consistently.

### Informational Issues

#### I-01. The Implementation Does Not Speak the SSH Protocol

**Severity:** Informational  
**Affected locations:** `src/main.c:207–243`, `src/main.c:258–274`, `README.md:3–7`

**Description**

The README describes the project as an SSH honeypot. The supplied implementation does not perform an SSH identification exchange, key exchange, authentication, channel handling, or command processing. After optional first-read PROXY metadata handling, client data is ignored. The server periodically writes generated printable ASCII lines ending in CRLF.

**Impact**

This may be an intentional low-interaction decoy, but it is not a protocol-compliant SSH server. Operators should not assume that SSH clients will negotiate or authenticate successfully, or that the application records SSH usernames, passwords, commands, or channel activity. It is not a substitute for a full SSH honeypot when those capabilities are required.

**Recommendation**

- Describe the service as a low-interaction TCP decoy/banner sink if that is the intended behavior.
- Document what telemetry it does and does not collect.
- If SSH protocol interaction is a requirement, use a maintained SSH implementation or add a carefully scoped, fuzz-tested protocol layer.

#### I-02. Banner PRNG Is Predictable and Repeats Across Connections

**Severity:** Informational  
**Affected locations:** `src/main.c:46–49`, `src/main.c:51–61`, `src/main.c:288–290`

**Description**

`client_t` is zeroed for each connection and `rng_state` is not seeded afterward. The LCG therefore starts from the same state for every client and emits the same sequence of generated lines for each connection. The generator is not cryptographically secure.

**Impact**

The output is predictable and can help identify or fingerprint the service. No cryptographic keys, authentication tokens, or other security-sensitive values are generated by this PRNG in the reviewed source, so this is not reported as a cryptographic compromise.

**Recommendation**

- If banner variation is intended to make the decoy less fingerprintable, seed each connection independently from the operating system CSPRNG.
- Do not use this LCG for keys, tokens, nonces, identifiers, or any security-sensitive purpose.

#### I-03. Build Script Does Not Enforce or Pin the Declared libuv Version

**Severity:** Informational  
**Affected locations:** `README.md:9–11`, `scripts/compile.sh:7`

**Description**

The README declares `libuv >= 1.52.0`, but `compile.sh` invokes `pkg-config --cflags --libs libuv` without asking `pkg-config` to enforce that minimum. The archive contains no lockfile or build manifest recording the exact resolved libuv version.

The upstream libuv advisory for CVE-2024-24806 identifies `uv_getaddrinfo()` hostname truncation and lists libuv 1.48.0 as the patched release. The README's declared minimum, if followed, is above that fixed version. The reviewed application source does not call `uv_getaddrinfo()`, so this particular issue is not identified as reachable through the current source call paths.

**Impact**

Different build environments can silently use different libuv versions, and the build helper itself does not enforce the README's stated compatibility floor. The exact deployed dependency cannot be determined from this source archive.

**Recommendation**

- Enforce the documented minimum in the build helper, for example with `pkg-config --atleast-version=1.52.0 libuv`.
- Record the exact libuv version used for release builds.
- Add dependency inventory and vulnerability checks to the release process.
- Rebuild against a maintained libuv v1.x release and keep the dependency updated.

## Code Quality Security Assessment

### Input Validation

**Rating:** Needs Improvement

- PROXY v1 source addresses are copied without IP-literal validation.
- PROXY headers are accepted from any network peer, without a trusted-proxy check.
- PROXY v1 source/destination ports are parsed into `int` variables but are not range-checked or used.
- PROXY parsing is attempted only against the first positive read; fragmented headers are not accumulated across reads.
- After the optional PROXY header, application payload is ignored rather than parsed as SSH.

### Memory Safety

**Rating:** Needs Improvement

- The stack-local write-buffer lifetime violation in `on_timer()` is the principal memory-safety concern.
- `randline()` performs a four-byte comparison even when only three bytes were generated.
- Fixed-size client and read buffers avoid obvious attacker-controlled heap allocation in the read path.
- The reviewed source contains no direct heap buffer overflow or attacker-controlled copy length that was confirmed as exploitable.

### Cryptography and Authentication

**Rating:** Not Applicable to the Current Implementation

- No SSH cryptography, key exchange, authentication, password processing, or credential storage is implemented.
- The application does not use the LCG for cryptographic material.
- Do not describe this service as providing SSH authentication or cryptographic protections.

### Privilege and Process Isolation

**Rating:** Deployment-Dependent / Not Implemented in Application Code

- No privilege drop, capability restriction, chroot, namespace, seccomp, or sandbox setup is performed by the application.
- The service listens on port `2222`, so it does not inherently require root privileges to bind.
- No shell execution, process spawning, or filesystem access was found in the reviewed C source.
- Run it as a dedicated unprivileged user in a restricted network environment.

### Resource Exhaustion Protections

**Rating:** Poor

- No global or per-source active-connection limit.
- No idle-session timeout or maximum session lifetime.
- No inbound byte/rate budget after connection acceptance.
- `MAX_BACKLOG` is only the listener backlog and does not cap accepted clients.
- No application-level backpressure or client admission policy is present.

### Logging and Monitoring

**Rating:** Needs Improvement

- Connection addresses are printed to stdout and stderr.
- PROXY v1 source text reaches logs without canonical IP validation or control-character escaping.
- PROXY metadata is not clearly distinguished from the actual socket peer address.
- No log retention, rotation, or structured logging is implemented in the application.

## Build and Release Security

The compile helper uses:

```sh
gcc -g -O0 -Wall -Wextra -o .build/exossh src/main.c $(pkg-config --cflags --libs libuv)
```

Observations:

- `-g -O0` indicates a debug-oriented build and should not automatically be treated as the production release profile.
- No explicit production hardening profile is present in the script. The script does not itself request stack protection, fortified libc checks, PIE, RELRO/NOW, or a non-executable stack.
- Toolchain distributions may enable some hardening defaults independently; the archive does not establish which defaults apply.
- The script does not enforce `libuv >= 1.52.0`.
- No automated tests, SAST, dependency scanner, fuzzing target, sanitizer build, or CI configuration was included.

**Recommendation:** Separate debug and release builds. Use a documented, reproducible production toolchain profile with platform-compatible hardening flags, verify the resulting ELF properties, enforce the libuv minimum, and add CI checks for warnings, sanitizers, tests, and dependency advisories.

## Compliance and Secure Engineering Considerations

### OWASP / Secure Engineering Themes

- **Security Misconfiguration:** The application binds to a wildcard address by default and does not establish privilege isolation or trusted-proxy boundaries.
- **Vulnerable and Outdated Components:** The source declares a minimum libuv version, but the build script does not enforce it and no dependency lock is present.
- **Identification and Authentication Failures:** Not applicable as an SSH authentication service; the application does not implement SSH authentication. PROXY source attribution is unauthenticated.
- **Security Logging and Monitoring Failures:** PROXY v1 log injection and forged source attribution can undermine operator telemetry.
- **Denial of Service:** Missing connection limits, idle timeouts, and read-rate controls leave the service exposed to resource exhaustion.
- **Memory Safety:** The asynchronous write buffer does not live through the write completion callback.

### Honeypot-Specific Security

The most important controls for this implementation are:

- Hard limits on concurrent accepted clients, per-source connections, and connection rates.
- Idle and maximum-session timeouts.
- Correct ownership of every buffer retained by asynchronous operations.
- Trusted-proxy authentication/allowlisting before honoring PROXY headers.
- Strict validation and safe logging of every forwarded address.
- Least-privilege execution, network isolation, and outbound traffic restrictions.
- Clear documentation that the current implementation does not provide SSH protocol interaction or credential/command capture.

## Recommendations

### Immediate — Before Public Exposure

1. **Fix H-01:** Implement global/per-source connection limits, idle timeouts, and inbound rate/budget controls.
2. **Fix M-01:** Move the `uv_write()` payload to storage that remains valid until the completion callback; retain request/client state until all pending callbacks complete.
3. **Fix M-02:** Disable PROXY support for direct Internet exposure, or accept PROXY headers only from a narrow trusted-proxy allowlist on a private listener.
4. **Fix L-01:** Validate forwarded addresses and escape control characters before logging.
5. Run the service as a dedicated unprivileged user, behind restrictive firewall rules, with outbound access denied unless explicitly required.

### Near-Term Engineering Work

1. Fix the uninitialized-byte comparison in `randline()`.
2. Check libuv initialization, read, timer, bind, and listen return codes; handle partially initialized clients safely.
3. Enforce `libuv >= 1.52.0` in the build helper and record the exact version used for release builds.
4. Add tests for high connection counts, idle clients, high-rate inbound data, client disconnect during write, slow/non-reading clients, fragmented PROXY headers, forged addresses, and malformed PROXY fields.
5. Run AddressSanitizer and UndefinedBehaviorSanitizer builds, plus MemorySanitizer where supported.
6. Add fuzz tests for both PROXY v1 and v2 parsers.
7. Add a production build profile and verify hardening properties of the resulting binary.
8. Document the low-interaction behavior and telemetry limitations so operators understand what is and is not captured.

### Operational Security

1. Do not run the honeypot on a host that contains sensitive credentials or privileged management services.
2. Do not mount host secrets, SSH agent sockets, private keys, or sensitive directories into its runtime environment.
3. Restrict egress and place the listener in an isolated network segment.
4. Monitor active connections, file descriptors, memory, CPU, and process restarts.
5. Protect and rotate logs; treat the claimed PROXY address as untrusted metadata unless it came from an authenticated proxy.
6. Apply OS-level resource limits and network rate controls in addition to application-level limits.

## Conclusion

The supplied `exossh` 1.3.0 source is small and has a limited application-level protocol surface: it does not implement SSH authentication, command execution, or filesystem operations. However, its network-facing resource management and asynchronous write handling need correction before public exposure.

The most significant issue is the absence of active-client and idle-session limits, which permits unauthenticated clients to retain server resources. The asynchronous write buffer also violates libuv's lifetime contract. In addition, the PROXY protocol implementation trusts arbitrary peers and allows attacker-controlled source metadata into logs.

**Overall Risk: HIGH.**  
**Deployment Decision: Not recommended for direct exposure to untrusted networks until H-01, M-01, and M-02 are remediated.**
