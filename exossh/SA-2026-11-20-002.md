## Executive Summary

This report presents the findings of a security audit conducted on the exossh project (v1.3.0), a minimalist and frugal SSH honeypot server designed to trap illegal access on SSH service, prevent denial-of-service attacks on port 22, and minimize resource usage of suspicious SSH traffic. The server is built with libuv (>= 1.52.0) in C.

**Overall Assessment**: The codebase demonstrates a focused, minimal attack surface with proper PROXY protocol v1/v2 parsing, basic resource controls, and a simple event-driven architecture. However, several security gaps exist: no connection rate limiting, no per-IP connection limits, unbounded memory allocation for clients, weak random number generation for banner generation, lack of authentication/authorization, and dependency version not pinned in build system. The server listens on all interfaces (:: and 0.0.0.0) by default with no configuration options.

**Risk Level**: Medium

## Methodology

- Manual code review of all source files (`src/main.c`, build scripts, configuration)
- Static analysis of security-critical paths (connection handling, PROXY protocol parsing, banner generation, memory management)
- Review of resource limits, timeouts, and concurrency controls
- Dependency and build configuration assessment
- Evaluation against common honeypot/SSH security practices and C secure coding guidelines

## Findings

### High Priority Issues

#### 1. No Connection Rate Limiting or Per-IP Limits
**Severity**: High  
**Status**: Unmitigated  

**Description**: The server accepts unlimited concurrent connections up to the OS backlog limit (MAX_BACKLOG = 64) and libuv's internal limits. There is no per-IP connection limit, connection rate limiting, or any mechanism to prevent a single source from exhausting server resources.

**Risk**: A single attacker can open many connections, consuming file descriptors, memory (client_t struct ~1.2KB each), and CPU (timer callbacks every 10 seconds per connection). This directly contradicts the project's stated goal of "prevent denial-of-service attacks on port 22" and "minimize resource usage of suspicious ssh traffic".

**Location**: `src/main.c:276-329` (on_new_connection), `src/main.c:341` (uv_listen with MAX_BACKLOG 64)

**Recommendation**:
- Implement per-IP connection tracking with configurable limits
- Add connection rate limiting (e.g., max N connections per second per IP)
- Consider exponential backoff or temporary IP bans for abusive sources
- Add a global connection limit with graceful degradation

#### 2. Unbounded Memory Allocation for Clients
**Severity**: High  
**Status**: Unmitigated  

**Description**: Each new connection allocates a `client_t` struct via `malloc()` with no upper bound on total allocations. The refcount mechanism only frees memory when both the TCP handle and timer are closed, but there's no limit on how many can exist simultaneously.

**Risk**: Memory exhaustion (OOM) under sustained connection flood. An attacker opening connections faster than they're cleaned up can exhaust system memory.

**Location**: `src/main.c:282-286` (malloc for client_t), `src/main.c:199-205` (on_close free logic)

**Recommendation**:
- Implement a global connection limit with a semaphore or counter
- Reject new connections when limit is reached (send RST or close immediately)
- Consider a memory pool or pre-allocated client array

#### 3. Weak Random Number Generator for Banner Generation
**Severity**: Medium-High  
**Status**: Unmitigated  

**Description**: The `rand16()` function uses a simple LCG (Linear Congruential Generator) with constants `1103515245` and `12345` (glibc's rand() constants). The seed (`rng_state`) is initialized to zero (via `memset`) and never seeded with entropy.

**Risk**: Predictable banner output reduces honeypot effectiveness. Attackers can fingerprint the honeypot by observing the deterministic banner sequence. While not a direct vulnerability, it undermines the deception goal.

**Location**: `src/main.c:46-49` (rand16), `src/main.c:51-62` (randline), `src/main.c:288` (memset zeros rng_state)

**Recommendation**:
- Seed RNG with cryptographic entropy (e.g., `getrandom()`, `/dev/urandom`, or libuv's `uv_random()`)
- Consider using a CSPRNG like ChaCha20 for banner generation
- At minimum, seed with time + pid + stack address

### Medium Priority Issues

#### 4. Dependency Version Not Pinned
**Severity**: Medium  
**Status**: Requires Attention  

**Description**: The build script uses `pkg-config --cflags --libs libuv` without version pinning. The README states "libuv >= 1.52.0" but the build system doesn't enforce this.

**Risk**: Building against vulnerable or incompatible libuv versions. No reproducible builds. Supply chain risk if libuv has CVEs.

**Location**: `scripts/compile.sh:7`

**Recommendation**:
- Pin libuv version in build system (CMake, meson, or at minimum document exact version in a lockfile)
- Add automated dependency vulnerability scanning in CI
- Consider vendoring or using a lockfile mechanism

#### 5. No Configuration Options - Hardcoded Values
**Severity**: Medium  
**Status**: By Design (Minimalist)  

**Description**: All critical parameters are hardcoded: PORT (2222), INTERVAL_LINE_BANNER_MS (10000), MAX_LINE_LENGTH (32), READ_BUFFER_SIZE (1024), MAX_BACKLOG (64). No command-line arguments, config file, or environment variable support.

**Risk**: Inflexible deployment. Cannot adjust timeouts, buffer sizes, or port for different environments. Cannot disable PROXY protocol if not behind a proxy. Cannot bind to specific interface.

**Location**: `src/main.c:37-41` (defines), `src/main.c:338` (bind to ::), `src/main.c:341` (listen backlog)

**Recommendation**:
- Add configuration via command-line args, config file, or environment variables
- At minimum: port, bind address, banner interval, connection limits
- Document required/production settings

#### 6. PROXY Protocol Without Source Validation
**Severity**: Medium  
**Status**: Requires Operational Controls  

**Description**: PROXY protocol v1/v2 parsing is implemented and enabled by default. The server trusts the PROXY header for client IP address without validating the source of the connection.

**Risk**: IP spoofing if deployed behind an untrusted or misconfigured proxy. The logged/displayed IP can be forged.

**Location**: `src/main.c:75-189` (parse_proxy_v1, parse_proxy_v2), `src/main.c:225-240` (try_parse_proxy in on_read)

**Recommendation**:
- Document that proxy support must only be enabled behind trusted load balancers/proxies
- Add optional source IP allow-list for PROXY protocol connections
- Consider making PROXY protocol optional (disabled by default)

#### 7. No Authentication or Authorization
**Severity**: Medium  
**Status**: By Design (Honeypot)  

**Description**: As a honeypot, the server intentionally accepts all connections and performs no authentication. It sends random banners and logs connections.

**Risk**: By design for a honeypot, but worth documenting. If misused as a real SSH server, it provides no access control.

**Recommendation**: Clearly document this is a honeypot only, not a production SSH server. Add explicit warning in README and code comments.

#### 8. Information Disclosure in Logs
**Severity**: Low-Medium  
**Status**: Acceptable with Caveats  

**Description**: The server logs every connection with IP address and "connected"/"disconnected" messages to stdout. No log rotation, no structured logging, no option to suppress.

**Risk**: Log volume could fill disk under high connection rates. Stdout logging may expose connection patterns in shared environments.

**Location**: `src/main.c:202`, `src/main.c:229`, `src/main.c:313`

**Recommendation**:
- Add log level configuration
- Consider rate-limited logging
- Add option for structured/json logging

### Low Priority Issues

#### 9. Buffer Size Limits Not Enforced on Read
**Severity**: Low  
**Status**: Partially Mitigated by libuv  

**Description**: READ_BUFFER_SIZE is 1024 bytes but libuv's `uv_read_start` will continue calling `alloc_buffer` and `on_read` for streaming data. The `on_read` handler only processes PROXY protocol once, then ignores subsequent data.

**Risk**: An attacker sending large amounts of data after PROXY handshake will cause repeated `on_read` calls with `nread > 0`, consuming CPU in the event loop. The `(void)buf;` cast silences the unused warning but doesn't stop the reads.

**Location**: `src/main.c:241-243` (on_read ignores data after proxy_done)

**Recommendation**:
- Close connection after PROXY handshake if no further protocol expected
- Or implement a maximum total bytes read per connection
- Use `uv_read_stop()` after proxy_done to stop reading

#### 10. No TLS/Encryption (By Design)
**Severity**: Informational  
**Status**: By Design  

**Description**: This is a plaintext SSH honeypot. No TLS, no SSH protocol implementation, no encryption.

**Risk**: Not applicable for a honeypot, but traffic is visible on network.

**Recommendation**: Document clearly. If SSH protocol emulation is added later, implement proper key exchange.

#### 11. Timer Callback Uses write_req.data for Function Pointer
**Severity**: Low  
**Status**: Code Quality  

**Description**: The `on_timer` callback casts `req->data` to a function pointer and calls it: `uv_timer_start(&client->timer, (uv_timer_cb)req->data, ...)`. This works but is an unusual pattern.

**Risk**: Minor - potential for confusion, type safety issue. If `req->data` is corrupted, arbitrary code execution.

**Location**: `src/main.c:258-274` (on_timer), `src/main.c:264-265` (req->data = (void *)on_timer)

**Recommendation**: Use a dedicated timer callback or store a flag in client_t instead of function pointer in write_req.data.

#### 12. Missing Security Headers / Compiler Hardening
**Severity**: Low  
**Status**: Build Configuration  

**Description**: The compile script uses `-g -O0 -Wall -Wextra` but no hardening flags like `-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, `-fPIE -pie`, `-Wformat-security`, etc.

**Risk**: Easier exploitation if memory corruption bugs exist.

**Location**: `scripts/compile.sh:7`

**Recommendation**: Add hardening flags for production builds:
```
-fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie -Wformat-security -Werror=format-security
```

## Code Quality Security Assessment

### Input Validation
**Rating**: Good  
- PROXY protocol v1/v2 parsing includes length checks, signature validation, version/command checks, address family validation
- Proper bounds checking on `sscanf` output and string copies with `strncpy` + manual null-termination
- IPv4/IPv6 address parsing uses `inet_ntop` with proper buffer sizes

### Memory Safety
**Rating**: Fair  
- No obvious buffer overflows in parsing code
- `malloc`/`free` paired correctly in happy path
- **Concerns**: No allocation failure handling beyond printing error (line 284-285), no bounds on total allocations, `memset` zero-initialization but RNG state not seeded, potential use-after-free if timer fires after handle closed (refcount mitigates)

### Concurrency Safety
**Rating**: Good  
- Single-threaded libuv event loop - no data races
- Refcount correctly tracks handle + timer lifetime
- Proper cleanup in error paths

### Cryptographic Implementation
**Rating**: N/A / Poor  
- No cryptography used (by design for honeypot)
- RNG for banners is non-cryptographic and unseeded

## Compliance Assessment

### Common Honeypot Security Practices
- **Deception**: Weak - predictable banners due to unseeded LCG
- **Containment**: Good - no shell access, no command execution, minimal protocol
- **Logging**: Basic - stdout only, no structure, no rotation
- **Resource Control**: Poor - no limits, contradicts project goals
- **Deployment Flexibility**: Poor - hardcoded everything

### C Secure Coding (CERT/SEI)
- **MEM31-C** (free dynamically allocated memory): Followed
- **MEM35-C** (allocation size): No integer overflow risk (fixed struct size)
- **STR31-C** (sufficient space for strings): `strncpy` with manual null-term, buffer sizes respected
- **INT30-C** (unsigned integer operations): `addr_len` calculations use uint16_t, safe
- **MSC30-C** (rand() for security): **VIOLATED** - LCG used for banner generation
- **ERR33-C** (handle errors): malloc failure handled but continues; uv_* errors logged but server keeps running

## Recommendations

### Immediate Actions (High Priority)
1. **Add connection limits**: Global max connections + per-IP limits with configurable thresholds
2. **Seed RNG properly**: Use `uv_random()` or `getrandom()` to seed `rng_state` at client creation
3. **Add memory bounds**: Implement semaphore or counter to limit concurrent `client_t` allocations
4. **Stop reading after PROXY**: Call `uv_read_stop()` in `on_read` after `proxy_done = 1`

### Medium-term Improvements
1. **Pin libuv version**: Add CMake/meson build with version pinning, or document exact version in lockfile
2. **Add configuration system**: Command-line args or config file for port, bind address, intervals, limits
3. **Make PROXY protocol optional**: Disable by default, require explicit enable with warning
4. **Add compiler hardening**: Update compile.sh with `-fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie`
5. **Improve logging**: Add log levels, rate limiting, structured output option

### Operational Security
1. **Run with least privilege**: Dedicated user, no root, restricted filesystem access
2. **Network placement**: Bind to specific interface, not ::/0.0.0.0, unless intentionally exposed
3. **Monitor resources**: Watch file descriptors, memory, CPU for anomalies
4. **Log aggregation**: Pipe stdout to log collector with rotation
5. **Document honeypot-only use**: Explicit warnings in README, code, and any packaging

## Conclusion

Version 1.3.0 of exossh implements a functional minimal SSH honeypot with correct PROXY protocol parsing and a clean libuv event loop. However, it fails to meet its own stated goals of preventing DoS and minimizing resource usage due to the complete absence of connection limiting, rate limiting, and memory bounds. The unseeded LCG for banner generation reduces deception effectiveness.

The primary risks are operational and resource-exhaustion related rather than memory corruption or injection vulnerabilities. The code itself is relatively clean C with proper bounds checking in parsing routines.

With the recommended connection limiting, RNG seeding, and configuration additions, exossh would provide a much more robust honeypot suitable for production deployment.

**Risk Level**: Medium  
**Recommended Actions**: Address connection limiting and RNG seeding within 30 days; add configuration and build hardening as medium-term improvements.
