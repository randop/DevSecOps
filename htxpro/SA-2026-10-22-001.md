# Security Audit Report for htxpro (Version 0.7.1)

**Project:** htxpro (https://github.com/randop/htxpro)

**Version:** 0.7.1

**Audit Date:** 2026-10-22

**Auditor:** Independent Security Analysis (Grok)

**Audit Type:** Source Code Security Review (Static)

**Artifact:** `master` branch, tree `d9d574a9971c7881644ddc59e29bdc3204b2b9f0` (as of 2026-10-22)

**Report ID:** SA-2026-10-22-001

**AI Model:** xAI Grok 4.7

## Executive Summary

This report presents an independent security audit of htxpro 0.7.1, a Linux-only Rust web server that terminates HTTP/3 (quiche), HTTP/2 (monoio-http), and HTTP/1.1 on a mandatory Monoio `IoUringDriver`. All first-party Rust sources under `src/` (about 7,400 lines), the YAML examples, `Dockerfile`, systemd unit, `Cargo.toml`, and `Cargo.lock` were reviewed. Security-critical paths — HTTP/1.1 framing, host routing, static file confinement, the WorkOS authorization-code gate, QUIC retry, and admission control — were traced line-by-line. Host-wildcard matching and the session-secret length check were re-simulated outside the crate.

**Overall Assessment:** The server is carefully built. HTTP/1.1 rejects `Transfer-Encoding`, duplicate headers, and non-origin request targets. QUIC uses stateless Retry tokens bound to peer address, port, and connection ID. OAuth state is HMAC-signed, compared in constant time, and bound to PKCE S256. Path `..` segments are rejected after percent-decoding. Limits and timeouts are actually enforced, not merely advertised. The weaknesses are concentrated in authentication configuration, the shipped Docker profile, and a few resource-isolation gaps. None are an unauthenticated remote code-execution bug. The serious authentication failure is config-triggered: the check that claims to require 32 bytes of entropy accepts the placeholder published in the repository, and that key forges every session and OAuth state cookie. The image that `docker build` produces listens in cleartext and exposes an unauthenticated writable item store.

**Risk Level:** Medium

## Methodology

- Manual review of `src/main.rs`, `src/config.rs`, `src/http1_server.rs`, `src/http2_server.rs`, `src/http3_server.rs`, `src/http_types.rs`, `src/static_site.rs`, `src/tls.rs`, `src/security/mod.rs`, `src/security/workos.rs`, `src/security/http_client.rs`, `src/controllers/mod.rs`, `src/controllers/core.rs`, `src/controllers/items.rs`, plus `Cargo.toml`, `Cargo.lock`, `Dockerfile`, `deploy/htxpro.service`, `deploy/config.docker.yaml`, `deploy/README.md`, `config.example.yaml`, `ARCHITECTURE.md`, and `CHANGELOG.md`.
- Simulation of `host_matches` against the single-label SNI matcher in `src/tls.rs`, and of the published `session_secret` placeholder against the length check.
- Review of admission control, QUIC anti-amplification, OAuth cookie and redirect handling, and static path decoding.
- Dependency review against RustSec entries published through 2026-10-22 for the locked rustls versions. quiche 0.30.0 was not matched to a current critical advisory in this pass.
- Evaluation against OWASP Top 10, RFC 9110 / 9112 / 9113 / 9114, RFC 6749, and RFC 7636.

This was a static review. The crate was not executed and `cargo test` was not run (the tree was cloned without a build of quiche/BoringSSL). Findings below are from source and from the simulations named above.

## Findings

### High Priority Issues

#### 1. Session Secret Check Counts Bytes, Not Entropy — Published Placeholder Forges Sessions

**Severity:** High

**Status:** Confirmed — exploitable when security is configured with the documented secret; authentication is not enabled in the default Docker config

**Description:** `validate_security()` documents and errors as if it required entropy:

```rust
anyhow::ensure!(
    security.session_secret.len() >= 32,
    "security.session_secret must contain at least 32 bytes of entropy"
);
```

The predicate is only `str::len() >= 32`. The HMAC key is the raw string (`hmac::Key::new(HMAC_SHA256, session_secret.as_bytes())` in `SecurityRuntime::new`). There is no denylist, no minimum unique-character check, and no requirement to load the key from a file mode `0600`.

The placeholder shipped in `config.example.yaml` (commented block) and in the configuration example in `ARCHITECTURE.md` is:

`replace-with-at-least-32-random-bytes`

That string is 37 bytes. It passes validation. Anyone who can read the repository can compute the same HMAC-SHA256 over `SessionClaims` and `StateClaims` and mint:

- a session cookie accepted by `verify_session` until `exp` (default 3600 seconds, configurable up to one year)
- an OAuth state cookie whose `state` and PKCE `verifier` the server will trust

Forged session claims set `sub`, `email`, and `name`. `whoami` and any later handler that trusts `request.auth` will treat the caller as that identity. A forged state cookie lets an attacker complete the callback with their own authorization code while choosing `return_to`.

**Risk:** Full authentication bypass and OAuth-state forgery on any deployment that pastes the documented secret, or any other 32+ character password, into `security.session_secret`.

**Recommendation:**

- Compare the configured secret against a list of known placeholders and reject it.
- Require a key loaded from a dedicated file (mode `0600`) or an environment variable, and document that the YAML example is not a valid key.
- Derive the HMAC key with HKDF instead of using the password bytes directly.
- At startup, refuse secrets with low Shannon entropy or with fewer than 32 bytes decoded from a hex/base64 alphabet so that a typed password cannot pass the check by accident.
- Add a regression test that `replace-with-at-least-32-random-bytes` is rejected.

### Medium Priority Issues

#### 2. OAuth `redirect_uri` Is Not Required to Be HTTPS

**Severity:** Medium

**Status:** Confirmed

**Description:** `ensure_secure_endpoint()` is applied to `authorization_endpoint` and `token_endpoint` (HTTPS, or an IP that parses as loopback). `redirect_uri` is only checked as an HTTP(S) URL with a non-root path and no query string. `http://api.example.test/callback` is accepted if that host matches the virtual host.

The authorization code is delivered in that URL's query string. `handle_callback` then exchanges it and emits `Set-Cookie` on the same response. If `cookie_secure` is false (the documented setting for plain-HTTP testing), the session cookie is stored by the browser. If `cookie_secure` remains true, the cookie is still written onto the cleartext response. The shipped examples enable `plain_listen` on `0.0.0.0:8080`, so the cleartext callback is reachable whenever plaintext is left on.

**Risk:** Network capture of authorization codes and, when `cookie_secure` is disabled, of session cookies. This is an operator-configuration bug that the loader should reject the same way it rejects an `http://` token endpoint.

**Recommendation:**

- Require `redirect_uri` to be `https://` unless the host is a numeric loopback address.
- Refuse to start if any virtual host has security enabled while `cookie_secure` is false and a plaintext listener is enabled.
- Bind the signed state claims to the redirect URI and to the request host, and check both on callback.

#### 3. Shipped Docker Configuration Exposes Cleartext HTTP and an Unauthenticated Writable API

**Severity:** Medium

**Status:** Confirmed — this is the image default, not only a comment

**Description:** `Dockerfile` copies `deploy/config.docker.yaml` to `/app/config.yaml`. That file sets `http1_plain_enabled` and `http2_plain_enabled`, binds `plain_listen` to `0.0.0.0:8080`, and publishes controller routes with no `security` module:

- `GET /metrics` returns in-flight counts, rate-limit rejects, timeout counters, and connection totals (`AppRuntime::metrics_snapshot`)
- `POST /echo` reflects the request body
- `GET`/`POST`/`PUT`/`PATCH`/`DELETE /v1/items` reads and writes the in-memory item store

`deploy/README.md` warns not to publish port 8080 unless cleartext is intended, then the sample `docker run` publishes `-p 8080:8080/tcp`. Code defaults for the plaintext flags are `false` (`#[serde(default)]` on `bool`); the vulnerable profile is the one the image actually runs.

**Risk:** Unauthenticated read/write of the demo store, operational reconnaissance via `/metrics`, and cleartext transport on all interfaces. There is no per-route authentication inside the handlers; the only gate is the virtual-host module, which this config does not set.

**Recommendation:**

- Ship the image with plaintext listeners off and with `/metrics`, `/echo`, and the items routes absent or bound to a host that requires a security module.
- Make the sample `docker run` match the warning: do not publish 8080.
- Split a `config.example.yaml` "demo" profile from the runtime default.

#### 4. The Items Handler Uses One Process-Wide Store

**Severity:** Medium

**Status:** Confirmed

**Description:** `ControllerRuntime::new` creates a single `Rc<RefCell<items::StoreState>>` and every route whose handler is `"items"` uses it, regardless of controller name or virtual host. `items::handle` does not consult `request.auth`. Isolation exists only because `dispatch_inner` runs the host gate first.

A public host and an authenticated host that both register the `items` handler share records. A caller who passes the public host's gate reads and overwrites the authenticated host's data. The store is also not partitioned by tenant on `*.tenant.example.test`.

**Risk:** Cross-host data disclosure and tampering as soon as two trust domains mount the built-in handler. Capacity limits (`MAX_ITEMS` 1024, 16 MiB) contain memory use; they do not contain authorization.

**Recommendation:**

- Key the store by virtual host, or require the handler to refuse requests when `request.auth` is `None` unless the route is explicitly marked public.
- Do not treat the built-in CRUD handler as a multi-tenant primitive without an ownership check on `id`.

#### 5. `default_host` Admits Arbitrary Authorities into the Default Site's Budget

**Severity:** Medium

**Status:** Confirmed — `default_host` is set in `config.example.yaml` and `deploy/config.docker.yaml`

**Description:** `Config::resolve_host` falls through to `default_host` when no exact name and no wildcard match. `acquire_request` then charges that virtual host's inflight counter and workload class. With the shipped static default host, unknown `Host` / `:authority` values are classified as `WorkloadClass::Static`.

The static cap is global, not per host:

```rust
state.active_static_requests >= self.config.limits.max_inflight_static_requests
```

The default is 16. One client is allowed 32 in-flight requests per IP, so a single source can hold every static slot on the process. Each hold lasts until the response finishes, bounded by `request_process_ms` (5 s) plus `response_write_ms` (10 s), and can be renewed. Legitimate static hosts, including other names that are not the default, share that same counter.

Separately, the default site's bytes are returned with status 200 for an attacker-chosen `Host`. Caches or non-browser clients that key only on the URL can store that response under the wrong name. Browsers will not attach the real host's cookies to the attacker's name, because `Set-Cookie` does not set `Domain`.

**Risk:** Low-concurrency denial of service against every static virtual host, plus the usual default-vhost content confusion.

**Recommendation:**

- When the authority matches nothing, return 421 and charge a dedicated `"<unmatched>"` budget that is not the default host's static pool. Keep `default_host` as an explicit opt-in that still uses a separate counter.
- Prefer rejecting unknown hosts in production multi-tenant configs.

#### 6. QUIC Receive Windows Are Not Tied to a Process Memory Budget

**Severity:** Medium

**Status:** Confirmed by inspection of `make_quic_config`; not load-tested

**Description:** Each accepted QUIC connection advertises `initial_max_data` of 4 MiB and 1 MiB per stream direction, with up to `max_concurrent_streams_per_connection` bidirectional streams (default 128). `max_quic_connections` defaults to 512 and `max_quic_connections_per_ip` to 64. Eight source addresses can fill the connection table. 512 × 4 MiB is a 2 GiB receive window the peer is allowed to occupy inside quiche, before the application body cap (`max_request_body_bytes`, default 1 MiB) applies. Application bodies are additionally bounded by `max_inflight_requests` (default 256).

Stateless Retry is implemented and is the right anti-amplification control: Initials shorter than 1200 bytes are dropped, and the Retry token is HMAC-SHA256 over the peer IP, port, server CID, and original CID, with a 10 second `Instant` lifetime. That stops bandwidth amplification. It does not cap memory after the handshake, and Retry itself is not rate-limited per source, so an Initial flood still costs header parsing and HMAC on the event loop.

Active migration is disabled (`set_disable_active_migration(true)`). Early data is not enabled. Those are sound choices; they do not offset the window size.

**Risk:** Memory exhaustion by a handful of completed QUIC handshakes. Availability only; no confidentiality break was identified on this path.

**Recommendation:**

- Scale `initial_max_data` to the request body limit, or maintain a process-wide received-byte budget that closes connections when exceeded.
- Rate-limit unauthenticated Initial/Retry processing per source address.
- Lower the default `max_quic_connections` on small hosts and document the memory product `max_quic_connections × initial_max_data`.

#### 7. Authenticated Mutations Have No CSRF Token

**Severity:** Medium

**Status:** Conditional — requires attacker-controlled HTML on a same-site virtual host

**Description:** Session cookies are `HttpOnly; SameSite=Lax; Path=/` and, by default, `Secure`. There is no CSRF token and no custom header requirement on `POST`/`PUT`/`PATCH`/`DELETE`. `SameSite=Lax` blocks cross-site POST. It does not block same-site POST. Hosts under one registrable domain (`api.example.test` and `anything.tenant.example.test`) are same-site, so a script served by the wildcard static host can `fetch` the authenticated API with credentials. The wildcard matcher also accepts extra labels (Finding 8), which widens the set of names that serve that static tree.

The items handler and `echo` perform state changes. Nothing in `controllers/` checks an origin header.

**Risk:** Cross-host state change with the victim's session, if any same-site virtual host ever serves content an attacker can influence (XSS, a compromised tenant page, or a too-broad wildcard root). Not exploitable against the current operator-authored static files alone.

**Recommendation:**

- Require a non-cookie header or a CSRF token for unsafe methods, and reject browser-form content types on API routes.
- Prefer `SameSite=Strict` for the session cookie when the OAuth callback host and the application host are the same.
- Serve untrusted tenant HTML on a separate registrable domain from the authenticated API.

### Low Priority Issues

#### 8. Virtual-Host Wildcards Match Multiple Labels

**Severity:** Low

**Status:** Confirmed by simulation

**Description:** SNI selection uses a single-label matcher (`wildcard_matches` in `src/tls.rs`: the left label must not contain a dot). Virtual-host routing uses `host_matches`:

```rust
host.len() > suffix.len() + 1
    && host.ends_with(suffix)
    && host.as_bytes().get(host.len() - suffix.len() - 1) == Some(&b'.')
```

Simulation results for pattern `*.example.com`:

| Host | Virtual host | SNI wildcard |
| --- | --- | --- |
| `a.example.com` | match | match |
| `a.b.example.com` | match | no match |
| `example.com` | no match | no match |
| `badexample.com` | no match | no match |

`*.tenant.example.test` therefore serves `a.b.tenant.example.test`. Exact names are still tested first, so this does not steal an explicitly configured host. It does attach the wildcard site, and its security module if any, to names the operator likely did not intend. Cookies are host-only (no `Domain`), so this is not a cookie-tossing bypass.

**Recommendation:** Use the same single-label rule as `wildcard_matches`. Add the `a.b.example.com` case next to the existing `host_matches` tests.

#### 9. Static Reads Follow Symlinks and Do Not Hide Dotfiles

**Severity:** Low

**Status:** By design — `ARCHITECTURE.md` already says not to place untrusted symlinks under a served root

**Description:** `static_site::serve` percent-decodes the path, rejects `\`, NUL, `.`, and `..`, and refuses non-`Normal` components. That blocks URL traversal, including `%2e%2e` and `%2f`. `read_bounded_file` then `File::open`s the joined path. `open` follows symlinks and does not check that the canonical file is still under the canonical root. Startup canonicalizes the root directory itself, not the files created later inside it. There is no denylist for `.git`, `.env`, or backup names. `mime_guess` will serve them with whatever type the extension maps to. Size is capped by `max_static_file_bytes` (1 byte to 32 MiB). The read runs under the request-process deadline, which limits a hang on a FIFO if cancellation drops the io_uring operation.

**Risk:** A symlink inside a static root, or a VCS directory deployed as the root, is readable by any client who can name it. This build has no upload handler, so a remote client cannot plant the symlink.

**Recommendation:** Open with `O_NOFOLLOW`, or open and then verify `/proc/self/fd/N` (or the canonical path) still starts with the root. Reject dot segments and names such as `.git`. Keep the runtime user unable to write the roots, as the deployment notes already say.

#### 10. HTTP/3 Does Not Apply the HTTP/1.1 and HTTP/2 Request Checks, and Omits `nosniff`

**Severity:** Low

**Status:** Confirmed — current handlers compensate, so this is not an open redirect today

**Description:** HTTP/1.1 rejects targets that do not start with `/`, that start with `//`, or that contain `\`, `#`, or control characters, and it rejects `Transfer-Encoding` and duplicate headers. HTTP/2 rejects `//`, `#`, and `\`. The HTTP/3 header loop assigns `:path` and `:authority` from raw QPACK fields with no origin-form check. Duplicate pseudo-headers overwrite; the last value wins if quiche delivers them.

`static_site` and `safe_return_to` still refuse `//`, controls, and `..`, so the gap is not currently a traversal or an open redirect. `pump_outgoing` also does not emit `x-content-type-options: nosniff`, which both TCP writers set, and it does not scrub `content-type` for control characters before the H3 header is built. H3 framing is binary, so this is not HTTP/1 response splitting on the wire htxpro itself speaks. A translator in front of the process could be less careful.

**Recommendation:** Run one shared origin-form and header-safety check before `dispatch` on all three protocols. Add `nosniff` on HTTP/3. Reject duplicate pseudo-headers in the application even if quiche already does.

#### 11. Stateless Sessions Cannot Be Revoked

**Severity:** Low

**Status:** Confirmed — design limitation

**Description:** Session cookies are HMAC tokens containing `sub`, `email`, `name`, module name, and `exp`. There is no `jti`, no server-side session table, and no logout route. `session_ttl_seconds` may be as long as 31,536,000 (one year). A stolen cookie remains valid until `exp`. The cookie is not bound to the host, the TLS channel, or the client address. Theft still requires XSS that can read `HttpOnly` (it cannot), a `cookie_secure: false` network capture, or a leak of the HMAC key (Finding 1).

**Recommendation:** Keep TTLs short. Add a logout route that rotates a key id (`kid`) or records revoked `jti`s until expiry. Put the host into the signed claims and check it in `verify_session`.

#### 12. Certificate Name, Certificate Lifetime, and Token-Endpoint Address Are Loosely Bound

**Severity:** Low

**Status:** Confirmed

**Description:**

- Routing uses `:authority` / `Host`, not the SNI value that selected the certificate. A non-browser client can complete TLS with name A (or with the first chain, which is the fallback for missing SNI) and request host B. Browsers will not. If host B has no security module, its content is served on that connection.
- `TlsMaterial::load` pairs leaves to keys and builds chains. It does not reject certificates that are expired, not yet valid, or missing `serverAuth`. Clients will fail those handshakes; startup will not.
- The outbound token client pins the URL host via rustls server-name verification, does not follow redirects, and caps the response at 2 MiB. It does not reject DNS answers in private, link-local, or metadata ranges. A configured hostname that resolves to `169.254.169.254` and presents a certificate for that name receives `client_secret`. Loopback `http://` is intentionally allowed and is IP-only (`localhost` is not treated as loopback).

**Recommendation:** Optionally bind the routed host to the SNI name in strict mode. Warn or fail on expired leaves at load. Refuse token-endpoint addresses that fall in loopback (except an explicit dev flag), link-local, or RFC 1918 / ULA ranges when the URL was not a literal loopback.

#### 13. Locked rustls Is One Release Behind a Security Fix; rustls 0.21 Is Still Linked

**Severity:** Low

**Status:** Confirmed against RustSec as of 2026-10-22

**Description:** `Cargo.lock` pins direct `rustls` 0.23.45. Rustls 0.23.46 (2026-10-13) fixes four advisories. The one that applies to this tree is RUSTSEC-2026-0349 (CVSS 3.7): a network attacker can poison the client's remembered key-exchange group with an unauthenticated ServerHello, so later connections to that name offer only classical X25519. htxpro's WorkOS client builds a `rustls::ClientConfig` and sends `client_secret` on it. Impact is loss of hybrid post-quantum secrecy on that connection, not a plaintext break, and only if the peer accepts the classical share.

The other three do not apply to the features this binary enables:

- RUSTSEC-2026-0346 — `Debug` of client session values. The server does not log those values.
- RUSTSEC-2026-0347 — ECH early data sent after rejection. ECH is not enabled. Affected range is also `< 0.23.44`.
- RUSTSEC-2026-0348 — Brotli certificate decompression up to 1 GiB. The `brotli` feature is not enabled (`ring`, `std`, `tls12` only).

`monoio-http` 0.3.12 depends on `monoio-rustls` 0.3.0, which links `rustls` 0.21.12. The server's TLS acceptor uses `monoio-rustls` 0.4 / rustls 0.23 directly. The 0.21 crate is still in the lockfile and is end-of-life. No critical advisory was confirmed on the quiche 0.30.0 pin during this pass.

**Recommendation:** Bump `rustls` to `>= 0.23.46`, refresh `Cargo.lock`, and re-run tests. Drop or upgrade the monoio-http path that pulls rustls 0.21. Run `cargo audit` in CI.

#### 14. Browser Hardening Headers and Log Hygiene

**Severity:** Low

**Status:** Confirmed

**Description:**

- Responses set `X-Content-Type-Options: nosniff` on TCP only (Finding 10). They do not set `Strict-Transport-Security`, `Content-Security-Policy`, `Referrer-Policy`, or a frame-ancestors / `X-Frame-Options` policy. Static HTML and the SPA fallback are active content. The OAuth callback is a 303 with an empty body, which avoids the worst Referer leak, but a later same-origin document can still leak the callback URL if a browser sends it.
- A non-2xx body from the token endpoint is included in a `warn!` log, truncated to 512 characters. A verbose identity provider can echo token material into logs.
- `server: htxpro` is always sent. `/status` reports the crate version when that route is mounted.

**Recommendation:** Add HSTS on TLS responses (include subdomains only when every name is HTTPS-only), a restrictive CSP for static HTML, `Referrer-Policy: no-referrer` on the callback, and `frame-ancestors 'none'`. Log the token-endpoint status code, not the body.

## Code Quality Security Assessment

#### Input Validation

**Rating:** Good (with exceptions)

- HTTP/1.1 request-line parsing is strict: exactly three tokens, HTTP/1.1 only, origin-form, no controls, no `#` or `\`, `Host` required, duplicate headers rejected, `Content-Length` digit-only, `Transfer-Encoding` and `Expect` rejected with connection close.
- Static and controller paths are percent-decoded once; `..`, `.`, `\`, and NUL are rejected. The unit tests cover `%2e%2e` and `%2f`.
- OAuth `return_to` allows only bytes `0x21..=0x7e` excluding `\`, rejects `//` and scheme-relative forms, and rejects the same after percent-decoding.
- **Weaknesses:** HTTP/3 does not share those origin-form checks (Finding 10); virtual-host wildcards are multi-label (Finding 8); `session_secret` length is treated as entropy (Finding 1); `redirect_uri` may be cleartext (Finding 2).

#### Memory Safety

**Rating:** Good

- First-party server code has no `unsafe`. Release builds use `panic = "abort"`, thin LTO, and `codegen-units = 1`. Counters and body lengths generally use `saturating_add` / `checked_add`.
- Request bodies, header blocks, static files, and the item store have hard caps. The QUIC window product in Finding 6 is the main memory gap, and it sits in quiche's buffers rather than in an unchecked `Vec` in application code.
- `yaml_serde` with `deny_unknown_fields` parses local operator config. Alias expansion was not fuzzed; a hostile YAML file is an operator-local startup concern.

#### Cryptographic Implementation

**Rating:** Good (with the key-management exception in Finding 1)

- Inbound TLS uses `rustls` `with_safe_default_protocol_versions` (TLS 1.2 and 1.3) and a custom SNI resolver. Leaves must match a configured private key or startup fails. HTTP/3 uses the same chains through BoringSSL's certificate callback.
- QUIC Retry tokens use a process-generated HMAC-SHA256 key, not a static secret.
- OAuth uses PKCE S256, 32 bytes from `ring::rand::SystemRandom` for `state` and the verifier, and `hmac::verify` plus `subtle::ConstantTimeEq` for state. Cookie values are base64url of the JSON payload and the tag.
- **Weaknesses:** the HMAC key is the config string; sessions are not revocable; rustls 0.23.45 is one security release behind on the outbound client (Finding 13). 0-RTT is not enabled.

## Dependency Analysis

### rustls 0.23.45 (direct) and 0.21.12 (via monoio-http 0.3.12)

See Finding 13. `Cargo.lock` makes the build reproducible, which is better than a floating `find_package`. The lock is still stale relative to rustls 0.23.46 (2026-10-13). Transitive rustls 0.21.12 should be removed even if the live acceptor uses 0.23.

### quiche 0.30.0 and boring 5.3.0

Pinned exactly (`boring = "=5.3.0"`, quiche `0.30.0` with `boringssl-boring-crate`). No critical advisory was identified for this pin in the current window. QUIC behavior reviewed in-tree (Retry, migration disabled, idle timeout wired to `keep_alive_idle_ms`, `max_field_section_size` set from `max_header_bytes`) is consistent with the library being used as a state machine rather than as an HTTP router.

### monoio 0.2.4 and monoio-http 0.3.12

The runtime is constructed only as `RuntimeBuilder::<IoUringDriver>`. There is no epoll fallback; ring setup failure aborts startup. HTTP/2 accept errors close the connection instead of spinning, and response bodies are written in flow-control-sized chunks. monoio-http's older rustls dependency is the issue, not the H2 state machine that this tree drives.

### ring 0.17.14, x509-parser 0.18.1, webpki-roots 1.0.10

Used for HMAC, PKCE, certificate name extraction, and the outbound root store. webpki-roots is compiled into the binary, so trust-anchor updates require a rebuild. That is acceptable if releases are frequent; it is a problem if the server is left on a stale image.

### Build and CI

- No `.github` workflows and no `cargo audit` / `cargo deny` configuration are in the tree.
- Release profile strips symbols and aborts on panic. It does not set `overflow-checks = true`.
- `Dockerfile` uses floating `rust:bookworm` and `debian:bookworm-slim` tags, not digests. The runtime user is UID 10001, which is right. The image still embeds the permissive YAML from Finding 3.

**Recommendation:** Pin image digests, add a CI job for `cargo audit`, `cargo test`, and at least one HTTP/1 parser fuzz target. Set `overflow-checks = true` on release until the hot paths are measured.

## Compliance Assessment

### OWASP Top 10 Coverage

- **Injection:** Strong on the request parsers reviewed. No shell, SQL, or template sink. Header values written by the application pass `is_safe_header` (token name, no CTL except tab). HTTP/3 `content-type` is the exception and is server-generated.
- **Broken Authentication:** The WorkOS flow (PKCE, signed state, host check on `redirect_uri`, HttpOnly cookie) is sound. Finding 1 removes that guarantee if the HMAC key is the published placeholder. Finding 11 limits incident response. Finding 7 is a same-site CSRF gap.
- **Sensitive Data Exposure:** TLS defaults are modern. Cleartext is off in code defaults and on in the Docker profile (Finding 3). `redirect_uri` may be HTTP (Finding 2). Spool-style file permission issues do not arise; the server does not write request bodies to disk. The item store is RAM only.
- **Broken Access Control:** Host gate is applied before static and controller dispatch, including the OAuth callback. The items handler has no object-level authorization and one global map (Finding 4). `default_host` serves one site for every other name (Finding 5).
- **Security Misconfiguration:** Dominant theme of Findings 2, 3, 5, and 12. systemd unit is better than average: `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `LockPersonality`, `MemoryDenyWriteExecute`, `RestrictAddressFamilies=AF_INET AF_INET6`. It does not set `CapabilityBoundingSet=`, `SystemCallArchitectures=native`, or `RestrictRealtime`.
- **Vulnerable Components:** Finding 13. Lockfile exists; scanning does not.
- **Identification and Authentication Failures / Logging:** JSON logs with a configurable filter. The example filter is `htxpro=debug`. Token-endpoint bodies can reach the log (Finding 14). `/metrics` is safe only when the route is authenticated.
- **SSRF:** The only outbound client is the configured token endpoint. Redirects are not followed. Private-address filtering after DNS is missing (Finding 12). A remote caller cannot change the URL.
- **XSS, XXE, insecure deserialization:** No XML. JSON bodies go through `serde_json`. Static HTML is served as HTML without a CSP (Finding 14). Cookie and location values used for redirects are constrained.

### HTTP-Specific Security

- RFC 9112: HTTP/1.1 origin-form, `Content-Length` only, no chunked requests, no request smuggling desync inside this process because there is no downstream HTTP hop. Pipelining keeps bytes in a buffer and drains exactly `Content-Length`.
- RFC 9113: HTTP/2 uses the library for framing, sets `max_header_list_size` and `max_concurrent_streams`, and writes body bytes only after send-window capacity. The code comments and the accept-loop error path show the connection is torn down on a connection-level protocol error instead of spinning.
- RFC 9114 / QUIC: Retry before accepting state, minimum Initial size, migration disabled, H3 field-section size capped. `:path` validation is weaker than on TCP (Finding 10).
- RFC 6749 / 7636: authorization-code with PKCE S256. `redirect_uri` is sent on the authorize redirect and omitted from the WorkOS token POST, which matches WorkOS's authenticate JSON rather than a generic token endpoint. State is bound to the module name and compared with `ct_eq`.
- Alt-Svc `h3=":<listen port>"; ma=86400` is advertised on TCP, including cleartext responses. That is an upgrade hint, not a downgrade.

## Recommendations

### Immediate Actions (High Priority)

1. Reject non-cryptographic `session_secret` values, including the published placeholder, and load the HMAC key from a `0600` file or the environment (Finding 1).
2. Require HTTPS `redirect_uri` for non-loopback hosts, and refuse `cookie_secure: false` when a plaintext listener is on (Finding 2).
3. Change `deploy/config.docker.yaml` so the image does not enable cleartext or mount `/metrics`, `/echo`, and items without a security module. Fix the `docker run` example (Finding 3).
4. Return 421 for unknown authorities without charging the default static pool (Finding 5).

### Medium-term Improvements

1. Partition or authenticate the items store (Finding 4).
2. Add a CSRF check on unsafe methods (Finding 7).
3. Cap QUIC memory and rate-limit pre-handshake Initials (Finding 6).
4. Make virtual-host wildcards single-label and share one request-target validator across H1, H2, and H3 (Findings 8 and 10).
5. Open static files with a root check that survives symlinks (Finding 9).
6. Bump rustls to 0.23.46 or newer, drop rustls 0.21 from the graph, and add `cargo audit` to CI (Finding 13).
7. Add HSTS, CSP, `Referrer-Policy`, and frame-ancestors; stop logging token-endpoint bodies; add a logout/`kid` story (Findings 11 and 14).

### Operational Security

1. Leave `http1_plain_enabled` and `http2_plain_enabled` false on any network that is not a local development socket. Do not publish container port 8080.
2. Run as the dedicated `htxpro` user. Keep `tls_key` and the session-secret file mode `0600` and owned by that user. Do not put `client_secret` in a world-readable YAML if the host has other accounts.
3. Point each static root at a directory the service user cannot write. Do not use the git checkout as a static root.
4. Put authenticated APIs on a different registrable domain from any host that serves user-influenced HTML.
5. Rebuild when `webpki-roots` or rustls ships security fixes. The trust store is compiled in.
6. If a reverse proxy is placed in front, terminate it on localhost and do not trust `X-Forwarded-For`: every limit in this process keys off the socket peer address. The server does not implement PROXY protocol.
7. Keep the systemd restrictions that are already in the unit. Do not "fix" a seccomp denial of `io_uring_setup` by running the container `--privileged`.

## Conclusion

Version 0.7.1 is a serious implementation of a small HTTP/1.1, HTTP/2, and HTTP/3 server. The parsers, the QUIC Retry authenticator, the PKCE state cookie, and the admission limits show deliberate defensive work, and the absence of `unsafe` in the server paths matches that. The issues that matter operationally are the session-key check that will accept the secret printed in the project's own documentation, the Docker config that turns on cleartext and a world-writable demo API, and resource accounting that lets unknown hosts and large QUIC windows crowd out real traffic. Fixing Findings 1, 2, 3, and 5 does not require an architectural change. With those closed, and with rustls 0.23.46 in the lockfile, the residual risk is Low for a single-operator deployment that does not serve untrusted HTML on a sibling name.

**Risk Level:** Medium

**Recommended Actions:** Remediate Findings 1, 2, 3, and 5 before any authenticated or internet-facing deployment. Address Findings 4, 6, and 7 within 30 days. Upgrade rustls on the next release.
