# Security Audit Report for htxpro (Version 0.7.1)

**Project:** htxpro (https://github.com/randop/htxpro)

**Version:** 0.7.1

**Audit Date:** 2026-10-22

**Auditor:** Independent Security Analysis (OpenAI GPT-6)

**Audit Type:** Source Code Security Review (Static)

**Artifact:** `master` branch, source files retrieved on 2026-10-22; commit SHA not independently established

**Report ID:** SA-2026-10-22-002

**AI Model:** OpenAI GPT-6

## Executive Summary

This report reviews htxpro, a Linux-only Rust HTTP server implementing HTTP/1.1, HTTP/2, and HTTP/3 (QUIC), with virtual-host routing, static-site serving, in-process REST controllers, and an optional WorkOS OAuth2 authentication module.

**Overall Assessment:** Medium

The reviewed code includes several positive controls: request/header/body limits and phase timeouts; HTTP/1.1 rejection of duplicate headers and `Transfer-Encoding`; lexical path traversal checks for static content; authenticated OAuth state and PKCE; HMAC-signed session tokens; and bounded static-file reads. The dependency lockfile currently resolves `quiche` 0.30.0 and `rustls` 0.23.45. These are at or beyond the versions identified as fixing the reviewed 2026 advisories for HTTP/3 resource exhaustion and Rustls TLS-handshake message handling respectively.

Two issues merit attention. First, the bundled Docker configuration enables cleartext listeners on all interfaces and configures the example CRUD API without a security module. If this example configuration is copied into a reachable deployment, remote clients can use the API's state-changing routes without authentication, including over cleartext HTTP. Second, static-path validation prevents lexical traversal but follows filesystem symlinks; an untrusted symlink placed in a served root can expose files outside that root. The latter depends on the deployment's file-write trust boundary and is partly mitigated by the project's own operational guidance.

No exploit was executed and the service was not built or live-tested as part of this review. Findings are based on static source/configuration evidence; the deployment finding is conditional on using the bundled example configuration or equivalent settings.

## Findings

### Medium Priority Issues

#### 1. Example Deployment Exposes Unauthenticated Write API on Public Cleartext Listeners

**Severity:** Medium

**Status:** Confirmed for the bundled configuration; deployment impact is conditional

**Evidence:**

- `deploy/config.docker.yaml` binds the main listener to `0.0.0.0:8443`, enables the plain HTTP/1.1 and HTTP/2 listeners, and binds the plain listener to `0.0.0.0:8080` ([configuration lines 2–7](https://github.com/randop/htxpro/blob/master/deploy/config.docker.yaml#L2-L7)). `config.example.yaml` uses the same public binding and protocol defaults ([lines 1–5](https://github.com/randop/htxpro/blob/master/config.example.yaml#L1-L5)).
- The bundled `api.example.test` virtual host maps to `public_api` without a `security` setting, and `public_api` registers `POST`, `PUT`, `PATCH`, and `DELETE` routes for `/v1/items` ([Docker config lines 54–69](https://github.com/randop/htxpro/blob/master/deploy/config.docker.yaml#L54-L69)).
- `SecurityRuntime::guard()` allows requests for virtual hosts without `security` configured ([`src/security/mod.rs`](https://github.com/randop/htxpro/blob/master/src/security/mod.rs#L112-L120)). The item controller checks request-body limits and then processes write operations without an authorization check ([`src/controllers/items.rs`](https://github.com/randop/htxpro/blob/master/src/controllers/items.rs#L24-L42), [write/delete handlers](https://github.com/randop/htxpro/blob/master/src/controllers/items.rs#L59-L124)).

**Description:** The example deployment is externally reachable by default if its published ports are exposed. It enables unencrypted HTTP listeners on all interfaces and includes an unauthenticated CRUD API. A remote client able to reach the service and send a matching `Host`/`:authority` value can read, create, update, or delete items in the sample store. The store is in-memory, and the hostnames are placeholders; the impact is therefore dependent on whether these example routes/configuration are carried into a real deployment. The risk becomes material if the example API is repurposed for application data or the cleartext listener is exposed beyond a trusted network.

**Risk:** Unauthorized changes to API state, deletion or modification of records, and exposure of request/response data to network observers when cleartext HTTP is used. The default configuration may be copied into production without a sufficiently explicit security boundary.

**Recommendation:**

- Make cleartext listeners opt-in or bind them to loopback by default. If HTTP is required for certificate issuance or internal routing, firewall it to trusted peers and terminate/redirect external HTTP at a controlled edge.
- Configure a security module on the API virtual host and verify that authorization is enforced for write routes; otherwise remove the demonstration write routes from the deployable example.
- Add a deployment test that fails or warns when a non-loopback cleartext listener serves a mutating controller without an explicit authorization policy.

### Low Priority Issues

#### 2. Static File Serving Follows Symlinks Outside the Configured Root

**Severity:** Low

**Status:** Confirmed behavior; exploitability depends on who can write the served tree

**Evidence:** `src/static_site.rs` decodes and validates the request path, rejects `.` and `..` segments, and joins the remaining relative path to `site.root` ([lines 18–46](https://github.com/randop/htxpro/blob/master/src/static_site.rs#L18-L46)). `read_bounded_file()` then opens the resulting path directly with `monoio::fs::File::open()` ([lines 86–90](https://github.com/randop/htxpro/blob/master/src/static_site.rs#L86-L90)); it does not enforce that the resolved filesystem target remains below the configured root or reject symlink traversal.

**Description:** The lexical traversal checks prevent ordinary `../` path traversal, but filesystem symlinks are resolved by `File::open`. If an attacker or untrusted publishing workflow can place a symlink inside a served root that points to a readable file outside that root, a request for the symlink path can cause the server to return the external file's contents.

The project architecture documentation already advises that static roots should be publisher-owned and not writable by the server runtime, and that untrusted symlinks should not be placed below a served root ([`ARCHITECTURE.md`](https://github.com/randop/htxpro/blob/master/ARCHITECTURE.md#L29-L32)). This lowers the risk in deployments that follow the guidance, but the file server does not enforce the boundary itself.

**Risk:** Conditional local-file disclosure if untrusted content can introduce symlinks into a served directory and the target file is readable by the server process.

**Recommendation:**

- Enforce containment at file-open time rather than relying only on lexical path checks. On Linux, prefer a directory-relative open strategy with `openat2` restrictions such as `RESOLVE_BENEATH` and, where appropriate, `RESOLVE_NO_SYMLINKS`.
- Ensure deployment/publishing processes cannot place untrusted symlinks under served roots, and keep sensitive files outside directories served by htxpro.
- Add regression tests for symlinks pointing to a parent directory, an absolute path, and another file within an adjacent directory.

#### 3. Container Base Image Tags Are Not Immutable

**Severity:** Low

**Status:** Confirmed build configuration; supply-chain impact is operational

**Evidence:** The Dockerfile uses `FROM rust:bookworm` and `FROM debian:bookworm-slim` rather than immutable image digests ([`Dockerfile` lines 1 and 10](https://github.com/randop/htxpro/blob/master/Dockerfile#L1-L10)). The dependency lockfile is copied into the build context, which is a positive control ([line 5](https://github.com/randop/htxpro/blob/master/Dockerfile#L4-L9)).

**Description:** Moving base-image tags and the package repository state can change the compiler, system libraries, and runtime image used by a future build. This does not establish that the current image is vulnerable, but it reduces build reproducibility and makes it harder to prove exactly which base-image contents produced a release.

**Recommendation:** Pin base images by digest, use a controlled update process to advance those digests, record the Rust toolchain and build provenance, and publish an SBOM for release images.

## Code Quality Security Assessment

### Input Validation and Request Handling

**Rating:** Good, with deployment and filesystem-boundary caveats

- The HTTP/1.1 parser enforces a header-size limit, rejects duplicate headers, rejects `Transfer-Encoding` and `Expect`, and applies request-target validation ([`src/http1_server.rs`](https://github.com/randop/htxpro/blob/master/src/http1_server.rs#L562-L647)).
- The static-file handler percent-decodes paths, rejects backslashes, NUL bytes, and dot segments, and bounds file reads. The remaining symlink issue is described in Finding 2.
- Request-body limits, header limits, connection/stream limits, rate limits, and per-phase timeouts are configurable and applied across the protocol handlers.

### Authentication and Session Handling

**Rating:** Good in the reviewed paths; deployment is configuration-dependent

- The WorkOS authorization flow uses an HMAC-signed state token, state expiry, PKCE S256, and a signed session cookie. Session verification checks token version, module, subject, and expiry (`src/security/mod.rs`).
- Virtual-host authentication is optional by configuration. A host without a configured security module is intentionally allowed through the security guard; mutating controller routes therefore need explicit protection when used for real application data (Finding 1).

### Dependency Analysis

- **quiche 0.30.0** is recorded in `Cargo.lock`. Upstream advisory [GHSA-4fgf-9xrr-88gf](https://github.com/cloudflare/quiche/security/advisories/GHSA-4fgf-9xrr-88gf) describes remotely triggerable HTTP/3/QPACK memory resource exhaustion and identifies 0.29.3 as the first fixed version. The locked 0.30.0 is newer than that fix.
- **rustls 0.23.45** is recorded in `Cargo.lock`. Upstream advisory [GHSA-2mjx-qc3c-rqvc](https://github.com/rustls/rustls/security/advisories/GHSA-2mjx-qc3c-rqvc) identifies versions before 0.23.45 as affected; the locked version is the patched version.
- The Docker build copies `Cargo.lock`, a positive measure for keeping dependency resolution consistent. Base-image digest pinning and SBOM/provenance generation remain recommended (Finding 3).
- No local `cargo audit` or equivalent scan was run. The checks above cover selected relevant advisories, not an exhaustive declaration that every dependency is free of known issues.

## Recommendations

### Immediate Actions

1. Do not deploy the sample API configuration as-is on an untrusted network. Disable or restrict the cleartext listener and protect or remove the unauthenticated write routes.
2. Enforce filesystem-root containment for static files, including symlink handling, and keep served roots writable only by trusted publishing processes.

### Medium-Term Improvements

1. Add a configuration validation warning/error when an externally bound cleartext listener exposes mutating routes without an explicit authentication/authorization policy.
2. Add symlink-containment regression tests and security-focused tests for each HTTP protocol's equivalent request-routing behavior.
3. Pin Docker base-image digests and emit an SBOM and build provenance for releases.
4. Run `cargo test`, a Rust dependency audit, and dynamic tests in CI; include HTTP/3 malformed-frame tests and static-file boundary tests.

### Operational Security

1. Expose only required ports. If port 8080 is needed, restrict it to a trusted network or an internal reverse proxy.
2. Keep TLS private keys in mounted secrets with restrictive ownership and permissions.
3. Ensure static roots contain only trusted published content, with no attacker-controlled symlinks or sensitive files.
4. Re-check dependency advisories when updating the lockfile and before each release.

## Conclusion

The reviewed server code contains useful protocol, resource, authentication, and input-validation controls. The main actionable concern is the example deployment's public, cleartext listener combined with a virtual host that exposes unauthenticated mutating API routes. Static-file serving also relies on a deployment trust assumption around symlinks rather than enforcing filesystem containment in the open operation. Fixing these issues and strengthening release-image provenance would improve the security baseline before using the example deployment for real application data.
