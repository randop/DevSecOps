# Security Audit Report for htxpro Web Server (Version 0.7.1)

**Project:** htxpro (https://github.com/randop/htxpro)

**Version:** 0.7.1

**Audit Date:** 2026-10-22

**Auditor:** Independent Security Analysis (Claude)

**Audit Type:** Source Code Security Review (Static) with Dependency Advisory Matching

**Artifact:** `master` branch, tree `d9d574a` (commit dated 2026-10-22T06:19:28Z, "feat: cli option to print the package name and version and exit")

**Report ID:** SA-2026-10-22-003

**AI Model:** Anthropic Claude Sonnet 5.5

## Executive Summary

This report presents an independent security audit of htxpro (v0.7.1), a Linux-only web server written in Rust on the `monoio` io_uring runtime. It serves HTTP/1.1, HTTP/2 (TLS and cleartext h2c) and HTTP/3 (QUIC via `quiche`/BoringSSL), with host-based static sites, in-process REST controllers, and optional WorkOS (OAuth 2.0 / PKCE) authentication with stateless signed cookies. All 14 Rust source files (7,381 lines), the build, container, systemd and configuration artifacts, the changelog and architecture document, and the full git history (6 commits) were reviewed. The lockfile (`Cargo.lock`) was matched against the RustSec advisory database (commit `7ad117a`, 2026-10-23).

**Overall Assessment:** The codebase shows strong security fundamentals for a project of this age: a deliberately strict HTTP/1.1 parser (rejects duplicate headers, `Transfer-Encoding`, ambiguous `Content-Length`, obs-fold and `Expect`), robust path-traversal defenses in static serving, constant-time HMAC verification, PKCE plus signed state in the OAuth flow, a strict open-redirect guard, stateless QUIC Retry on every new connection with 0-RTT disabled, fail-closed configuration validation, `panic = "abort"` with essentially no reachable panic sites, no `unsafe` request-handling code, and a non-root container user. No Critical or High severity issue (remote code execution, authentication bypass, memory corruption, request smuggling) was found.

The audit did identify **eight Medium issues**: the shipped container configuration exposes an unauthenticated mutating API and metrics endpoint, a documented placeholder `session_secret` passes validation, two algorithmic-complexity CPU amplification paths on the single event-loop thread, memory amplification in static serving and the demo item store, a vendored HTTP/2 stack lacking upstream reset-flood mitigations, patchable advisories in the outbound TLS client, and cookie/CSRF protections that assume sibling subdomains are trusted. Eight Low issues cover operational and defense-in-depth gaps.

**Scope limits (important):** This was a static review. The Rust toolchain could not be installed in the audit environment, so the project was **not compiled, its 41 unit tests were not executed, and no fuzzing or load testing was performed**. Findings are marked "Confirmed (code inspection)" where the behavior follows directly from the code, or "Likely" where reproduction would be needed. Logic simulations were limited to ports of the host-matching and secret-length checks.

**Risk Level:** Medium

- Dependency assessment: all 16 resolved security-relevant crates mapped against RustSec advisories; applicability of each hit triaged by feature flags and call path. The vendored `h2` fork inside `monoio-http 0.3.12` was downloaded from crates.io and compared against upstream `h2` advisories.
- Logic simulation of host-pattern matching and secret-length validation.
- Evaluation against OWASP Top 10, RFC 9110/9112 (HTTP semantics and HTTP/1.1 framing), RFC 9113 (HTTP/2), RFC 9114/9000 (HTTP/3, QUIC), RFC 7636 (PKCE) and OAuth 2.0 security best practice.

## Findings

### High Priority Issues

None identified.

### Medium Priority Issues

#### 1. Shipped Container Configuration Exposes Unauthenticated API, Metrics and Plaintext Listeners

**Severity:** Medium

**Status:** Confirmed (code inspection) — requires attention

**Description:** The `Dockerfile` copies `deploy/config.docker.yaml` to `/app/config.yaml` and runs the server with it by default (`Dockerfile` line 20, `ENTRYPOINT`). That configuration contains **no `security` section** (zero references) and enables:

- `http1_plain_enabled: true` and `http2_plain_enabled: true` on `0.0.0.0:8080` (cleartext, exposed via `EXPOSE 8080/tcp`);
- on host `api.example.test`: `GET /metrics`, `GET /status`, `POST /echo`, and the full `/v1/items` create/read/update/delete set (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) with no authentication.

`default_host: "example.test"` plus the fallback in `resolve_host` means requests with an unrecognized `Host` header are served the default site, but the API vhost is selected whenever `Host: api.example.test` is sent, which any client can do. The `/metrics` handler discloses internal state (tracked client IPs, in-flight counters, limits), and the item store is a single global, unauthenticated, 16 MiB writable store.

**Risk:** Operators who run the published image or copy the Docker config into production expose unauthenticated state-changing endpoints, internal telemetry, and cleartext listeners. Together with Finding 5, the item store gives anonymous clients a writable memory sink.

**Recommendation:**

- Ship the Docker image with a minimal, locked-down default (static sites only, TLS only); move demo controllers into a clearly named `config.demo.yaml`.
- Require `security` (or an explicit `allow_unauthenticated: true`) for controllers with mutating routes, and for `metrics`/`status`, or bind them to an admin-only listener.
- Fail startup if a mutating controller route is reachable on a cleartext listener without authentication.

#### 2. Documented Placeholder `session_secret` Passes Validation

**Severity:** Medium

**Status:** Confirmed (simulation)

**Description:** Config validation only checks `session_secret.len() >= 32` (bytes). The example in `config.example.yaml` line 136 and `ARCHITECTURE.md` line 180 is `"replace-with-at-least-32-random-bytes"`, which is **37 bytes and therefore passes**. There is no entropy check, no rejection of known placeholders, and the secret must be placed literally in the YAML file. An operator who copies the documented snippet and edits only the WorkOS credentials starts a server whose HMAC key is public. Because session and OAuth-state cookies are stateless HMAC tokens, anyone who knows the key can forge a valid session for any `sub`, `email`, and module name, which is a **complete authentication bypass** for protected virtual hosts.

**Risk:** Authentication bypass through a copy-paste misconfiguration; the failure is silent.

**Recommendation:**

- Reject known placeholder strings (and low-entropy values) at startup; require a base64/hex-encoded value that decodes to at least 32 random bytes.
- Support loading secrets from a file path or environment variable (`session_secret_file`) so they are not stored in the main config.
- Remove literal usable values from docs; use `<generate with: openssl rand -base64 48>`.

#### 3. QUIC Event Loop Performs O(sessions) Work and Allocation per Received Datagram

**Severity:** Medium

**Status:** Confirmed (code inspection); impact "Likely" (not load-tested)

**Description:** In `src/http3_server.rs`, `pump_all()` runs after **every** `ServerEvent::Datagram` (line 1054), after every response event, and on every 5 ms timer tick. `pump_all()` (line 1762) iterates all sessions and, for each session, allocates a zeroed 1,350-byte `Vec` per loop iteration, including the iteration that returns `Done`, before calling `conn.send()`. With up to 512 QUIC connections (`max_quic_connections`), each inbound datagram, including datagrams that are immediately discarded, costs roughly 512 allocations, 690 KB of zero-fill, and 512 `send` calls. All of this runs on the single event-loop thread that also handles TCP, TLS handshakes and request dispatch.

An attacker needs only to complete the Retry handshake for enough connections (per-IP limit 64, so about 8 source addresses) to inflate the session count, then send junk or small datagrams at a high rate. Throughput collapses for every protocol; kernel UDP receive buffers overflow and legitimate packets are dropped.

**Risk:** Low-bandwidth CPU-exhaustion denial of service affecting all listeners.

**Recommendation:**

- Pump only the session that received the datagram (or sessions with pending output), tracked via a dirty set or a `conn.timeout()`-driven timer wheel.
- Reuse a single send buffer instead of allocating per iteration.
- Rate-limit datagrams per source address before they reach the session table.

#### 4. Per-IP Admission Table Scanned on Every Request/Connection; IPv6 Not Aggregated

**Severity:** Medium

**Status:** Confirmed (code inspection)

**Description:** `acquire_request()`, `acquire_tcp_connection()` and `acquire_quic_connection()` each call `state.clients.retain(...)` (lines 331, 583, 643) over the entire per-IP table before admitting the caller. The table can hold up to `max_tracked_client_ips` = 65,536 entries, so each admission is up to 65,536 closure evaluations on the event-loop thread; when full, an additional full scan finds the oldest inactive entry (lines 340, 592). Entries are keyed by exact `IpAddr`, so an attacker holding an IPv6 /64 (2^64 addresses; typically a single residential or VPS allocation) can:

- fill the table cheaply, making every subsequent admission by anyone pay the full scan cost;
- bypass the per-IP token bucket (20 rps, burst 40) and per-IP connection caps (32 TCP / 64 QUIC) simply by rotating source addresses, since each new address receives a fresh budget.

**Risk:** CPU amplification and effective neutralization of per-IP rate limiting for IPv6 attackers. Throttling for IPv4 attackers remains effective.

**Recommendation:**

- Key IPv6 clients by /64 (or a configurable prefix) and IPv4 by /32.
- Replace the full `retain` with amortized expiry (a time-ordered queue or periodic sweep every N seconds).
- Keep the global limits (`global_requests_per_second`, connection caps) as the backstop and document that per-IP limits assume direct client exposure (see Finding 15 for proxy/NAT behavior).

#### 5. Whole-Object Buffering Amplifies Memory Use in Static Serving and the Item Store

**Severity:** Medium

**Status:** Confirmed (code inspection); magnitude "Likely"

**Description:**

- Static files are read fully into memory (up to `max_static_file_bytes`, default 16 MiB, configurable to 32 MiB) and the HTTP/1.1 writer then copies the body again (`bytes.to_vec()` per write) before sending. A single response can therefore pin about 2x the file size. `max_inflight_static` defaults to 16, and `max_inflight_requests_per_ip` (32) is larger than it, so one client can occupy the entire static budget with slow-reading connections (write deadline 10 s), pinning roughly 16 x 16 MiB x 2 = 512 MiB. `HEAD` requests also read the whole file.
- The demo item store limits stored size by serialized `body_bytes` (16 MiB cap), but `serde_json::Value` is far larger in memory than its JSON text (for example an array of single-digit numbers, `[1,1,1,...]`, costs about 2 bytes of input but roughly 32 bytes per element in memory, an estimated 16x amplification). Handlers also `request.clone()` bodies and clone stored values for responses.

**Risk:** Memory exhaustion / OOM kill (and `panic = "abort"` on allocation failure) from a small number of connections.

**Recommendation:**

- Stream static files in fixed-size chunks (or use `sendfile`/splice via io_uring) instead of buffering; avoid the second copy by writing from the owned buffer.
- Charge the item store by estimated in-memory size, not input length; cap element counts and nesting depth.
- Use a cheaper `HEAD` path that stats the file rather than reading it.

#### 6. Vendored HTTP/2 Implementation Lacks Upstream Reset-Flood Mitigation

**Severity:** Medium

**Status:** Likely — not dynamically reproduced

**Description:** HTTP/2 is provided by the `h2` implementation vendored inside `monoio-http 0.3.12` (a fork of the upstream `h2` crate). Comparing the fork's source against upstream advisories:

- It **does** contain the CONTINUATION-flood size check (the behavior fixed upstream as RUSTSEC-2024-0332 / CVE-2024-27316) and a limit on locally reset streams.
- It contains **no** `max_local_error_reset_streams` / pending-accept-reset accounting (searched the whole crate source: no matches). That counter is the upstream mitigation for RUSTSEC-2024-0003 (resource exhaustion by repeatedly provoking stream resets, fixed in `h2` 0.3.24 / 0.4.2).
- Applicability of the newer upstream advisory RUSTSEC-2026-0258 (empty-DATA-frame handling, fixed upstream in `h2` 0.4.16) could not be established; no empty-frame accounting was found in the fork's receive path.

htxpro's own rate limiter and in-flight caps are applied only **after** request headers are accepted from the HTTP/2 layer, so work done inside the library for malformed or reset streams is not covered by them.

**Risk:** HTTP/2 denial of service (CPU/memory) from reset-heavy clients, on a server where one thread serves all protocols.

**Recommendation:**

- Confirm with a reset-flood test (for example `h2load`/custom client sending invalid frames and RST_STREAM) against a staging build.
- Backport the upstream `max_local_error_reset_streams` and empty-frame protections into the vendored code, or move to a maintained `h2` build.
- Add an HTTP/2 connection-level budget (frames per second, resets per connection) that closes abusive connections with `GOAWAY`.

#### 7. Patchable Advisories in the Outbound TLS Client Dependencies

**Severity:** Medium

**Status:** Confirmed (lockfile match); exploitability requires a network-position attacker

**Description:** The WorkOS token exchange uses an in-process TLS client built on `rustls 0.23.45` and `rustls-webpki 0.103.15`, validating `api.workos.com` with `webpki-roots`. Matching `Cargo.lock` against the RustSec database:

| Advisory | Crate / version in use | Patched in | Relevance to htxpro |
| --- | --- | --- | --- |
| RUSTSEC-2026-0382 | `rustls-webpki 0.103.15` | `>= 0.103.16` | Applies: certificate verification may accept distrusted intermediates; affects the outbound client that transmits the OAuth `code`, PKCE verifier and `client_secret`. |
| RUSTSEC-2026-0349 | `rustls 0.23.45` | `>= 0.23.46` | Applies to the client role: an unauthenticated ServerHello can downgrade later connections to classical key exchange. Low practical impact for a single fixed endpoint. |
| RUSTSEC-2026-0346 | `rustls 0.23.45` | `>= 0.23.46` | Not applicable: requires a custom `ClientSessionStore` combined with `Debug` logging. |
| RUSTSEC-2026-0347 | `rustls 0.23.45` | `>= 0.23.46` | Not applicable: Encrypted Client Hello not used. |
| RUSTSEC-2026-0348 | `rustls 0.23.45` | `>= 0.23.46` | Not applicable: `brotli` certificate-compression feature not enabled. |

An attacker who can intercept traffic to the token endpoint and present a chain that exploits the validation weakness could capture the authorization code and client secret. This is a narrow precondition, but fixes are available through a plain `cargo update`.

**Risk:** Exposure of OAuth client credentials/authorization codes under a network-adversary scenario.

**Recommendation:**

- Run `cargo update -p rustls -p rustls-webpki` (targets `rustls >= 0.23.46`, `rustls-webpki >= 0.103.16`) and rebuild; commit the new `Cargo.lock`.
- Add `cargo audit` / `cargo deny` to CI so advisories fail the build (see Finding 16).

#### 8. Cookie and CSRF Protections Assume Sibling Subdomains Are Trusted

**Severity:** Medium

**Status:** Confirmed (code inspection); exploitability depends on deployment (untrusted content on sibling subdomains)

**Description:** Cookie-authenticated routes have no CSRF defense beyond `SameSite=Lax` (`src/security/mod.rs` line 310). `SameSite` is a **site** (registrable domain) boundary, not an origin boundary, so requests from `evil.tenant.example.test` to `api.example.test` are same-site and carry the cookie. The server performs no `Origin`/`Sec-Fetch-Site` check and the JSON handlers do not require `Content-Type: application/json`, so a cross-origin `text/plain` "simple request" avoids CORS preflight and still reaches mutating handlers. The project's own reference design serves `*.tenant.example.test` as multi-tenant content next to `api.example.test`.

Related weaknesses at the same trust boundary:

- Cookie names have no `__Host-` prefix, so a sibling subdomain can set a `Domain=example.test` cookie that shadows the real one. `cookie_value()` returns the first match, enabling cookie tossing / session fixation (forcing a victim into an attacker's valid session) and tampering with the OAuth state cookie.
- Session tokens are not bound to a host; a token issued for one vhost using module `X` is valid on any other vhost using module `X`.

**Risk:** State-changing requests forged from untrusted sibling subdomains; login CSRF / session fixation.

**Recommendation:**

- Enforce `Origin` (or `Sec-Fetch-Site: same-origin`) on non-safe methods for authenticated routes; require `application/json` for JSON bodies.
- Use `__Host-` prefixed cookie names (requires `Secure`, `Path=/`, no `Domain`), and bind session claims to the serving host.
- Document that untrusted tenant content must not share a registrable domain with authenticated applications.

### Low Priority Issues

#### 9. Dotfiles and Symlink Targets Are Served from Static Roots

**Severity:** Low

**Status:** Confirmed (code inspection)

**Description:** `src/static_site.rs` rejects `..`, backslashes, NUL and malformed percent-encoding (traversal protection is sound), but has no filter for dot-prefixed segments (only line 25's `\\`/NUL check; no `starts_with('.')` rule), so `/.env`, `/.git/config`, `/.htpasswd` are served if present in a site root. Symlinks are followed and canonicalization is applied only to the root at startup, so a link inside a root can point outside it (documented behavior, but a common footgun). The shipped image copies only `public/` and `sites/`, which limits current exposure.

**Recommendation:** Deny dot-prefixed path segments by default (allow `.well-known` explicitly); open files with `O_NOFOLLOW`/`openat2(RESOLVE_BENEATH)` or re-verify the canonical path remains under the root.

#### 10. No Security Response Headers, HSTS or HTTP-to-HTTPS Redirect

**Severity:** Low

**Status:** Confirmed

**Description:** Responses set `x-content-type-options: nosniff` and a fixed `server: htxpro` (no version disclosure), but there is no `Strict-Transport-Security`, `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy` or `Permissions-Policy`, and the configuration has no mechanism to add custom response headers per vhost. When the cleartext listener is enabled there is no redirect to HTTPS. Static `text/html` is served without an explicit `charset`.

**Recommendation:** Add per-vhost `headers:` configuration with safe defaults (HSTS on TLS responses, `Referrer-Policy`, `X-Frame-Options`), an optional `redirect_to_https`, and `charset=utf-8` for text types.

#### 11. Request Validation Is Inconsistent Across Protocols

**Severity:** Low

**Status:** Confirmed (code inspection)

**Description:** The HTTP/1.1 parser enforces origin-form paths, rejects `//`, `#`, backslashes, control characters, duplicate headers and obs-fold. HTTP/2 enforces the path rules but accepts the unusual `:authority` forms normalized only by `rsplit_once(':')`. HTTP/3 builds requests from pseudo-headers with defaults (`:path` falls back to `/`, empty `:method` allowed), converts header values with lossy UTF-8, and concatenates duplicate headers (including `cookie` and `content-length`, which is then unparseable and silently ignored for the early size check). Consequences are currently limited because later layers (static path decoding, `safe_return_to`, route matching) re-validate, but the same request can be accepted on one protocol and rejected on another, which weakens WAF/proxy parity and invites future bugs. Method comparison is also case-inconsistent (guard and controllers case-insensitive, static serving case-sensitive).

**Recommendation:** Centralize request normalization/validation in one function used by all three protocols; reject malformed pseudo-headers per RFC 9113/9114.

#### 12. Session and OAuth State Design Limitations

**Severity:** Low

**Status:** Confirmed (code inspection)

**Description:**

- **No revocation:** sessions are stateless HMAC tokens with a fixed expiry; there is no logout invalidation, `iat`, or key identifier, so secret rotation logs everyone out and a stolen cookie is valid until expiry.
- **No domain separation** between state and session tokens: both are `payload.HMAC` under the same key with no `typ` claim. Verified that confusion is **not currently exploitable** because `SessionClaims` requires `sub` and `StateClaims` requires `state`/`verifier`/`return_to`, but this is incidental and fragile under future changes.
- **State is replayable:** the signed state cookie is cleared by the response but is not single-use server-side. A client can retain it and call `/callback?code=x&state=...` repeatedly, causing the server to make outbound token-exchange requests with the operator's `client_id`/`client_secret` (bounded only by the per-IP limiter, which Finding 4 shows is weak for IPv6). This could trigger provider-side rate limiting or lockout.
- Error responses from the token endpoint (first 512 bytes) and attacker-supplied `error`/`error_description` query values are written to logs at `warn` level.
- The callback runs under `request_process_ms` (5 s default) while the token-exchange timeout defaults to 10 s, so slow provider responses fail as 504 before the client timeout applies.

**Recommendation:** Add a `typ` claim or derive separate HMAC subkeys per token type (HKDF); add a short in-memory replay cache for state nonces; add `kid` support for key rotation; align timeouts.

#### 13. Certificate Lifecycle and SNI Semantics

**Severity:** Low

**Status:** Confirmed (code inspection)

**Description:** TLS certificates and keys are loaded once at startup. The only signal handlers are SIGINT/SIGTERM; there is no reload (SIGHUP) and no expiry check or warning, so short-lived certificates require a full restart (dropping all connections). Private keys remain in memory unzeroized for the process lifetime, and key file permissions are not checked. An unknown SNI receives the default (first) certificate, disclosing its names. Wildcard handling differs: TLS SNI wildcards match one label, but virtual-host wildcards (`host_matches`) match multiple labels. Simulation: `*.tenant.example.test` matches `a.b.tenant.example.test` and `evil.tenant.example.test.tenant.example.test`.

**Recommendation:** Implement hot reload via an `ArcSwap`-style resolver on SIGHUP; log a warning when certificates expire within 14 days; warn on group/world-readable key files; align wildcard semantics.

#### 14. io_uring Is Mandatory and Service Hardening Is Incomplete

**Severity:** Low

**Status:** Confirmed (design / configuration)

**Description:** The runtime is built exclusively with `IoUringDriver` and fails if io_uring setup is blocked (`src/main.rs` line 36; systemd unit comments). io_uring has had a long history of kernel vulnerabilities, and many hardened container and sandbox profiles disable it, so deployments must weaken seccomp to run the server. The shipped systemd unit has solid basics (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `MemoryDenyWriteExecute`, `RestrictAddressFamilies`, non-root user) but lacks `CapabilityBoundingSet=` (ports are unprivileged, so all capabilities can be dropped), `PrivateDevices`, `ProtectKernelTunables/Modules/Logs`, `ProtectControlGroups`, `RestrictNamespaces`, `SystemCallFilter` (an allow-list that still permits io_uring), `UMask`, and `LimitNOFILE`. The container has no `HEALTHCHECK`.

**Recommendation:** Add the missing unit directives; document the minimum kernel version and the sysctl `kernel.io_uring_disabled` implications; consider an epoll fallback driver for restricted environments; add a container `HEALTHCHECK` against `/healthz`.

#### 15. Resource-Limit and Logging Design

**Severity:** Low

**Status:** Confirmed (code inspection)

**Description:**

- The global TCP connection cap is 256 with a per-IP cap of 32, so as few as 8 source addresses (one for an IPv6 /64 attacker, by Finding 4) can hold every TCP slot with slow or idle connections and starve legitimate users. Request-level rate limiting happens only after headers are parsed.
- All protocols share one event-loop thread (`RuntimeBuilder` built once, `block_on` once). CPU-bound synchronous handlers (JSON parse of 1 MiB bodies, serialization of up to 16 MiB of items, TLS handshakes) cannot be preempted by `request_process_ms`, which only fires at await points.
- Per-IP limits key on the peer address; behind a CDN, NAT or reverse proxy, all clients share one budget. There is no trusted-proxy / PROXY protocol support to recover the client address.
- Connection and timeout events are logged at `info`/`warn` per occurrence with attacker-influenced fields and no log rate limiting, enabling log flooding.

**Recommendation:** Raise defaults or make caps adaptive; add pre-handshake connection rate limiting; offload CPU-heavy handlers; add trusted-proxy support; sample or rate-limit warn-level logs.

#### 16. Supply-Chain, Build Hygiene and Documentation Drift

**Severity:** Low

**Status:** Confirmed

**Description:**

- **No CI exists** (`.github/` absent) although `ARCHITECTURE.md` states a CI workflow runs formatting, compilation, tests and Clippy. No `cargo audit`/`cargo deny`, no `SECURITY.md` or disclosure policy.
- Docker build uses floating tags (`rust:bookworm`, `debian:bookworm-slim`, no digests) and `cargo build --release` without `--locked`.
- All 6 commits are unsigned and from a single maintainer; release binaries are not signed or attested.
- Documentation inaccuracies: `ARCHITECTURE.md` states there is no Tokio dependency, but `tokio 1.53.2` and `tokio-util` are in the lockfile (via `monoio-compat` and `monoio-codec`); the test count claimed (34) differs from the 41 `#[test]` functions present.
- Legacy and unmaintained crates in the graph: `rustls 0.21.12` / `rustls-webpki 0.101.7` / `sct` (via `monoio-rustls 0.3.0` from `monoio-http`) are on end-of-life lines; the lockfile versions match RUSTSEC-2026-0098, -0099 and -0104 for `rustls-webpki`, with no patched release on the 0.101 line. These appear unreachable at runtime, since htxpro uses `monoio-rustls 0.4.0` directly, but the dependency graph should be confirmed with `cargo tree -i rustls@0.21.12`. `rustls-pemfile 2.2.0` (direct) and `fxhash 0.2.1` (via `monoio`) are flagged unmaintained.

**Recommendation:** Add CI (fmt, clippy `-D warnings`, test, `cargo audit`, `cargo deny`, `--locked`); pin base images by digest; publish `SECURITY.md`; sign tags/releases; replace `rustls-pemfile` with `rustls-pki-types` PEM parsing; update the docs.

### Informational

#### 17. Positive Security Practices Observed

- Strict HTTP/1.1 framing (single `Content-Length`, no `Transfer-Encoding`, no obs-fold, no `Expect`), bounded header/body sizes, and absolute header/body/response deadlines (slow-loris resistant).
- Static path handling: percent-decoding then segment validation, `%2F`/backslash/NUL rejection, canonical root.
- Authentication: HMAC-SHA256 with constant-time verification, PKCE (S256) plus signed state, `HttpOnly; SameSite=Lax; Secure` (default) cookies, strict `safe_return_to` open-redirect guard, `Cache-Control: no-store` on login redirects, redirect URI host validated against the vhost at startup, plain-HTTP token endpoints permitted only for loopback.
- QUIC: stateless Retry for every new connection with per-process random key and 10 s token lifetime, 0-RTT disabled, active migration disabled, bounded stream and flow-control limits.
- Fail-closed configuration validation (secret length, URL schemes, host patterns, route patterns, header-value sanity, certificate/key consistency).
- Only three non-test panic sites (mutex locks) in 7,381 lines; no `unsafe` in request paths; secrets are excluded from version control (`config.yaml` in `.gitignore`); no secrets found in history; container runs as non-root UID 10001.
- Project has 41 unit tests, including parser and security-module tests (not executed in this audit).

## Code Quality Security Assessment

#### Input Validation

**Rating:** Good (with exceptions)

- HTTP/1.1 request-line, header and framing validation is strict and well tested; path and percent-decoding handling in static serving is careful; route matching compares decoded segments and rejects encoded separators; JSON bodies are size-limited.
- **Weaknesses:** inconsistent validation across protocols (Finding 11), dotfiles served (Finding 9), placeholder secret accepted (Finding 2), no CSRF/Origin enforcement (Finding 8).

#### Memory Safety

**Rating:** Good

- Safe Rust throughout request handling; arithmetic on attacker-supplied lengths uses checked operations; the only native code is BoringSSL/`quiche` and `ring` via well-known crates.
- **Weaknesses:** logical memory exhaustion (Finding 5) rather than memory corruption; `panic = "abort"` means any future reachable panic terminates the whole single-threaded server.

#### Cryptographic Implementation

**Rating:** Good

- No home-grown cryptography: `ring` HMAC with constant-time compare, `rustls` (TLS 1.2/1.3, safe default suites, no early data) for TCP, BoringSSL TLS 1.3 for QUIC, PKCE S256, 256-bit random state/verifier.
- **Weaknesses:** no domain separation or key rotation for signed tokens (Finding 12), no certificate hot reload or expiry monitoring (Finding 13), patchable outbound-client advisories (Finding 7).

## Dependency Analysis

### Method

`Cargo.lock` (resolved crates) was matched against the RustSec advisory database (commit `7ad117a`, 2026-10-23), restricted to Linux-affecting, non-withdrawn advisories, then triaged manually by feature flags and call path.

### Results

- **rustls 0.23.45 / rustls-webpki 0.103.15 (direct path):** RUSTSEC-2026-0382 and RUSTSEC-2026-0349 apply to the outbound client; patched releases exist (Finding 7). RUSTSEC-2026-0346, -0347 and -0348 do not apply to this configuration.
- **rustls 0.21.12 / rustls-webpki 0.101.7 / sct 0.7.1 (transitive via `monoio-http`):** end-of-life lines matching RUSTSEC-2026-0098, -0099, -0104 and -0382 with no fix available on that line; believed unreachable at runtime (Finding 16; verify with `cargo tree`).
- **Vendored `h2` in `monoio-http 0.3.12`:** not tracked by RustSec under its own name; comparison to upstream advisories shows missing reset-flood mitigation (Finding 6).
- **quiche 0.30.0 / boring 5.3.0 / boring-sys 5.3.0, ring 0.17.14, http 1.5.0, bytes 1.12.1, serde_json 1.0.151, tracing-subscriber 0.3.23, x509-parser 0.18.1, yaml_serde 0.10.7, libyaml-rs 0.3.0, signal-hook 0.3.18:** no matching advisories at the time of audit.
- **Unmaintained:** `rustls-pemfile 2.2.0`, `fxhash 0.2.1`.
- **Tokio** is present transitively despite documentation to the contrary (Finding 16).

### Build Hardening

- Release profile: thin LTO, `codegen-units = 1`, `strip = "symbols"`, `panic = "abort"`. Rust defaults provide stack protection, PIE and RELRO on Linux targets; BoringSSL is built from the pinned `boring-sys` crate (requires cmake/clang in the build image).
- No `--locked`, no digest-pinned base images, no CI security jobs (Finding 16).

## Compliance Assessment

### OWASP Top 10 Coverage

- **Broken Access Control:** Per-vhost opt-in authentication; shipped Docker config exposes unauthenticated mutating routes (Finding 1); no per-user isolation in the item store; no CSRF defense (Finding 8).
- **Cryptographic Failures:** Sound primitives; placeholder secret acceptance (Finding 2); no HSTS (Finding 10); certificate lifecycle gaps (Finding 13).
- **Injection:** Strong. No shell/SQL sinks; JSON serialization via `serde_json`; response header values validated; logs are structured JSON.
- **Insecure Design:** Stateless sessions without revocation (Finding 12); single-thread architecture sensitive to CPU amplification (Findings 3, 4, 15).
- **Security Misconfiguration:** Demo configuration as image default (Finding 1); incomplete service hardening (Finding 14); no security headers (Finding 10).
- **Vulnerable and Outdated Components:** Patchable advisories and EOL TLS stack in graph (Findings 7, 16); vendored `h2` fork (Finding 6).
- **Identification and Authentication Failures:** PKCE/state/HMAC done correctly; secret-strength validation weak (Finding 2); fixation via cookie tossing (Finding 8).
- **Software and Data Integrity Failures:** Unsigned commits/releases, no CI, floating image tags (Finding 16).
- **Security Logging and Monitoring Failures:** Structured logging present; log flooding and no alerting hooks (Finding 15).
- **SSRF:** Not applicable; outbound destinations come only from validated operator configuration.

### Protocol-Specific Security

- **HTTP/1.1 (RFC 9112):** Request-smuggling-resistant framing; keep-alive deadlines; no pipelining abuse paths found.
- **HTTP/2 (RFC 9113):** Concurrency limits set; reset-flood mitigation incomplete in the vendored implementation (Finding 6).
- **HTTP/3 / QUIC (RFC 9114, 9000):** Retry, version negotiation, and anti-amplification handled; CPU amplification in the packet pump (Finding 3).
- **OAuth 2.0 / PKCE (RFC 7636, BCP 212):** Compliant flow with exact redirect URI binding; state replay and fixation hardening recommended (Findings 8, 12).

## Recommendations

### Immediate Actions (High Priority)

1. Ship a locked-down default container configuration; require authentication or explicit opt-out for mutating and metrics routes (Finding 1).
2. Reject placeholder/low-entropy `session_secret` values; support secret files (Finding 2).
3. Update `rustls`/`rustls-webpki` and rebuild (Finding 7).
4. Fix the O(sessions)-per-datagram pump and per-session allocations (Finding 3).
5. Replace per-request `retain` scans with amortized expiry and aggregate IPv6 by /64 (Finding 4).

### Medium-term Improvements

1. Stream static files; account the item store by in-memory size (Finding 5).
2. Test and patch HTTP/2 reset-flood handling in the vendored `h2` (Finding 6).
3. Add `Origin`/`Sec-Fetch-Site` checks, `__Host-` cookies and host-bound sessions (Finding 8).
4. Deny dotfiles and symlink escapes by default; add per-vhost response headers, HSTS and HTTPS redirect (Findings 9, 10).
5. Centralize request validation across protocols (Finding 11).
6. Add token-type separation, state replay protection and key rotation (Finding 12).
7. Add certificate hot reload with expiry warnings (Finding 13).
8. Add CI (`fmt`, `clippy -D warnings`, tests, `cargo audit`, `cargo deny`, `--locked`), pin images by digest, publish `SECURITY.md` (Finding 16).
9. Add regression tests: placeholder secret rejection, wildcard host edge cases, dotfile access, cross-protocol path parity, reset-flood behavior.

### Operational Security

1. Do not expose the demo configuration, `/metrics` or `/status` to the internet; restrict them to an admin network.
2. Serve authenticated applications on a registrable domain separate from any untrusted tenant content.
3. Generate `session_secret` with a CSPRNG (for example `openssl rand -base64 48`), store it outside the config repository, and rotate on compromise.
4. Terminate behind or alongside network-level rate limiting if clients arrive via IPv6 or shared NAT; keep UDP/443 reachable only as intended.
5. Apply the missing systemd hardening directives; run containers with a seccomp profile that permits only the required io_uring syscalls.
6. Monitor memory, open connections, and per-protocol latency; alert on certificate expiry and on `warn`-level log volume spikes.

## Conclusion

htxpro v0.7.1 is a carefully engineered server whose security-critical parsing, path handling and OAuth flow are implemented with noticeably more rigor than is typical for a young project, and the absence of Critical or High findings reflects that. The weaknesses are concentrated in three areas: safe-by-default deployment (the demo configuration and the documented secret placeholder), algorithmic and memory amplification on a single event-loop thread (QUIC packet pump, admission-table scans, whole-file buffering), and dependency/supply-chain hygiene (a vendored HTTP/2 fork behind upstream, patchable TLS advisories, no CI). None require architectural change; most are localized fixes. Because the review was static, the DoS-related findings (3, 4, 5, 6) should be confirmed with load and fuzz testing after remediation.

**Risk Level:** Medium

**Recommended Actions:** Remediate Findings 1-4 and 7 within 14 days; address the remaining Medium items within 30 days; schedule Low items within the next release cycle.
