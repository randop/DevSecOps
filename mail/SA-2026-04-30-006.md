## 2. DETAILED FINDINGS

### [MAIL-01] Critical: File Corruption via DMA Pointer Double-Increment
**Location:** `mail/src/dma_file_writer.cpp` (`drain_batch` and `write_physical`)

**Description:**  
The `_pos` member variable tracks the current offset for Direct Memory Access (DMA) writes. It is incremented inside `write_physical` after each successful `dma_write`. However, it is incremented a second time in the caller function `drain_batch` using `s.logical_size`.

**Impact:**  
The file pointer jumps twice the expected distance for every block written. This results in files containing interleaved "holes" (null bytes) and data, effectively corrupting all received emails and session logs. Truncation at the end of the session will also use this corrupted pointer, leading to oversized files.

**Recommendation:**  
Remove the `_pos += s.logical_size;` increment from `drain_batch` and rely solely on the update within `write_physical`.

### [MAIL-02] High: Disk Space Exhaustion via Unbounded Session Logging
**Location:** `mail/src/main.cpp` (SMTP Session Loop)

**Description:**  
The server logs all client input to a session-specific log file. While there is a check against `SMTP_COMMAND_BUFFER_SIZE_LIMIT` (2KB), the implementation merely logs an error and sends an SMTP 552 response. It fails to set `active = false` or break the loop.

**Impact:**  
A malicious client can continue sending data indefinitely after the limit is reached. The server will continue writing this data to the disk. Since a unique log file is created per connection, an attacker can exhaust disk space on the host by opening multiple connections and streaming garbage data.

**Recommendation:**  
Terminate the connection immediately by breaking the `while (active)` loop when `session_state_logfile_pos` exceeds `SMTP_COMMAND_BUFFER_SIZE_LIMIT`.

### [MAIL-03] High: SMTP DATA Termination Logic Flaw
**Location:** `mail/src/main.cpp` (DATA mode handling)

**Description:**  
The server detects the end of the DATA segment (`\r\n.\r\n`) by checking only the last 16 bytes of the total stream received in the `fixed_stream` buffer. If a client sends the termination sequence followed by additional data in the same TCP segment, the termination sequence will be pushed out of the 16-byte window before the check occurs.

**Impact:**  
The server will fail to recognize the end of the email message, continuing to treat subsequent input (which may be new SMTP commands) as message body data. This leads to protocol desynchronization and potential data loss or corruption.

**Recommendation:**  
Search the entire current `buffer_stream` for the `\r\n.\r\n` sequence instead of relying on a small sliding window at the end of the buffer.

### [MAIL-04] Medium: Memory Leak during STARTTLS Upgrade
**Location:** `mail/src/main.cpp` (`smtp_session::upgrade_tls`)

**Description:**  
The code calls `out.release()` on a `std::unique_ptr<output_stream<char>>`. This releases ownership of the pointer without deleting the underlying object or transferring it to a new owner.

**Impact:**  
Every successful STARTTLS negotiation leaks memory. In a long-running server, this will lead to gradual memory exhaustion.

**Recommendation:**  
Properly destroy the old stream or use `std::move` if the intention is to transfer ownership. In Seastar, ensure the stream is closed before destruction if it owns resources.

---

### [MAIL-05] Medium: Out-of-Bounds Access in Domain Loading
**Location:** `mail/src/email_helpers.cpp` (`load_email_domains`)

**Description:**  
The logic for adding a root domain to the domain list contains an off-by-one error:
```cpp
result.count++;
result.domains[result.count] = root_domain;
```
If `result.count` was `1`, it becomes `2`, and the root domain is written to `domains[2]`, skipping `domains[1]`.

**Impact:**  
The `domains` array contains an uninitialized (empty) entry at index `1`. While the SMTP RCPT check iterates through the list, this uninitialized entry could lead to unexpected behavior or logic bypasses if the server logic expects a contiguous list of valid domains.

**Recommendation:**  
Set the value before incrementing: `result.domains[result.count++] = root_domain;`.

---

### [MAIL-06] Medium: Brittle IP Formatting Buffer Management
**Location:** `mail/src/ip_helpers.cpp` (`format_ip`)

**Description:**  
The `format_ip` function writes to a fixed-size buffer `out.ip` (size `INET6_ADDRSTRLEN`) without bounds checking. While current IPv4/IPv6 logic theoretically fits, the lack of `snprintf` or similar safe functions makes the code vulnerable to overflows if the address parsing or compression logic is modified or if `proxy_info_t` contains malformed data.

**Impact:**  
Potential stack-based buffer overflow if address formatting exceeds 45 characters.

**Recommendation:**  
Implement explicit bounds checking or use `std::string` / `std::format_to_n`.

---

### [MAIL-07] Low: Broken SMTP Command Parsing State Machine
**Location:** `mail/src/main.cpp` (Command handling)

**Description:**  
The server attempts to parse SMTP commands from every chunk returned by `session->in.read()`. If a command is not found at the start of a chunk, it immediately defaults to `SMTP_COMMAND::UNKNOWN` and sends a 500 error.

**Impact:**  
The server is incompatible with any client that sends commands in multiple packets (e.g., "E" then "HLO"). It will spam 500 errors for every byte or partial chunk that does not form a complete, recognizable command prefix.

**Recommendation:**  
Buffer incoming data until a CRLF is reached before attempting to identify the command.

## 3. CODE QUALITY & ARCHITECTURAL OBSERVATIONS

1.  **Direct Memory Access (DMA) Alignment:** The `dma_file_writer` correctly uses `std::aligned_alloc`, but the destruction of the buffer uses `std::free`. While often compatible, `std::aligned_alloc` should ideally be paired with platform-specific free functions if required, though `free` is standard for C++17+.
2.  **Lack of Dot-Stuffing Support:** The implementation does not handle the SMTP dot-stuffing requirement (RFC 5321 Section 4.5.2). Lines starting with a dot are not un-stuffed, leading to corrupted message bodies when receiving emails with lines beginning with `.`.
3.  **Redundant Proxy Checks:** In `main.cpp`, there is a redundant nested `if` block for `session_state_proxy_header_read`.
