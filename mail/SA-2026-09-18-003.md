# Security Audit Report for Mail SMTP Server (Version 1.6.2)

**Project:** mail (https://github.com/randop/mail)

**Version:** 1.6.2

**Audit Date:** 2026-09-18

**Auditor:** Independent Security Analysis (Kimi)

**Audit Type:** Source Code Security Review (Static)

**Artifact:** `master` branch, tree `a3b66a7` (as of 2026-09-18)

**Report ID:** SA-2026-09-18-003

**AI Model:** Moonshot AI Kimi K3 Instant

## Executive Summary

This report presents an independent security audit of the Mail SMTP server (v1.6.2), a privacy-first, self-hosted SMTP receiver written in C++23 on the Seastar framework. All 21 source/build/config files were reviewed; security-critical logic (SMTP state machine, email/domain validation, PROXY v2 parsing, TLS upgrade, file I/O, resource limits) was traced line-by-line and key behaviors were verified by simulation.

**Overall Assessment:** The codebase is well-structured and shows strong security fundamentals: strict RFC-oriented email syntax validation, fail-closed X.509 certificate/private-key validation at startup, random UUID-based spool filenames, correct PROXY v2 signature/version/length checks, and careful modern C++ memory handling. However, this audit identified **one remotely triggerable flaw in the recipient-domain validation that partially bypasses the anti-relay protection**, a **config-triggered out-of-bounds write**, and several denial-of-service weaknesses around unbounded growth and limits that are announced but not enforced. These should be addressed before production deployment.

**Risk Level:** Medium

## Methodology

- Manual line-by-line review of all files: `src/main.cpp`, `src/smtp_session.cpp`, `src/email_helpers.cpp`, `src/ip_helpers.cpp`, `src/string_helpers.cpp`, `src/smtp_configuration.cpp`, `src/file_helpers.cpp`, `src/uuid_helpers.cpp`, `src/x509_helpers.cpp`, `src/dma_file_writer.cpp`, all headers, `CMakeLists.txt`, `etc/mail/smtp.conf`, and helper scripts.
- Simulation of suspicious comparison/parsing logic to confirm exploitability (domain matching, array bounds).
- Review of resource limits, timeouts, and concurrency controls.
- Dependency and configuration assessment.
- Evaluation against OWASP Top 10 and RFC 5321 / RFC 3207 (STARTTLS) / RFC 3164 (PROXY v2) security considerations.

## Findings

### High Priority Issues

#### 1. Recipient Domain Validation Accepts Prefix Matches (Anti-Relay Bypass)

**Severity:** High

**Status:** Confirmed — requires attention

**Description:** Local-recipient checks in `handle_connection()` (RCPT handler) use `string_helpers::compare_string_views(presented_domain, configured_domain)`. The comparison loop only iterates to `configured_domain.size()` and returns success when all bytes of the *configured* domain match the *beginning* of the presented domain. It never verifies the presented domain is the same length. Verified by simulation:

- Presented `online.com.evil.com` matches configured `online.com` → **True**
- Presented `online.comx` matches configured `online.com` → **True**
- Presented `online.com.` (trailing dot) matches configured `online.com` → **True**

Any domain that *starts with* a configured domain is accepted as local. An attacker controlling `evil.com` can claim RCPT TO `user@online.com.evil.com` and the server treats it as a local recipient, queueing the message (given the matching-domain RCPT logic in `main.cpp`). This weakens the primary open-relay defense.

**Risk:** Acceptance and spooling of mail for domains the operator does not own; spam/backscatter sink; disk consumption.

**Recommendation:**

- Replace with an exact, length-checked, case-insensitive comparison (`a.size() == b.size()` plus byte-wise `tolower` equality).
- Treat a single trailing dot (FQDN root) as equivalent to the bare domain explicitly, if desired, rather than accidentally.
- Add regression tests for `online.com.evil.com`, `online.comx`, `online.com.`, and mixed-case variants.

#### 2. Out-of-Bounds Write in `split_email_domains()`

**Severity:** High

**Status:** Confirmed — requires attention

**Description:** In `src/email_helpers.cpp`, `split_email_domains()` copies a comma-separated domain list into `email_domains_t::domains`, a fixed `std::array<sstring, MAX_EMAIL_DOMAINS>` (12), with **no bounds check**:

```cpp
for (auto &x : parts) {
    result.domains[result.count] = x;
    result.count++;
}
```

The input string comes from `smtp_config->all_email_domains()`, which is populated from the INI `all_email_domains` key (`from_ini_file`) or the `MAIL_EMAIL_DOMAINS` environment variable with no count validation. A configuration containing more than 12 domains writes `seastar::sstring` objects past the end of the array — memory corruption, undefined behavior, potential crash or code execution depending on layout.

**Risk:** Memory corruption triggered by operator misconfiguration or a tampered config file; at minimum a reliable crash/DoS at startup or per-connection.

**Recommendation:**

- Clamp the loop: `for (...) { if (result.count >= MAX_EMAIL_DOMAINS) break; ... }`.
- Validate each configured domain with `validate_domain()` and reject/skip invalid entries.
- Consider reading `all_email_domains` exclusively from `load_email_domains()` (which is bounded) instead of raw config.

### Medium Priority Issues

#### 3. Command Buffer Limit Announced but Not Enforced

**Severity:** Medium

**Status:** Confirmed

**Description:** When the per-connection log size exceeds `SMTP_COMMAND_BUFFER_SIZE_LIMIT` (2500 bytes), the server sends `552 5.3.4 Message size limit exceeded` **but does not close the connection** (`active` remains true, no `break`). The client can continue issuing commands indefinitely; every command and every response is appended to the per-session log file, which grows without bound. Additionally, a log file is created for **every** connection at accept time and is never rotated or deleted.

**Risk:** Disk/inode exhaustion DoS; long-lived connections consuming a semaphore slot while growing logs indefinitely.

**Recommendation:**

- On limit exceeded: send the error, then terminate the session (`active = false`).
- Apply a real per-line/per-command size cap independent of log size.
- Add log rotation/cleanup (e.g., age-based purge) for the log directory.

#### 4. Unbounded RCPT Count and Recipient Vector Growth

**Severity:** Medium

**Status:** Confirmed

**Description:** `session_state_rcpt_count` and `session_mail_rcpt` grow without limit per connection. A client can issue arbitrarily many `RCPT TO` commands (each receiving `250 Accepted` when the domain matches), growing heap memory per connection; multiplied by the 1024-connection semaphore, this is a memory-exhaustion vector. There is no `MAXRCPT` equivalent.

**Risk:** Memory exhaustion / OOM under sustained multi-connection abuse.

**Recommendation:** Cap recipients per transaction (e.g., 100) with a `452 4.5.3 Too many recipients` response.

#### 5. Stale Recipient State Across Transactions (Information Leak)

**Severity:** Medium

**Status:** Confirmed

**Description:** `session_mail_rcpt` is never cleared. `RSET`, `HELO`/`EHLO`, and a completed `DATA` transaction reset the counters but not the vector. Consequences:

- Recipients from a previous transaction are re-written as `X-Mail-Rcpt-Email-Address` headers into the **next** message on the same connection (disclosure of earlier recipients' addresses to the next sender).
- A second `DATA` without new `RCPT` is accepted (counter still ≥ 1) and appended to the same open `.eml` file, merging multiple messages into one spool file.

**Risk:** Cross-transaction metadata leakage; malformed spool files confusing downstream processing.

**Recommendation:** Clear `session_mail_rcpt` in `RSET`, `HELO`/`EHLO`, and after each completed `DATA`; reset transaction state consistently.

#### 6. Misleading RCPT Responses (250 Sent Before Domain Check)

**Severity:** Medium

**Status:** Confirmed

**Description:** In the RCPT handler, `250 Accepted` is sent immediately after syntax validation, **before** the domain-match check. For non-local recipients the client is told the recipient was accepted, but the address is silently dropped from `session_mail_rcpt` (the message is discarded unless another recipient matched). Senders receive no relay-denied indication (no `550`/`554`), producing silent mail loss and masking open-relay testing.

**Risk:** Silent mail loss; ambiguous relay behavior; debugging/monitoring confusion.

**Recommendation:** Perform the domain check first; reply `250` only for accepted local recipients and `554 5.7.1 Relay access denied` otherwise.

#### 7. STARTTLS State Machine Weaknesses

**Severity:** Medium

**Status:** Confirmed

**Description:**

- `EHLO` advertises `STARTTLS` unconditionally, even on connections that are already TLS (`is_tls` is never consulted).
- `STARTTLS` is accepted at any protocol state, including mid-transaction and when TLS is already active; a second upgrade wraps TLS in TLS (the pre-TLS streams are moved aside, and the previous `plain_in`/`plain_out` are overwritten and leaked until close).
- No requirement to re-issue `EHLO` after upgrade (RFC 3207 SHOULD).

**Risk:** Protocol state confusion; resource churn; misleading capability advertisement.

**Recommendation:** Reject `STARTTLS` when `is_tls` (e.g., `454 TLS already active`); only accept it in the command state before `MAIL`; consider requiring `EHLO` afterward.

### Low Priority Issues

#### 8. Configured Message Size Limit Not Enforced

**Severity:** Low

**Status:** Confirmed

**Description:** `EHLO` advertises the configurable `email_limit_size`, but the DATA-phase enforcement in `handle_connection()` hardcodes `DEFAULT_EMAIL_SIZE_LIMIT` (512 KB). An operator raising the limit in `smtp.conf` gets a larger advertised `SIZE` value with no change in actual enforcement.

**Recommendation:** Enforce `smtp_config->email_limit_size()` consistently.

#### 9. Oversized/Partial Messages Left in Spool

**Severity:** Low

**Status:** Confirmed

**Description:** When the size limit is exceeded mid-DATA, the already-written partial `.eml` file is left in the data directory (no cleanup), and the terminator-detection path writes the `\r\n.\r\n` bytes (and any pipelined bytes after it in the same chunk) into the file as well. The server also does not un-dot-stuff received data, so stored messages retain doubled dots.

**Risk:** Spool pollution; disk consumption via repeated aborted oversized deliveries; slightly corrupted message bodies.

**Recommendation:** Delete the partial file on aborted transactions; strip the terminator; implement RFC 5321 dot-unstuffing.

#### 10. Spool/Log File Permissions Rely on umask

**Severity:** Low

**Status:** Requires operational control

**Description:** `open_file_dma(..., rw | create)` creates message and log files with default permissions (0666 & ~umask). With a typical 022 umask, spooled mail and session logs are world-readable on the host — notable for a privacy-first product.

**Recommendation:** Create spool/log files with explicit 0600 (and directories 0700), e.g., via `open_flags` options/`chmod` after creation.

#### 11. PROXY v2 Trusted Without Source Restriction

**Severity:** Low

**Status:** By design — requires operational controls

**Description:** With `proxy_support = true`, any peer presenting a syntactically valid PROXY v2 header dictates the logged and header-injected source IP (`X-Mail-Source-IP-Address`). The parser itself is solid (signature, version/command 0x21/0x01, family, length all validated, reads bounded to the declared length).

**Risk:** Source-IP spoofing if the port is reachable from untrusted networks.

**Recommendation:** Bind to loopback/private interfaces when behind a proxy, firewall the port, or add a trusted-proxy CIDR allow-list.

#### 12. Minor Robustness and Hygiene Items

**Severity:** Low

**Status:** Informational

**Description:**

- `get_ip_address()` treats any non-`AF_INET` family as IPv6 and falls back to a hardcoded `172.17.0.1` on conversion failure (misleading logs).
- `MAIL_EMAIL_DOMAINS` entries and INI `all_email_domains` are not syntax-validated.
- Command detection prefix-matches without a token-boundary check, so e.g. `DATAX`/`QUITxyz` are treated as `DATA`/`QUIT` (see also Findings 5/9 interaction); fragmented commands split across reads are dropped after a `500` response, and pipelined commands after the first CRLF in a chunk are silently discarded.
- The RCPT handler's single-domain special case duplicates the same prefix-match flaw as Finding 1.

**Recommendation:** Tighten command tokenization (require exact verb + space/CRLF boundary), buffer partial lines across reads, process all pipelined lines in a chunk.

## Code Quality Security Assessment

#### Input Validation

**Rating:** Good (with exceptions)

- Email address validation (`validate_local`, `validate_domain`, quoted-string handling) is strict and bounds-checked; CRLF injection into headers via validated addresses is not possible.
- PROXY v2 parsing validates magic, version/command, family, and length before any read; bounded reads.
- **Weaknesses:** prefix-match domain comparison (Finding 1), unbounded domain list (Finding 2), command prefix matching, unvalidated config-supplied domains.

#### Memory Safety

**Rating:** Good (with exceptions)

- Modern C++23, `string_view`/spans, Seastar ownership; no classic stack/heap overflows in session/TLS paths; careful stream lifecycle around STARTTLS.
- **Weaknesses:** out-of-bounds `std::array` write in `split_email_domains` (Finding 2); unbounded per-connection vector growth (Finding 4). Note: `compare_string_views` reads a constructed `string_view` of command length from a possibly shorter line but terminates on the sstring's guaranteed NUL within capacity — not exploitable in practice, yet fragile.

#### Cryptographic Implementation

**Rating:** Adequate–Good

- X.509 parsing and key consistency checks at startup; mismatch fails closed via `set_x509_key_file`.
- STARTTLS upgrade path implemented with explicit stream leak workarounds.
- No minimum TLS version or cipher-suite policy configured (defaults inherited from Seastar/OpenSSL).

## Dependency Analysis

### Seastar Framework (referenced v25.05.0)

- Not pinned in `CMakeLists.txt` (`find_package(Seastar REQUIRED)`); version floats with the build environment. No critical CVEs identified for the referenced version in the current window.

### OpenSSL

- Version entirely system-dependent and unpinned. Multiple moderate/low CVEs have been patched in the 2025–2026 OpenSSL 3.x/4.x stream; none directly impact basic SMTP STARTTLS, but staying current is essential.

### Boost (json, program_options, property_tree)

- Used for CLI/INI/JSON config parsing; standard components. `read_ini` is safe for local operator files. Keep updated.

### Build Hardening

- Release build uses `-O3` + `NDEBUG` (asserts stripped) but no stack protector, FORTIFY_SOURCE, PIE flags, or `-Werror`; no sanitizers or static analysis in CI.

**Recommendation:** Pin dependency versions (or provide a lockfile/Containerfile with digests), enable `-fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie`, and add CI jobs for clang-tidy, ASan/UBSan, and dependency scanning.

## Compliance Assessment

### OWASP Top 10 Coverage

- **Injection:** Strong — validated parsers; no shell/SQL sinks. Header injection via validated addresses not feasible.
- **Broken Authentication:** Not applicable by design (no SMTP AUTH; relay prevented by domain checks — see Finding 1 weakening this).
- **Sensitive Data Exposure:** TLS present; TLS policy hardening recommended; spool file permissions depend on umask (Finding 10); cross-transaction recipient leak (Finding 5).
- **Broken Access Control:** Domain-based recipient validation (bypass risk per Finding 1).
- **Security Misconfiguration:** Deployment-sensitive — proxy trust, umask, unpinned dependencies, advertised-but-unenforced limits.
- **Vulnerable Components:** Dependency pinning and scanning needed.
- **Insufficient Logging & Monitoring:** Logging is present (arguably excessive); limits not enforced (Finding 3).
- Others (XSS, XXE, Insecure Deserialization): Not applicable — no web interface; INI/JSON parsing is simple and local.

### SMTP-Specific Security

- RFC 5321 command sequencing enforced (DATA requires MAIL + RCPT; EHLO resets state).
- Dot-stuffing/unstuffing not implemented; terminator bytes written to spool (Finding 9).
- STARTTLS per RFC 3207 with caveats (Finding 7).
- PROXY v2 per HAProxy spec with correct framing validation (Finding 11 for trust).
- No SMTP AUTH, VRFY/EXPN/BDAT return `502` — reduces attack surface.

## Recommendations

### Immediate Actions (High Priority)

1. Fix recipient-domain comparison to exact, length-checked matching (Finding 1).
2. Bound and validate `split_email_domains()` input (Finding 2).
3. Enforce the command/log limit by closing the connection (Finding 3).
4. Cap RCPT count per transaction (Finding 4).
5. Clear per-transaction recipient state on RSET/HELO/DATA completion (Finding 5).

### Medium-term Improvements

1. Reorder RCPT validation before the 250 response; return `554` for relay attempts (Finding 6).
2. Enforce configured `email_limit_size`; delete partial spool files on abort; strip terminator; implement dot-unstuffing (Findings 8, 9).
3. Harden STARTTLS state machine (reject when already TLS; require EHLO after upgrade) (Finding 7).
4. Set explicit 0600/0700 permissions on spool/log files (Finding 10).
5. Pin dependencies; add build hardening flags and CI static analysis/sanitizers.
6. Add regression tests (domain matching edge cases, >12 domain list, fragmented/pipelined commands, oversized messages).

### Operational Security

1. Enable `proxy_support` only behind a trusted load balancer; firewall port 2525 to known sources where feasible.
2. Run as a dedicated low-privilege user with restrictive umask; keep spool/log directories private.
3. Monitor disk usage and connection counts; alert on log/spool growth.
4. Keep the host OpenSSL and Seastar builds patched; consider a minimum TLS 1.2 policy at the proxy if not in the app.
5. Prefer non-standard ports/firewall/reverse proxy exposure as recommended in deployment scripts.

## Conclusion

Version 1.6.2 demonstrates solid engineering — strict input validation, fail-closed TLS material handling, unpredictable spool filenames, and a correct PROXY v2 parser. The principal weaknesses are concentrated in the recipient-domain comparison (a genuine prefix-match bypass of the anti-relay control), an unbounded domain-list copy, and limits that are advertised but not enforced. None require architectural change; all are localized fixes. With Findings 1–5 remediated and the operational controls applied, the server provides a strong privacy-oriented foundation for self-hosted SMTP receiving.

**Risk Level:** Medium

**Recommended Actions:** Remediate Findings 1–5 within 14 days; address Medium items within 30 days.
