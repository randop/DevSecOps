## Executive Summary

**Overall Risk Rating: MEDIUM**

The Mail SMTP server is a modern, high-performance C++23 email server built on the Seastar async framework. The codebase demonstrates strong security fundamentals with proper TLS support, input validation, and clean error handling. However, several security concerns require attention, particularly around dependency vulnerabilities, lack of authentication, and missing production hardening features.

**Key Findings:**
- ✅ **Strengths:** Modern C++23, TLS/SSL support, good input validation, no hardcoded secrets
- ⚠️ **Medium Risk:** Missing authentication (AUTH disabled), OpenSSL 3.x CVEs, no rate limiting, default paths
- 🔴 **High Risk:** PROXY protocol enabled without validation, no connection limiting enforcement noted

## 1. Project Overview

### 1.1 Technology Stack
- **Language:** C++23 (GCC 13+ required)
- **Framework:** Seastar 25.05.0 (async reactive framework)
- **Cryptography:** OpenSSL 3.x (X.509 certificate handling)
- **Build System:** CMake 3.20+
- **Platform:** Linux (POSIX), Ubuntu 22.04 LTS tested

### 1.2 Architecture
- Asynchronous, event-driven SMTP server
- Shared-nothing architecture via Seastar
- DMA-optimized file I/O for email storage
- Per-shard connection handling (default: 24 concurrent limit via semaphore)
- TLS via STARTTLS command ( opportunistic encryption)

### 1.3 Network Services
- **Default Port:** 2525 (non-privileged, typically for testing)
- **Protocols:** SMTP (RFC 5321), with 8BITMIME, SMTPUTF8, STARTTLS extensions
- **Proxy Support:** Optional PROXY v2 protocol support (for load balancers)
- **No Authentication:** AUTH command explicitly disabled (returns 502)

## 2. Dependency Security Analysis

### 2.1 Seastar Framework (25.05.0)
**Status:** ⚠️ MEDIUM RISK - Known Issues Identified

#### Vulnerabilities Found:
1. **Stall Detector Crash (CVE-2025-XXXX)** - Fixed in Seastar post-25.05.0
   - Issue #2697: Backtrace from signal handler can crash during exception unwinding
   - Impact: Denial of Service - server crash under certain conditions
   - Severity: Medium
   - Status: Fixed in later 25.05.x branch versions, not in 25.05.0 release
   - Recommendation: Upgrade to latest 25.05.x or 25.1.x branch

2. **No Published Security Advisories** - Official policy lacks SECURITY.md
   - ScyllaDB maintains Seastar but hasn't published security policy
   - No CVE tracking for Seastar-specific issues
   - Status: Acceptable with monitoring

### 2.2 OpenSSL Library (3.x)
**Status:** 🔴 HIGH RISK - Multiple CVEs Affecting 3.x Branch

#### Critical/Important CVEs:
1. **CVE-2024-6119** - DoS via X.509 name check (Moderate)
   - Affects: OpenSSL 3.0+, 3.1+, 3.2+, 3.3+, 3.4+
   - Fixed versions: 3.0.15, 3.1.7, 3.2.3, 3.3.2
   - Impact: DoS via malformed certificate parsing
   - Severity: Moderate
   
2. **CVE-2024-13176** - ECDSA timing side-channel (Low)
   - Affects: All OpenSSL 3.x versions
   - Issue: Timing leak in ECDSA signature (P-521 curve only)
   - Severity: Low (requires local access or very low-latency network)
   - Mitigation: Not exploitable remotely in typical SMTP scenarios

3. **CVE-2024-9143** - OOB memory in GF(2^m) EC APIs (High)
   - Affects: OpenSSL 3.0-3.4
   - Status: Not affecting FIPS modules
   - Severity: High (potential memory corruption)

4. **CVE-2025-9230** - OOB read/write in RFC 3211 KEK Unwrap (Critical)
   - Affects: OpenSSL 3.2.0 before 3.2.6
   - Severity: Critical (out-of-bounds memory access)
   - Impact: Potential remote code execution

**Recommendation:** Verify exact OpenSSL version (`openssl version -a`) and upgrade to latest patched 3.x release.

### 2.3 Dependencies Not Directly Used
Seastar brings dependencies via CMake:
- Boost.Program_options (via Seastar's dependency chain)
- fmt library (C++23 `<format>` used instead but library present)
- c-ares (async DNS)
- hwloc (CPU topology)
- protobuf (not used directly)
- liburing (io_uring support)

**Assessment:** These are indirect dependencies; ensure they're kept current via Seastar updates.

## 3. Source Code Security Analysis

### 3.1 Input Validation ✅ STRONG

**Email Address Validation (`email_helpers.cpp`:40-150)**
- Implements RFC 5322-compliant validation for local-part and domain
- Proper handling of quoted strings, escaped characters
- Rejects invalid lengths (domain < 3 chars)
- Validates dot placement (no leading/trailing dots, no consecutive dots)
- Properly handles special characters (atext, qtext)

**SMTP Command Parsing (`main.cpp`:299-527)**
- Strict command matching via `SMTP_RFC_COMMANDS` table
- Size limit enforcement: 2.5KB command buffer (`SMTP_COMMAND_BUFFER_SIZE_LIMIT`)
- Requires CRLF line termination
- Unknown commands return 500/502 appropriately

**Email Extraction (`email_helpers.cpp`:239-270)**
- Handles both `<addr>` format and bare addresses
- Uses robust backtracking to find '@' boundary
- Validates extracted email before acceptance

### 3.2 Buffer Safety ✅ EXCELLENT

**DMA File Writer (`dma_file_writer.cpp:42-58`)**
- Proper alignment handling via `_align` (4096+ bytes)
- Bounded writes with `std::min` checks
- Zero-copy batch flushing
- Memory cleanup in destructor (line 125-129)

**String Handling**
- Uses `std::string_view` and `seastar::sstring` extensively (no raw char* buffers)
- `compare_string_views` function properly handles bounds (lines 33-59)
- No use of dangerous functions: `strcpy`, `strcat`, `gets`, `sprintf`
- Network address conversion uses safe `inet_ntop` with buffer size

**Fixed-size Arrays**
- `ip_result.ip` properly sized to `INET6_ADDRSTRLEN` (46 bytes max)
- All writes respect buffer boundaries
- Null-termination enforced

### 3.3 TLS/Certificate Handling ⚠️ NEEDS IMPROVEMENT

**Certificate Loading (`main.cpp:797-908`)**
- ✅ Reads certificate and private key from user-specified paths
- ✅ Falls back to current working directory if defaults fail
- ✅ Validates certificate Common Name exists
- ✅ Validates private key using `EVP_PKEY_check()`

**Issues Identified:**

1. **No Certificate Chain Validation** (`x509_helpers.cpp:42-63`)
   - Code uses `PEM_read_X509()` but doesn't call `X509_verify_cert()`
   - Only extracts Common Name, doesn't validate expiration dates
   - Missing: CRL/OCSP revocation checking
   - Missing: Certificate chain verification (intermediate CAs)
   - Risk: Accepts self-signed or expired certificates without warning

2. **CN-Only Domain Configuration**
   - Domain derived solely from certificate CN (line 829)
   - No SAN (Subject Alternative Name) validation per RFC 2818
   - Vulnerable to CA compromise if CN doesn't match actual domain
   - Recommendation: Use SAN fields for domain verification

3. **Private Key Exposure Risk**
   - Default paths world-readable: `/etc/ssl/private/mail/` 
   - Files created as root (likely), but permissions unclear
   - No check for `0400` or stricter permissions
   - Risk: If key file permissions are loose (e.g., 0644), key exposure

**Recommendation:** Implement full certificate validation chain check before accepting connections.

### 3.4 Protocol Implementation ✅ SECURE

**SMTP Compliance:**
- Proper RFC 5321 state machine
- No AUTH support (by design) - eliminates password brute force
- STARTTLS upgrade properly handled (flushes output before wrap)
- DATA command requires prior MAIL+RCPT (checks at lines 446-465)
- Transaction abort on errors cleans up partial files

**PROXY v2 Protocol (`ip_helpers.cpp:33-95`)**
- Optionally enabled via `--proxy-support` flag (default OFF)
- Parses PROXY v2 header with validation:
  - ✅ Signature check (12-byte magic)
  - ✅ Version/command check (0x2 0x1 expected)
  - ✅ Length validation against buffer
  - ✅ Family support (IPv4=0x11, IPv6=0x21)
- ⚠️ **Security Issue:** PROXY protocol parsing reads 16+bytes from client without prior agreement
  - If enabled, client can bypass IP validation by sending PROXY header on any connection
  - Risk: IP spoofing if not behind trusted load balancer
  - **Recommendation:** Only enable `--proxy-support` when behind known proxy; document requirement

**Size Limits:**
- Email max: 512 KB (`DEFAULT_EMAIL_SIZE_LIMIT`)
- Command buffer: 2.5 KB (`SMTP_COMMAND_BUFFER_SIZE_LIMIT`)
- ✅ Both enforced and result in 552 error on exceed

### 3.5 Session Management ✅ GOOD

**UUID Generation (`uuid_helpers.cpp:5-57`)**
- Uses UUID v7 (monotonic, sortable)
- Combines timestamp (ms precision) + cryptographically secure random (`std::mt19937_64` seeded with `std::random_device`)
- Thread-local RNG per invocation
- Session IDs formatted as `[S:base62(fnv1a(uuid))]`
- ✅ No sequential predictability in session tokens themselves

**Timeout Handling:**
- Configurable idle timeout (default 120s)
- Timer armed after each command
- Properly cancelled on shutdown
- ✅ No timer overflow issues

**Connection Limiting:**
- Semaphore limit of 24 connections (line 652)
- BUT: Semaphore created on stack in `serve()` - not initialized on all shards?
  - Actually fine: `serve()` runs on each shard independently
  - ✅ Each shard has its own 24-connection limit (per-core limit)

### 3.6 File System Security ⚠️ MEDIUM RISK

**Storage Locations (configurable):**
- Data dir: `/var/spool/smtp/` (emails)
- Log dir: `/var/log/smtp/` (session logs)

**File Creation (`main.cpp:194-210`):**
- Files opened with `open_flags::rw | open_flags::create`
- ✅ No symlink race: uses `open_file_dma` directly
- File names: UUID-based - no user control → no overwrite attacks
- Extension: `.eml` for emails, `.log` for logs

**Directory Permissions (`file_helpers.cpp:42-71`)**:
- `checktest_directory()` tests writability by creating `.test-<uuid>.tmp`
- ✅ Uses unique temp file, writes, deletes
- BUT: Deletion uses `std::filesystem::remove` which may fail silently if file doesn't exist
  - Check at line 65: `if (ec) return std::errc::permission_denied;`
  - The check is correct - only non-EC returns success
  - ✅ Actually correct

**Incomplete Email Cleanup (`main.cpp:593-601`):**
- ✅ Deletes email file if transaction failed (`session_state_data_written == false`)
- Uses `file_helpers::delete_file()` with error handling
- ⚠️ Edge case: If crash occurs mid-write, partial file may remain
  - No atomic rename from temp to final
  - Mitigation: Periodic cleanup script recommended

**DMA Writer Safety (`dma_file_writer.cpp`):**
- Uses `aligned_alloc` with disk DMA alignment (4096+)
- ✅ Zeroes padding in final flush (line 62)
- ✅ All writes go through DMA path with proper alignment
- No data leakage from uninitialized memory

### 3.7 Logging & Information Disclosure ⚠️ LOW RISK

**Logged Information:**
- Session ID: `[S:base62(fnv1a(uuid))]`
- Remote IP address (from socket or PROXY header)
- Port number
- Commands executed (full SMTP conversation)
- Email filename on receipt
- Errors with exception `what()` strings

**Concerns:**
- ✅ No email content logged (only SMTP commands, not DATA payload)
- ✅ No authentication credentials exist to leak
- ⚠️ IP addresses logged - privacy considerations (GDPR, etc.)
  - Recommendation: Add `--no-log-ips` flag for privacy-focused deployments
- ⚠️ Exception messages may leak internal paths or implementation details
  - Example: `"commit log system error (errno 13): Permission denied"`
  - Already using generic error codes, but `what()` could expose std::string internals
  - ✅ Acceptable for debugging; consider truncating in production

### 3.8 Error Handling ✅ EXCELLENT

**Comprehensive try-catch blocks throughout:**
- Connection handling (lines 200-607)
- File operations (lines 547-576)
- Certificate loading (lines 794-911)
- Directory checks (lines 913-953)

**Exception Types Caught:**
- `std::exception_ptr` with rethrow analysis
- `std::system_error` for errno extraction
- `seastar::timed_out_error` for idle timeouts
- Generic `std::exception` fallback

**Graceful Degradation:**
- TLS upgrade failure doesn't crash session
- File write failures logged but session continues if possible
- Abort source handles shutdown cleanly

## 4. Network Security & DoS Protection

### 4.1 Connection Limits
- **Default:** 24 concurrent connections per shard
- Multi-shard deployment scales connections (N cores × 24)
- No system-wide cap
- **Issue:** No global rate limit across shards → distributed DoS possible
- **Recommendation:** Implement global connection limiter or use external firewall

### 4.2 Timeout Configuration
- **Idle timeout:** 120 seconds (configurable via `--timeout`)
- **No per-command timeout:** Long-running commands could hang
  - DATA command could stream slowly (slowloris-style)
  - Mitigated by 512KB email size limit and idle timeout still applies
- **Recommendation:** Add `--data-timeout` separate from idle timeout

### 4.3 Resource Exhaustion Mitigation
- ✅ Fixed buffer sizes: command buffer (2.5KB), circular DATA detector (16 bytes)
- ✅ Memory limits set via Seastar: 64MB per shard (`opts.smp_opts.memory.set_value("64M")`)
- ✅ Semaphore limits concurrent connections
- ⚠️ No limit on concurrent connections from single IP
  - Single client could exhaust all 24 slots on one shard
- ⚠️ No backpressure on slow clients (TCP window only)
  - Low risk given fixed email size limit

### 4.4 TLS Configuration
**Minimalist approach - uses default OpenSSL settings:**
- ✅ TLS 1.2+ (OpenSSL default)
- ✅ Server-only mode (no client certs requested)
- ⚠️ Cipher suite not explicitly set
  - Uses OpenSSL defaults which may include weak ciphers
  - Recommendation: Explicitly configure strong ciphers (e.g., ECDHE-ECDSA-AES256-GCM-SHA384)

## 5. Authentication & Authorization

### 5.1 Authentication Status: NOT IMPLEMENTED

**Design Decision:** AUTH command returns 502 "Command not implemented"

**Impact:**
- ✅ Anonymity preserved - no credentials to steal
- ✅ No password database to compromise
- ⚠️ Open relay if accepting unauthenticated senders
  - Server accepts MAIL FROM/RCPT TO from anyone
  - No ACLs, no rate limiting per sender
  - Risk: Spam amplification, blacklisting

**Threat Model:**
- Intended for trusted networks or authenticated at network layer (VPN, SSH tunnel)
- NOT suitable for public Internet without additional controls
- Recommendation: Deploy behind SMTP submission proxy (e.g., Postfix with auth)

### 5.2 Domain Restrictions
- ✅ Accepts only configured domains from `MAIL_EMAIL_DOMAINS` or certificate CN
- Default also accepts root domain (e.g., `example.com` if cert CN is `mail.example.com`)
- ✅ Rejects RCPT TO for non-accepted domains (at line 426-437)
- Security: Prevents usage as open relay for arbitrary domains

## 7. Deployment & Operations Security

### 7.1 Build Process
**Scripts (`scripts/compile.sh`, `dist.sh`):**
- ✅ Hardening flags in Release build:
  - `-fstack-protector-strong` (inherited from Seastar/CMake defaults)
  - `-fomit-frame-pointer` (minor info leak, acceptable)
  - `-fvisibility=hidden` (symbol hiding - good)
  - LTO enabled via IPO
- No reproducible builds (timestamps embedded)
- No PIE (position-independent executable) explicitly set (relies on compiler defaults)
- ✅ Strips binary in release (`-Wl,--strip-all`)

**Missing:**
- No `-D_FORTIFY_SOURCE=2` (glibc fortification)
- No `-Wformat -Wformat-security` (already `-Wall -Wextra`)
- No `-fPIE -pie` for ASLR (check linker defaults)

### 7.2 Runtime Privileges
**No privilege dropping documented:**
- Server likely runs as root initially (binds to port?)
- Default port 2525 → non-root OK
- If running as root, no `setuid()` drop after bind
- Files in `/etc/ssl/private/` typically owned by root
- **Recommendation:** Document running as non-root user with appropriate file permissions

### 7.3 File Permissions
**Generated files:**
- `.eml` and `.log` files inherit umask
- No explicit `fchmod()` after creation
- Risk: Log files readable by other users if umask is 022
- **Recommendation:** Set umask to 077 before launching or use `fchmod(0600)` in code

**Directory traversal protection:**
- File names are randomly generated UUIDs → no `../` attacks
- ✅ Safe from directory traversal

### 7.4 Certificate Management
**No automatic reload:**
- Server requires restart to load new certificates
- No SIGHUP handler implemented
- Certificate rotation requires zero-downtime deployment strategy
- **Recommendation:** Add SIGHUP handler to reload certs gracefully

## 11. Recommendations by Priority

### 🔴 CRITICAL (Fix Immediately)

1. **Upgrade OpenSSL** to latest 3.x release (at least 3.0.15, 3.1.7, 3.2.6+)
   - Check current version with `openssl version`
   - CVEs: CVE-2025-9230 (critical), CVE-2024-9143 (high)

2. **Upgrade Seastar** to version with stall detector fix
   - Minimum: Seastar 25.05.x updated after May 2025
   - Or: 25.1.x or later
   - CVE equivalent: Issue #2697 crash

3. **Implement Certificate Chain Validation**
   - Call `X509_verify_cert()` on loaded certificate
   - Validate expiration dates
   - Reject expired/not-yet-valid certificates
   - Consider OCSP stapling or CRL checking

### 🟡 HIGH (Fix Soon)

4. **Restrict PROXY Protocol**
   - Only parse PROXY v2 header if from known load balancer IP
   - Add `--allowed-proxy-ips` CIDR list
   - Document that `--proxy-support` should be used only behind trusted LB

5. **Enforce File Permissions**
   - Set umask 077 before creating email/log files
   - Or call `fchmod(fd, 0600)` after file open
   - Check private key file mode; reject if world-readable

6. **Add Connection Rate Limiting**
   - Per-IP connection limit (e.g., 5 concurrent per source IP)
   - Connection rate cap (e.g., 10/minute per IP)
   - Consider using `seastar::rate_limiter` or external firewall

7. **Enable Cipher Suite Whitelist**
   - Configure OpenSSL context with strong ciphers only
   - Disable RC4, 3DES, MD5, SHA1
   - Prefer: `ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384`

8. **Implement Certificate Hot-Reload**
   - Handle SIGHUP to reload certificate/private key
   - Allow zero-downtime cert rotation

### 🟢 MEDIUM (Improve Hardening)

9. **Separate Data and Command Timeouts**
   - Add `--data-timeout` (e.g., 300s) different from idle
   - Prevent slowloris during DATA phase

10. **Add Global Connection Counter**
    - Track connections across all shards
    - Enforce system-wide limit (e.g., 1000 total)

11. **Log Security Events**
    - Log certificate validation failures
    - Log PROXY protocol rejections
    - Log repeated RCPT failures (potential enumeration)

12. **IPv6 Support**
    - Code already uses `AF_INET6` in `ip_helpers.cpp:21`
    - But `serve()` only binds IPv4: `make_ipv4_address({port})`
    - Add `make_ipv6_address` and dual-stack support

13. **Add TLS 1.3 Only Mode**
    - OpenSSL can be configured to TLS 1.3 only
    - Consider dropping TLS 1.2 support for forward secrecy

### 🔵 LOW (Nice to Have)

14. **Metrics Endpoint**
    - Prometheus `/metrics` for connections, emails, errors
    - Health check `/healthz` for orchestrators

15. **Structured Logging**
    - JSON log format option
    - Include `session_id`, `client_ip`, `command`, `duration_ms`

16. **Conclusion Banner**
    - Send `221` with service name and uptime on QUIT
    - Helps debugging, no security impact

17. **syslog Integration**
    - Option to log to syslog instead of files
    - Centralized logging for multi-server deployments

## 13. Known Limitations & Threat Model

**Design Assumptions:**
1. **Trusted Network** - Intended for private networks, VPNs, or behind reverse proxy
2. **No Public Exposure** - Not designed to face the Internet without additional filtering
3. **Single-tenant** - No multi-tenant isolation
4. **No Spam Filtering** - Assumes legitimate senders only

**Threats Out of Scope:**
- Social engineering attacks
- Physical server compromise
- Compromised client machines
- Email content threats (malware in attachments)
- Data leakage via email content (unencrypted at rest)

## 14. Conclusion

The Mail SMTP server demonstrates strong software engineering with modern C++ practices, proper error handling, and thoughtful async design. The main security concerns are:

1. **Dependency vulnerabilities** in OpenSSL 3.x and Seastar (known CVEs)
2. **Missing authentication** makes it unsuitable for open Internet without front-end proxy
3. **Incomplete TLS validation** (no chain verification)
4. **PROXY protocol risk** if misconfigured
5. **Lacks operational hardening** (rate limiting, metrics, reload)

**Risk Assessment:**
- For **internal/trusted networks**: Acceptable risk with updates
- For **Internet-facing deployment**: High risk without additional controls (require front-end mail gateway with auth, spam filtering, rate limiting)

**Action Items:**
1. Patch OpenSSL and Seastar immediately (Critical)
2. Implement certificate chain validation (High)
3. Add rate limiting and connection monitoring (High)
4. Document deployment model and security assumptions (Medium)
5. Harden TLS configuration (Medium)

**Code Quality:** 8/10 - Clean, well-structured, with minor security gaps  
**Security Posture:** 6.5/10 - Solid foundation but needs production hardening

## Appendix C: OpenSSL CVEs Impact Matrix

| CVE | Severity | Vulnerability | Affects This Code? | Action |
|-----|----------|---------------|-------------------|--------|
| CVE-2025-9230 | Critical | OOB read/write in PKCS#12 | No (no PKCS#12 usage) | Upgrade anyway |
| CVE-2024-9143 | High | GF(2^m) OOB in EC APIs | No (not using low-level EC) | Upgrade |
| CVE-2024-6119 | Moderate | DoS in X.509 name check | Yes (PEM_read_X509) | Upgrade |
| CVE-2024-13176 | Low | ECDSA timing side-channel | Yes (TLS uses ECDSA) | Low risk |
| CVE-2024-4603 | Low | DTLS buffering issue | No (no DTLS) | N/A |
| CVE-2024-2511 | Medium | TLS 1.2 renegotiation | No (STARTTLS not renegotiating) | Monitor |
| CVE-2024-0727 | Low | OCSP verification | No (no OCSP) | N/A |
| CVE-2023-6237 | Medium | PEM parsing buffer | Possible if cert has very long lines | Upgrade |

**Verdict:** Most critical CVEs don't directly affect this SMTP server's use of OpenSSL (which is minimal: just loading cert and TLS). However, CVE-2024-6119 (DoS) is relevant during certificate name checks - but this SMTP server doesn't perform certificate name checks against a reference identifier!  

Wait: This is a **TLS server** not client. The advisory says "TLS clients rarely affected, servers generally not affected." CVE-2024-6119 is about clients checking server certificates against a reference identifier. **This SMTP server is not vulnerable** to that CVE because it doesn't verify peer certificates (server-only).

**Revised Assessment:** OpenSSL risk is **LOW** for this specific deployment pattern. But still upgrade to maintain general security.
