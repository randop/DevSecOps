## Executive Summary

This report presents an independent static security review of the Mail SMTP server (v1.6.2), a privacy-first, self-hosted SMTP server built on Seastar/C++23. The review covers the full `src/` and `include/` tree, `CMakeLists.txt`, sample configuration, and deployment scripts, and cross-checks the prior audit (SA-2026-09-18-001) against the current source.

**Overall Assessment**: The codebase retains the strengths noted previously — RFC-oriented address parsing, domain-based relay protection, and mandatory X.509 validation at startup. However, this review identified a **new memory-safety defect** not previously reported: an out-of-bounds heap read in the domain-comparison routine used during RCPT TO processing, reachable pre-authentication by any anonymous connecting client. Several additional logic and enforcement gaps were also found (email size-limit bypass, non-terminating buffer-limit check, missing STARTTLS re-issuance guard, weak PRNG seeding for file names, and an off-by-one domain-list bug). The previously reported operational gaps (dependency pinning, TLS hardening, proxy trust, per-IP rate limiting) remain unaddressed in this snapshot.

**Risk Level**: Medium (elevated from the prior "Low to Medium" rating due to the newly identified out-of-bounds read).

## Methodology

- Full manual line-by-line review of all 11 `.hpp`/`.hh` headers and 11 `.cpp` sources (≈3,160 lines total)
- Independent re-derivation of findings rather than reuse of the prior report's conclusions
- Trace of all network-attacker-controlled data paths: raw socket reads, SMTP command dispatch, PROXY protocol v2 parsing, email address extraction, DATA/size-limit handling, STARTTLS state transition
- Review of build configuration (`CMakeLists.txt`), sample config (`etc/mail/smtp.conf`), and operational scripts (`scripts/*.sh`) for insecure defaults or secrets
- Comparison against the prior audit (SA-2026-09-18-001) to confirm which findings persist, which were remediated, and which are new
- Evaluation against OWASP Top 10, RFC 5321, and known SMTP-server vulnerability classes (notably STARTTLS plaintext-command injection)

## Findings

### High Priority Issues

#### 1. Out-of-Bounds Heap Read in Domain-Matching Comparison (New)

**Severity**: High
**Status**: Confirmed, Unreported Previously

**Description**: `string_helpers::compare_string_views()` (`src/string_helpers.cpp`) reads `a[i]` for every index up to `b.size()`, without ever checking that `a.size() >= b.size()`:

```cpp
while (a[i] != '\0' && i < b_size) {
  if (to_lower(a[i]) != to_lower(b[i])) return false;
  ...
  ++i;
}
```

This is called in `src/main.cpp` during RCPT TO handling:

```cpp
std::string_view check_email = email_helpers::get_domain(email);
if (compare_string_views(check_email, smtp_config->domain())) { ... }
...
if (compare_string_views(check_email, all_email_domains.domains[i])) { ... }
```

`check_email` is a `string_view` over the tail of the heap-allocated `email` string produced by `extract_email_address()` from the client-supplied RCPT TO argument — its `size()` is the *true* extent of the underlying allocation, with nothing valid beyond it. If the configured accepted domain (`smtp_config->domain()` or an entry in `all_email_domains`) is longer than the attacker-supplied domain candidate, and the two share a common prefix, the loop reads past the end of `email`'s heap buffer.

**Risk**: This is reachable by any anonymous TCP client, pre-authentication (there is no AUTH), simply by sending a crafted `RCPT TO:<x@<prefix-of-a-configured-domain>>`. It is undefined behavior that can crash the process (denial of service) depending on heap layout/allocator, and directly contradicts the "no classic buffer overflows" / "Good–Excellent memory safety" characterization in the prior audit. The same unguarded pattern is also used for command-prefix matching in the SMTP command dispatcher (`main.cpp` line ~205), though that call site is comparatively lower-risk because the compared strings are short and typically remain inside `sstring`'s small-string buffer — it should still be corrected for the same reason (see Finding 6).

**Recommendation**:
- Fix `compare_string_views()` to bound the loop by `std::min(a.size(), b.size())`, or simply return `false` immediately when `a.size() != b.size()` for exact-match use cases like domain comparison.
- Replace ad-hoc case-insensitive comparisons with a reviewed helper (e.g. `std::ranges::equal` with a case-folding projection) that cannot read past either operand's bounds.
- Add fuzz/unit tests for `extract_email_address` + domain matching using short attacker strings against longer configured domains.

### Medium Priority Issues

#### 2. Email Size Limit Enforcement Ignores Administrator Configuration (New)

**Severity**: Medium
**Status**: Confirmed

**Description**: The EHLO/HELO banner advertises the *configured* limit, but the DATA-phase enforcement check uses the *compile-time constant* instead:

```cpp
// Advertised to client:
std::format("...250 SIZE {}\r\n", ..., smtp_config->email_limit_size());
// Actually enforced:
if (session->get_email_size() > DEFAULT_EMAIL_SIZE_LIMIT) { ... }
```

`email_limit_size` is a documented, admin-configurable setting (`etc/mail/smtp.conf: email_limit_size = 524288`), but that value is never read at enforcement time — only the hardcoded 512 KB constant is checked.

**Risk**: An administrator who lowers `email_limit_size` to conserve disk space or bound resource usage gets no actual protection beyond the hardcoded default; the effective cap is always 512 KB regardless of configuration. This is primarily a resource/capacity-planning control bypass rather than a direct exploit.

**Recommendation**: Replace `DEFAULT_EMAIL_SIZE_LIMIT` with `smtp_config->email_limit_size()` at the enforcement site, and add a regression test asserting that the advertised and enforced limits are always identical.

#### 3. Command/Log Buffer Limit Check Does Not Terminate the Session (New)

**Severity**: Medium
**Status**: Confirmed

**Description**: When the per-session log/command buffer exceeds `SMTP_COMMAND_BUFFER_SIZE_LIMIT` (2,500 bytes), the server sends a `552` error but does not set `active = false` or otherwise close the connection:

```cpp
if (session->get_log_size() > SMTP_COMMAND_BUFFER_SIZE_LIMIT) {
  applog.error(...);
  sstring message = "552 5.3.4 Message size limit exceeded\r\n";
  co_await session->send(std::move(message));
}
```
(Contrast with the DATA-phase size check a few lines above, which correctly sets `active = false; break;`.)

**Risk**: A client can keep sending arbitrary bytes indefinitely; every read is still appended to the on-disk session log via `write_log()` before this check runs, and the connection is never dropped for it. Combined with the already-known absence of per-IP rate limiting (Finding 8 below), this allows sustained, unbounded log-directory growth from a single held-open connection, bounded only by the idle timeout and the global per-shard connection semaphore.

**Recommendation**: On exceeding the buffer limit, set `active = false` (and `break` out of the read loop) in addition to sending the error, matching the DATA-phase pattern.

#### 4. Missing Guard Against Repeated STARTTLS (New)

**Severity**: Medium
**Status**: Confirmed

**Description**: `smtp_session` tracks an `is_tls` flag, set to `true` inside `upgrade_tls()`, but it is never read anywhere in the codebase — there is no check preventing a client from issuing `STARTTLS` a second time after the connection is already wrapped:

```cpp
case SMTP_COMMAND::STARTTLS: {
  sstring message = "220 Ready to start TLS\r\n";
  co_await session->send(std::move(message));
  co_await session->upgrade_tls(certs); // no is_tls guard
  ...
}
```

**Risk**: Re-invoking `tls::wrap_server()` on an already-TLS-wrapped `connected_socket` is undefined/unsupported behavior for the underlying library and is a known root cause of protocol-confusion and command-injection classes of bugs in other SMTP implementations. At minimum this risks a crash or hung connection (denial of service) if triggered.

**Recommendation**: Check `is_tls` (expose a getter) before processing STARTTLS and reply `503 5.5.1 STARTTLS already in effect` if already upgraded, per RFC 3207 §4.

*Note — related positive finding*: the implementation appears to correctly avoid the classic **STARTTLS plaintext-command-injection** vulnerability class (e.g., CVE-2011-0411-style attacks), because it processes at most one command per raw socket read and does not requeue or reprocess any bytes trailing the current command line after a TLS upgrade. Any plaintext bytes pipelined by a MITM after a legitimate `STARTTLS` are discarded rather than being fed to the post-upgrade session. This is good practice and should be preserved (and covered by a regression test) when addressing Finding 4.

#### 5. Dependency Version Management (Carried Over, Unaddressed)

**Severity**: Medium–High
**Status**: Unchanged from SA-2026-09-18-001

**Description**: `CMakeLists.txt` still uses unconstrained `find_package(Seastar REQUIRED)`, `find_package(OpenSSL REQUIRED)`, and `find_package(Boost REQUIRED COMPONENTS json program_options)` with no version floor and no lockfile.

**Recommendation**: Unchanged from the prior report — pin minimum versions in CMake, add CI dependency scanning, track a current patched OpenSSL 3.x line.

#### 6. TLS Configuration Hardening (Carried Over, Unaddressed)

**Severity**: Medium–High
**Status**: Unchanged from SA-2026-09-18-001

**Description**: `serve()` still calls `certs->set_x509_key_file(...)` with no explicit minimum TLS version or cipher-suite restriction configured anywhere in `smtp_configuration` or at the `tls::server_credentials` call site.

**Recommendation**: Unchanged — explicitly set minimum TLS 1.2 (prefer 1.3) and restrict cipher suites via Seastar/GnuTLS-OpenSSL configuration; document required OpenSSL settings for production.

#### 7. Proxy Protocol Handling (Carried Over, Unaddressed)

**Severity**: Medium
**Status**: Unchanged from SA-2026-09-18-001

**Description**: `parse_proxy_v2()` correctly validates the PROXY v2 signature, version/command byte, and per-family address length before trusting the embedded source IP, and the client-supplied length field is used consistently for both the exact-read size and the internal bounds checks (no length-confusion bug was found here). However, there remains no source-IP allow-list restricting which upstream peers may present a PROXY header, and the shipped `scripts/production-run.sh` example enables `--proxy-support` without any accompanying network-level restriction.

**Recommendation**: Unchanged — document that `proxy_support` must only be enabled behind a trusted, network-isolated load balancer, and consider an optional source-IP allow-list.

#### 8. Resource Exhaustion Protections (Carried Over, Unaddressed)

**Severity**: Low–Medium
**Status**: Unchanged from SA-2026-09-18-001

**Description**: Only a global per-shard connection semaphore (1024, or 24 in `eco` budget mode) bounds concurrency; there is still no per-IP connection or rate limit. This gap is compounded by Finding 3 above.

**Recommendation**: Unchanged — add per-IP concurrent-connection and rate limits, with optional backoff/temporary bans.

### Low Priority Issues

#### 9. Weak PRNG Seeding for UUIDv7 File/Log Names (New)

**Severity**: Low
**Status**: Confirmed

**Description**: `uuid_helpers::generate_v7()` seeds a non-cryptographic `std::mt19937_64` generator once per thread from a single call to `std::random_device{}()`:

```cpp
thread_local std::mt19937_64 rng{std::random_device{}()};
```

This yields at most ~32 bits of effective seed entropy for the entire stream of "random" values a shard will ever produce, feeding a PRNG whose internal state is fully recoverable from a handful of observed outputs. These UUIDs are used to name spool email files and session log files (`generate_email_filename`, `generate_random_logname`), which the prior audit specifically credited as a security strength ("random UUID-based filenames").

**Risk**: Reduced practical unpredictability of on-disk file names versus what a CSPRNG would provide. Exploitation requires the attacker to already have some means of interacting with the filesystem or observing outputs, so this is a defense-in-depth weakening rather than a standalone vulnerability, but it undermines a control the project relies on for information-disclosure resistance.

**Recommendation**: Seed from multiple `std::random_device` draws (e.g., 2× 64-bit words) or switch to a CSPRNG (e.g., OpenSSL `RAND_bytes`) for the random component of generated identifiers.

#### 10. Off-by-One Bug Silently Drops Apex Domain (New)

**Severity**: Low
**Status**: Confirmed

**Description**: In `email_helpers::load_email_domains()` (used at startup to build the accepted-domains list from the certificate's CN):

```cpp
if (root_domain != default_email_domain &&
    ((result.count + 1) < MAX_EMAIL_DOMAINS)) {
  result.count++;
  result.domains[result.count] = root_domain; // writes to count, not count-1
}
```

`result.count` is incremented *before* the write, so `root_domain` is stored one slot past where the new count says it should be; the slot the count actually points to (`domains[old_count]`) is left default-constructed (empty), and `root_domain` itself falls outside the range that `join_email_domains()` iterates over and is silently lost.

**Risk**: The intended apex/root domain (e.g., `example.com` derived from a certificate CN of `mail.example.com`) is not actually added to the accepted recipient domains, and an empty string is counted as a domain entry instead. `compare_string_views` returns `false` for zero-length operands, so this does not create a relay/matching bypass, but it is a functional correctness bug that can cause legitimate mail to the apex domain to be rejected as "no valid recipients." Note this function is distinct from `split_email_domains()` (used per-connection), which was reviewed and found correct.

**Recommendation**: Write to `result.domains[result.count]` before incrementing, or increment after the write; add a unit test asserting the apex domain is present in the final domain set.

#### 11. Authentication Absence (Carried Over, By Design)

**Severity**: Low–Medium
**Status**: Unchanged — By Design (Privacy-Focused)

No change from SA-2026-09-18-001: SMTP AUTH is intentionally unimplemented, with domain-based RCPT validation as the anti-relay control. This remains an accepted design tradeoff; document it clearly for operators.

## Code Quality Security Assessment

#### Input Validation

**Rating**: Good, with a Caveat

RFC-oriented local-part/domain validation (`validate_local`, `validate_domain`) is thorough and correctly rejects malformed structures (leading/trailing dots, invalid quoting, disallowed characters). However, the string-comparison primitive used downstream of that validation (Finding 1) is not bounds-safe, which undercuts the otherwise solid parsing layer.

#### Memory Safety

**Rating**: Needs Improvement (revised down from the prior audit's "Good–Excellent")

Modern C++23 idioms (`string_view`, `span`, RAII ownership via Seastar) are used throughout, and no classic stack/heap buffer *overflows* (writes) were found. However, this review identified a genuine out-of-bounds *read* (Finding 1) reachable from unauthenticated network input, plus a second instance of the same unsafe pattern in command dispatch (Finding 4's related note / see `compare_string_views` call at `main.cpp:205`). Both stem from the same root-cause utility function and should be fixed together.

#### Cryptographic Implementation

**Rating**: Adequate (unchanged)

X.509 certificate/key loading and validation at startup, and the STARTTLS upgrade path itself, remain correctly implemented at the protocol level. TLS version/cipher policy is still left to library defaults (Finding 6). UUID generation is not cryptographic quality (Finding 9), though it is not used for any authentication or session-token purpose in the current codebase — only for file naming.

## Dependency Analysis

No change from SA-2026-09-18-001: Seastar (referenced v25.05.0), OpenSSL, and Boost (json, program_options) remain unpinned in the build. No new dependency-specific CVEs were identified as part of this review beyond reaffirming that OpenSSL should be kept current.

## Compliance Assessment

### OWASP Top 10 Coverage

- **Injection**: Address/command parsing remains well-structured; no shell/SQL injection surface exists in this codebase.
- **Broken Authentication**: Not applicable (by design; no AUTH).
- **Sensitive Data Exposure**: TLS present; version/cipher hardening still recommended (Finding 6).
- **Broken Access Control**: Domain-based recipient validation, but its comparison primitive has a memory-safety defect (Finding 1).
- **Security Misconfiguration**: Deployment example (`production-run.sh`) enables proxy trust without documented network isolation.
- **Vulnerable/Outdated Components**: Dependency pinning still needed (Finding 5).
- **Insufficient Logging & Monitoring**: Logging exists but its own size control is non-enforcing (Finding 3).

### SMTP-Specific Security

- Core RFC 5321 command sequencing is enforced correctly (MAIL→RCPT→DATA ordering, RSET semantics).
- Open-relay prevention via domain matching is present, but the underlying comparison is not memory-safe (Finding 1).
- STARTTLS is opportunistic (RFC 3207), correctly resistant to classic plaintext-injection replay (see note under Finding 4), but lacks a re-issuance guard.

## Recommendations

### Immediate Actions (High Priority)

1. Fix `compare_string_views()` to bound reads by the shorter of the two operands (Finding 1) — this is the priority item for this cycle.
2. Correct the DATA-phase size check to use `smtp_config->email_limit_size()` (Finding 2).
3. Terminate the session when the command/log buffer limit is exceeded (Finding 3).
4. Add an `is_tls` guard against repeated STARTTLS (Finding 4).

### Medium-term Improvements

1. Pin Seastar/OpenSSL/Boost versions and add CI dependency scanning (Finding 5).
2. Harden TLS configuration: minimum version + cipher suite restriction (Finding 6).
3. Add a source-IP allow-list for PROXY protocol connections; document trusted-proxy-only deployment (Finding 7).
4. Implement per-IP connection/rate limiting (Finding 8).
5. Strengthen UUID generation seeding (Finding 9); fix the apex-domain off-by-one (Finding 10).

### Operational Security

1. Enable `proxy_support` only behind trusted, network-isolated proxies.
2. Run with least privilege; restrictive permissions on data/log directories.
3. Monitor connection patterns and disk usage for spool/log directories, particularly given Finding 3.
4. Keep host OS and OpenSSL patched.

## Conclusion

Version 1.6.2 continues to demonstrate solid protocol-level design and input-validation fundamentals. This independent review, however, surfaces a previously unreported memory-safety defect (Finding 1) in the domain-matching logic underpinning the server's primary anti-relay control, reachable pre-authentication, along with several enforcement and logic gaps that reduce the effectiveness of controls the project already believes it has (Findings 2–4, 10). None of the previously reported operational gaps (dependency pinning, TLS hardening, proxy trust, rate limiting) have been remediated in this snapshot.

**Risk Level**: Medium
**Recommended Actions**: Address the out-of-bounds read (Finding 1) and the two non-enforcing size/session-termination checks (Findings 2–3) immediately; the remaining items on the timelines above.
