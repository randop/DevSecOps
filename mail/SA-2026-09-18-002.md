# Security Audit Report for Mail SMTP Server (Version 1.6.2)

**Project:** mail
**Version:** 1.6.2
**Audit Date:** 2026-09-18
**Auditor:** Automated Security Analysis (OpenAI GPT-5.6 Luna)
**Audit Type:** Source Code Security Review (Static)
**Artifact:** Current `master` branch
**Report ID:** SA-2026-09-18-002
**Scope:** Security-sensitive source, configuration, parsing, filesystem, SMTP state handling, TLS, dependency/build configuration and resource-control paths

## Executive Summary

This audit reviewed the current `master` branch of the Mail SMTP server, a self-hosted SMTP server implemented in modern C++23 using Seastar, OpenSSL and Boost. The repository reports version 1.6.2 and requires Seastar v25.05.0 in its source headers.

The codebase has several good security properties:

* Strong basic email-address validation.
* Domain-based recipient authorization that prevents straightforward open relay.
* Explicit message-size and idle-session controls.
* Randomized UUID-derived spool and log filenames.
* X.509 certificate and private-key validation during startup.
* PROXY protocol v2 signature/version/address-family validation.
* No obvious classic buffer-overflow pattern in the reviewed normal SMTP parsing paths.

However, this review identified **two significant issues**:

1. **High — SMTP command logging can grow without bound after the configured command-buffer limit is exceeded.** The implementation detects that the log has exceeded `SMTP_COMMAND_BUFFER_SIZE_LIMIT`, but does not terminate or otherwise cap the session. An attacker can repeatedly send command-mode data and cause unbounded per-connection log-file growth, potentially exhausting disk space across the available connection slots.
2. **High — `split_email_domains()` writes past a fixed-size 12-element array when `all_email_domains` contains more than 12 entries.** The configuration value is converted into an unconstrained vector and then copied into the fixed array without a bounds check. A remote connection is sufficient to reach this function, so a malformed local configuration can become a remotely triggerable memory-corruption condition.

Additional medium-risk concerns include lack of explicit TLS policy, unrestricted trust of PROXY protocol sources, absence of per-IP connection/rate limiting, and dependency versions being delegated to the host environment.

**Overall Risk Level: Medium–High**

The principal risk is no longer simply operational dependency/TLS configuration. The current implementation contains at least one credible resource-exhaustion vulnerability and one potential out-of-bounds write dependent on configuration.

# Findings

## High Priority Issues

### 1. Unbounded SMTP Command Log Growth / Disk Exhaustion

**Severity:** High
**Status:** Confirmed by source review
**CWE:** CWE-400 — Uncontrolled Resource Consumption
**Attack Vector:** Remote network connection

### Description

The server creates a per-session logfile and writes command-mode input to it:

```text
co_await session->write_log(buffer_stream.share());
```

The implementation then checks whether the log has exceeded:

```text
SMTP_COMMAND_BUFFER_SIZE_LIMIT = 2500
```

However, exceeding the limit only generates an error and SMTP response:

```text
applog.error("{} client {} exceeded command buffer limit", sid, ip);
...
"552 5.3.4 Message size limit exceeded"
```

The connection is **not closed**, the logfile is not deleted/truncated, and command processing continues.

`write_log()` increments the logfile position, so the check does not impose an actual hard storage limit.

### Security Impact

A remote attacker can:

1. Establish an SMTP connection.
2. Send command-mode data.
3. Exceed the nominal 2500-byte command-log limit.
4. Continue sending additional command-mode data.
5. Repeatedly rearm the idle timer by sending data.
6. Cause the session logfile to continue growing.

Multiple concurrent connections can multiply the effect. The server has a per-shard connection semaphore, defaulting to 1024 connections per shard or 24 in economy mode.

This creates a practical **disk-exhaustion / denial-of-service** path if the SMTP service has a sufficiently writable spool/log filesystem.

### Recommendation

Make the command-log limit a real hard limit.

Preferred behavior:

```text
if (session->get_log_size() > SMTP_COMMAND_BUFFER_SIZE_LIMIT) {
    send 552;
    close session;
    return;
}
```

Better still:

* Enforce the limit before writing the next buffer.
* Account for the current buffer size, not only cumulative size after writing.
* Close the connection immediately after the limit is reached.
* Consider disabling session logging after the threshold and retaining only a bounded diagnostic record.
* Monitor available filesystem capacity.
* Consider a global/per-directory spool and logfile quota.

### Priority

**Fix before production exposure.**

## 2. Out-of-Bounds Write in Configured Email-Domain List

**Severity:** High
**Status:** Confirmed by source review
**CWE:** CWE-787 — Out-of-bounds Write
**Attack Vector:** Remote trigger with vulnerable configuration

### Description

The project defines a fixed maximum of 12 email domains:

```text
MAX_EMAIL_DOMAINS = 12
```

and stores them in:

```text
std::array<seastar::sstring, MAX_EMAIL_DOMAINS> domains;
```

The environment-variable loader correctly limits the number of entries.

However, `split_email_domains()` does not enforce that same limit:

```text
auto parts = split_and_trim(all_email_domains);

...

for (auto &x : parts) {
    result.domains[result.count] = x;
    result.count++;
}
```

`split_and_trim()` returns an unconstrained vector, while `result.domains` contains only 12 elements.

The vulnerable function is called for each incoming connection:

```text
email_helpers::split_email_domains(
    smtp_config->all_email_domains(),
    smtp_config->domain());
```

### Security Impact

A configuration such as:

```text
all_email_domains=domain1.example,domain2.example,...,domain13.example,...
```

can cause `split_email_domains()` to write beyond the end of the fixed array.

The configuration itself requires local administrative access, but **once such a configuration is present, an unauthenticated remote SMTP client can trigger the vulnerable code path simply by connecting**.

Depending on compiler/runtime layout, consequences may include:

* Process crash.
* Memory corruption.
* Undefined behavior.
* Potential code execution in a sufficiently favorable exploitation scenario.

The practical exploitability should be confirmed with ASan/UBSan and a reproducer before assigning a CVSS score.

### Recommendation

Hard-cap the copy:

```text
for (auto &x : parts) {
    if (result.count >= MAX_EMAIL_DOMAINS)
        break;

    result.domains[result.count++] = x;
}
```

Preferably reject invalid configuration at startup rather than silently truncating it:

```text
if (parts.size() > MAX_EMAIL_DOMAINS)
    throw configuration_error(...);
```

The same maximum should be enforced consistently at every configuration boundary.

### Priority

**Fix before production exposure.**

# Medium Priority Issues

## 3. TLS Policy Is Not Explicitly Hardened

**Severity:** Medium
**Status:** Requires hardening

The application loads X.509 credentials and performs STARTTLS using Seastar's TLS wrapper.

However, the application does not explicitly specify:

* Minimum TLS version.
* Maximum TLS version.
* Cipher policy.
* Elliptic-curve/group policy.
* Other OpenSSL security-level requirements.

The build simply uses the host-provided OpenSSL:

```text
find_package(OpenSSL REQUIRED)
```

with no application-level version or cryptographic-policy pinning.

This matters because OpenSSL continues to receive security fixes. As of the audit date, OpenSSL 3.5.8, 3.6.4 and 3.0.22 were current releases in their respective branches, with the August 2026 security releases addressing multiple vulnerabilities.

### Recommendation

Document and enforce a production TLS policy:

* Minimum TLS 1.2.
* Prefer TLS 1.3 where compatible.
* Explicitly disable obsolete protocols.
* Use modern cipher suites.
* Track OpenSSL security advisories.
* Test STARTTLS downgrade/renegotiation behavior.

## 4. PROXY Protocol Trust Boundary Is Configuration-Only

**Severity:** Medium
**Status:** Requires operational control

When `proxy_support` is enabled, the server accepts a PROXY v2 header and replaces the observed client address with the address contained in the header. The header signature, version/command and supported address families are validated.

There is no source-IP allow-list for hosts permitted to submit PROXY protocol headers.

### Security Impact

If the SMTP port is directly reachable by an attacker while PROXY support is enabled, the attacker can provide an arbitrary source address in a syntactically valid PROXY header.

This affects:

* Logging.
* IP-based controls added later.
* Abuse attribution.
* Future rate-limiting decisions.
* Any security policy that trusts the recorded client IP.

### Recommendation

Either:

1. Enable PROXY protocol only on an isolated listener reachable exclusively from trusted load balancers; or
2. Add a configurable trusted-proxy CIDR allow-list.

Do not treat PROXY protocol syntax validation as authentication of the proxy.

---

## 5. No Per-IP Connection or Rate Limiting

**Severity:** Medium
**Status:** Requires improvement

The server has a per-shard connection semaphore, with a default limit of 1024 and an economy-mode limit of 24. Sessions also have a default 120-second idle timeout.

These controls limit total concurrency but do not limit one source IP.

### Security Impact

An attacker can consume a significant portion of available connection capacity from one or a small number of source addresses.

Combined with the logfile exhaustion issue, this increases the potential impact of unauthenticated network abuse.

### Recommendation

Implement:

* Per-source concurrent connection limits.
* Connection-rate limiting.
* Temporary backoff for abusive sources.
* Optional subnet-level controls.
* Integration with firewall/fail2ban-style operational controls.

---

## 6. SMTP DATA Framing Has Protocol-State Edge Cases

**Severity:** Medium
**Status:** Requires further testing

During DATA processing, the implementation writes the complete received buffer to the message file before determining whether the buffer contains the SMTP terminator:

```text
co_await session->write_data(std::move(email_stream));
...
find(SMTP_DATA_END);
```

The terminator is searched in only the final 16 bytes maintained by `fixed_stream`.

This design creates potential framing/desynchronization edge cases when a single network read contains:

```text
<message>\r\n.\r\n<additional SMTP commands>
```

The bytes after the terminator have already been written to the message file rather than being reprocessed as subsequent SMTP commands.

### Security Impact

The primary concern is protocol correctness and message-boundary confusion rather than an immediately demonstrated memory-safety issue.

### Recommendation

Implement a proper SMTP DATA state machine that:

* Searches for the terminator across buffer boundaries.
* Stops writing at the exact terminator.
* Preserves/reprocesses bytes following the terminator.
* Implements SMTP dot-stuffing correctly.
* Enforces the message-size limit before committing excessive data.

Add regression tests for terminators at every byte offset in a network buffer.

# Low Priority Issues

## 7. Authentication Is Not Implemented

**Severity:** Low / Design-dependent
**Status:** By design

`AUTH` returns:

```text
502 Command not implemented
```

The server instead relies on recipient-domain matching for relay control.

This is not itself an authentication bypass because the implementation does not claim to provide authenticated submission.

However, operators should understand that:

* There is no SMTP AUTH.
* A client cannot authenticate for submission.
* Domain membership is the principal recipient authorization mechanism.
* This design is unsuitable for deployments requiring authenticated outbound submission without an external trust boundary.

### Recommendation

Document the intended deployment model clearly. If authenticated submission is required, introduce an explicit authentication/submission design rather than treating domain validation as user authentication.

---

## 8. Client IP and Session Metadata Are Logged

**Severity:** Low
**Status:** Expected behavior with privacy implications

The implementation logs client IP addresses, session identifiers, connection events and SMTP command data. Per-session log files are generated using UUID-derived names.

This is not a direct vulnerability, but logs may contain sensitive operational metadata.

### Recommendation

* Restrict logfile permissions.
* Define retention periods.
* Protect logs as personal/confidential data.
* Consider configurable command logging levels.
* Avoid forwarding raw SMTP logs to less-trusted centralized systems.

# Positive Security Controls

## Input Validation

Email local-part and domain validation is implemented explicitly rather than relying solely on ad-hoc string operations. The code rejects malformed domains, leading/trailing dots and invalid local-part characters.

## Relay Control

`RCPT TO` addresses are parsed and compared against configured accepted domains before being added to the recipient list. DATA processing requires at least one accepted recipient.

This prevents the obvious open-relay condition in the reviewed path.

## Resource Limits

The server has:

* 512 KiB default email-size limit.
* 120-second default session timeout.
* Connection concurrency limits.
* A nominal 2500-byte command-log threshold.

The command-log threshold requires remediation because it is currently not a true hard limit.

## Filesystem Handling

Email and log filenames are generated from UUID-derived values rather than attacker-controlled SMTP strings. Directory paths are canonicalized during startup and writability is checked.

## TLS Credential Validation

The application parses the configured X.509 certificate and verifies the private key before starting the server.

The actual TLS socket upgrade is performed through Seastar's TLS server wrapper.

## PROXY v2 Parsing

The implementation checks the PROXY v2 signature, version/command, payload length and supported IPv4/IPv6 address families before accepting the supplied address.

# Dependency Analysis

## Seastar

The source identifies Seastar v25.05.0 as the required framework version, but the CMake configuration uses:

```text
find_package(Seastar REQUIRED)
```

without pinning the dependency to that version.

### Risk

Builds can therefore consume different Seastar versions depending on the host environment.

### Recommendation

Use a reproducible dependency strategy:

* Pin Seastar.
* Record the exact commit/release.
* Produce reproducible build manifests.
* Run dependency vulnerability scanning in CI.

---

## OpenSSL

OpenSSL is also discovered from the host:

```text
find_package(OpenSSL REQUIRED)
```

No minimum or exact version is enforced by the project.

OpenSSL continues to publish security releases; for example, the August 25, 2026 releases addressed multiple issues across the supported branches.

### Recommendation

Require a supported patched OpenSSL release and establish a regular security-update process.

For long-lived production deployments, OpenSSL 3.5 is currently the LTS branch listed by the OpenSSL project.

---

## Boost

Boost JSON and `program_options` are linked without an explicit version requirement:

```text
find_package(Boost REQUIRED COMPONENTS json program_options)
```

### Recommendation

Pin or otherwise constrain the tested Boost version and include it in dependency scanning.

# Build Security

The release build enables several hardening-related compiler/linker settings including hidden symbol visibility, `--as-needed`, stripping and interprocedural optimization.

However, the build does not visibly enable a security-oriented compiler baseline such as:

* Stack protector.
* Control-flow protection.
* Fortify source where applicable.
* ASan/UBSan security CI builds.
* Fuzzing targets.

### Recommendation

Add a dedicated security CI configuration:

```text
ASan + UBSan
-Wall -Wextra -Wpedantic
-fstack-protector-strong
-D_FORTIFY_SOURCE=3
```

where supported by the compiler/platform.

For release builds, evaluate:

* PIE.
* RELRO.
* NOW binding.
* CET/CF protection where available.

# Recommended Actions

## Immediate — Before Production

1. **Fix the command-log resource exhaustion issue.**

   * Make the command-log limit a hard cap.
   * Close the SMTP connection once exceeded.
   * Do not write unbounded data before checking the limit.

2. **Fix `split_email_domains()` bounds handling.**

   * Enforce `MAX_EMAIL_DOMAINS`.
   * Reject oversized configuration during startup.
   * Add ASan/UBSan regression coverage.

3. Add a regression test specifically containing more than 12 configured domains.

4. Add a regression test that sends unlimited command-mode input and verifies that the connection terminates once the configured limit is reached.

## Short Term

5. Add explicit TLS minimum-version and cipher-policy configuration.

6. Add trusted-proxy source restrictions for PROXY protocol.

7. Add per-IP connection/rate limiting.

8. Correct SMTP DATA framing so bytes following `<CRLF>.<CRLF>` are not accidentally incorporated into the message.

9. Add security-oriented CI with ASan and UBSan.

10. Pin or reproducibly lock Seastar, Boost and OpenSSL versions.

## Operational

11. Run the SMTP service with least filesystem privileges.

12. Put spool and log directories on controlled filesystems with quotas/monitoring.

13. Monitor disk utilization and SMTP connection counts.

14. Restrict direct access to PROXY-enabled listeners.

15. Maintain an explicit OpenSSL security-update procedure.

# Conclusion

The current 1.6.2 codebase retains several sound security fundamentals, particularly domain-based relay control, structured email validation, TLS credential checking, resource limits, and non-user-controlled spool filenames.

The security posture is nevertheless **Medium–High risk** until two implementation issues are addressed:

* The command-log "buffer limit" currently detects excessive input but does not stop storage growth, permitting a remotely driven disk-exhaustion attack.
* The configured email-domain list can exceed its fixed 12-element storage array, producing an out-of-bounds write reachable from the SMTP connection path.

These findings materially change the assessment from the supplied previous report, which characterized the remaining risk primarily as dependency/TLS/operational hardening.

After these two issues are fixed and regression-tested, the remaining work is primarily hardening: TLS policy, proxy trust boundaries, connection abuse controls, dependency reproducibility, and protocol-state testing.

**Risk Level: Medium–High**

**Recommended remediation window:** Critical implementation fixes immediately; hardening and dependency controls within 30 days.
