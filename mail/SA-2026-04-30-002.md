# 1. EXECUTIVE SUMMARY

A full static review was performed on the provided source tree (29 files). The project is a Seastar-based mail server with custom helpers for email parsing, file handling, networking, and cryptography.

The codebase demonstrates:

* Strong use of `noexcept`, bounded logic, and manual validation
* Awareness of RFC-style parsing for email addresses
* Custom implementations for critical parsing paths

However, multiple **security-critical gaps** were identified in:

* Input canonicalization and normalization
* Trust boundaries (environment variables, file paths)
* Email parsing completeness (RFC compliance gaps)
* Potential injection and abuse vectors
* Missing defensive limits (length, size, resource constraints)

**Overall Risk Rating:** High
**Primary Concern:** Input handling and trust boundary violations in a network-facing mail system

# 4. FINDINGS

---

## 4.1 Email Validation – Incomplete RFC Coverage

### Location

* `src/email_helpers.cpp`

### Observations

* `validate_email()` splits only on first `'@'`
* `validate_local()` and `validate_domain()` enforce partial rules
* No support for:

  * Internationalized domains (IDN / punycode)
  * UTF-8 normalization
  * Comments or obsolete RFC constructs
* Domain validation requires a dot but does not enforce TLD rules

### Impact

* Valid addresses may be rejected
* Invalid but syntactically acceptable edge cases may pass
* No canonicalization → downstream mismatch risk

### Risk Level

High

---

## 4.2 No Input Length Constraints

### Location

* Email parsing
* String helpers
* Domain joining (`join_email_domains`)

### Observations

* No maximum length checks for:

  * Local part
  * Domain
  * Entire email string
* Memory allocation based on input size

### Impact

* Memory exhaustion (DoS)
* Large payload amplification

### Risk Level

High

---

## 4.3 Environment Variable Trust

### Location

* `load_email_domains()`

### Observations

* Direct use of `std::getenv("MAIL_EMAIL_DOMAINS")`
* No validation, sanitization, or bounds checking
* Parsed into internal domain list

### Impact

* Configuration injection
* Malicious domain insertion
* Potential downstream trust abuse

### Risk Level

High

---

## 4.4 Lack of Canonicalization

### Location

* Email parsing
* Domain handling

### Observations

* No normalization for:

  * Case (domain should be case-insensitive)
  * Unicode equivalence
  * Trailing dots
* No punycode conversion

### Impact

* Duplicate identity bypass
* Spoofing via visually similar domains
* Authentication inconsistencies

### Risk Level

High

---

## 4.5 Domain Validation Gaps

### Location

* `validate_domain()`

### Observations

* Allows:

  * Arbitrary label lengths
  * No enforcement of 63-char label limit
  * No total domain length check (253 max)
* Only checks:

  * alnum / `-` / `.`
  * dot presence

### Impact

* Invalid domains accepted
* Potential resolver inconsistencies

### Risk Level

Medium

---

## 4.6 Missing Defensive Parsing Limits

### Location

* All parsing helpers

### Observations

* No limits on:

  * Number of domains parsed
  * String sizes
  * Iteration bounds beyond container size

### Impact

* CPU exhaustion
* Memory pressure under malicious input

### Risk Level

High

# 7. RECOMMENDATIONS

## 7.1 Email Handling

* Enforce full RFC 5321 / 5322 compliance or explicitly restrict scope
* Add:

  * length limits (local ≤ 64, domain ≤ 253)
  * punycode conversion
  * normalization (lowercase domain)
* Reject:

  * overly long inputs
  * non-canonical forms

---

## 7.2 Input Limits

* Global caps:

  * email length
  * domain count
  * buffer sizes
* Enforce early rejection

---

## 7.3 Environment Security

* Validate `MAIL_EMAIL_DOMAINS`
* Enforce:

  * max entries
  * valid domain format
* Reject malformed entries

---

## 7.4 File System Safety

* Enforce:

  * canonical path resolution
  * root directory jail
  * symlink checks (`O_NOFOLLOW`)
* Reject:

  * relative traversal
  * hidden/system paths

---

## 7.5 Cryptographic Hardening

* Enforce:

  * full certificate chain validation
  * hostname verification
  * revocation checks
* Avoid accepting self-signed certificates by default

---

## 7.6 Resource Protection

* Add:

  * rate limiting
  * connection caps
  * input throttling

---

## 7.7 Defensive Parsing

* Add strict bounds to all loops and buffers
* Reject:

  * excessively nested or large inputs

---

# 8. FINAL VERDICT

The project shows strong low-level control and intent for correctness, but it lacks critical safeguards required for a production-grade mail system exposed to untrusted input.

**Security posture is not sufficient for deployment in adversarial environments without remediation.**
